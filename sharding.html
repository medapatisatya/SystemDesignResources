Database Sharding, taught the way an interviewer actually grades it

01Sharding fundamentals

Sharding is what you reach for when a single machine can no longer hold, or serve, all of your data — not before.

Database sharding is splitting one logical dataset into multiple independent physical databases (shards), each holding a disjoint subset of the rows, so that no single machine has to store or serve all the data. The application (or a routing layer) decides which shard owns a given piece of data and sends the query there.

Without sharding:

Application
     │
     ▼
Single Database  ──►  everything lives here: storage, CPU, IOPS, connections
     │
     ▼
Huge Dataset

With sharding:

                     ┌──► Shard 1  (rows 1)
Application ─► Router├──► Shard 2  (rows 2)
                     ├──► Shard 3  (rows 3)
                     └──► Shard 4  (rows 4)

Each shard is a complete, independent database — its own disk, its own CPU, its own connection pool, often its own primary/replica pair. Nothing is shared between shards except the routing logic that decides where a row lives.

Sharding vs. partitioning

Partitioning is the general concept of splitting data into smaller pieces. Sharding is a specific, aggressive form of partitioning: the pieces live on separate physical database instances, usually on separate machines. A single Postgres instance with date-range table partitions is partitioning, not sharding — it's still one server, one CPU, one disk. The moment those partitions move to different servers that don't share hardware, you've crossed into sharding.

Sharding vs. replication

These solve opposite problems and get confused constantly. Replication copies the same data onto multiple machines — it buys you availability and read throughput, but every replica still has to store the full dataset and every write still has to land somewhere. Sharding splits different data onto different machines — it buys you write throughput and storage capacity, because each shard only holds a fraction of the data and a fraction of the writes.

Sharding vs. caching

Caching removes read load from the database by serving hot data from memory closer to the client. It does nothing for storage growth or write throughput — a cache miss still has to hit a full-sized, non-sharded database. Caching and sharding are complementary, not substitutes: caching buys you time before you need to shard, and once sharded, caching still sits in front of the shards.

02Why do we need sharding?

Six distinct bottlenecks push teams toward sharding. Naming the actual bottleneck is the interview signal — "it's too big" is not an answer.

Storage bottleneck

A single server's disk (or the largest instance type your cloud offers) caps out — say your dataset hits 20 TB and the biggest volume you can attach is 16 TB, or backup/restore time on a 20 TB volume becomes operationally unworkable.

CPU bottleneck

Sustained 95% CPU means every query — including simple ones — queues behind others. Vertical scaling has a ceiling (the biggest instance SKU), and beyond it there is no bigger box to buy.

Memory bottleneck

Working set no longer fits in RAM/buffer cache, so reads that used to be memory-hits become disk-hits, and latency degrades non-linearly.

I/O bottleneck

Disk IOPS/throughput saturate even though CPU and RAM look fine — common with write-heavy workloads and mechanical or shared network storage.

Connection bottleneck

A single Postgres/MySQL instance supports on the order of a few thousand concurrent connections before context-switching overhead dominates — at scale, thousands of app instances exhaust this before CPU is the limit.

Read bottleneck

Try read replicas before sharding. If the workload is read-heavy, adding read replicas behind a load balancer scales reads horizontally without touching the write path or splitting data at all — much cheaper than sharding.

Write bottleneck — why replication alone doesn't fix it

Replicas serve reads, but every write still has to go through the single primary and then propagate to every replica. Adding replicas increases total write amplification (the primary now fans out to more machines) without increasing how many writes/sec the system can accept. If your bottleneck is write throughput or the primary's storage, replication cannot help — this is precisely the situation sharding was built for: splitting the primary itself into many primaries, each owning a slice of the keyspace.

03When should I shard?

Interviewer signal

Do not shard just because the system is "large." Sharding is the most expensive, most operationally complex scaling technique on the list — it introduces cross-shard queries, distributed transactions, and rebalancing pain that a single database never had. Reach for it last.

Before proposing sharding, walk through cheaper options and explain why each one is insufficient for the stated bottleneck:

  • Index / query optimization — often a missing index or a bad query plan is the entire problem.
  • Vertical scaling — bigger CPU/RAM/disk buys time cheaply, until you hit the largest instance available.
  • Caching — absorbs read-heavy hot-key traffic before it reaches the DB.
  • Read replicas — scales reads horizontally; does nothing for writes or storage.
  • Connection pooling (e.g. PgBouncer) — fixes connection-count bottlenecks without touching data layout.
  • Better schema design / archiving cold data — often storage "bloat" is really unindexed, un-archived history.
  • Partitioning (single-instance) — splits a huge table into manageable chunks without leaving one machine.
Vertical Scaling
       │
       ▼
Indexes / Query Optimization
       │
       ▼
Caching
       │
       ▼
Read Replicas
       │

The exact order depends on the workload — a write-heavy ledger system exhausts vertical scaling and partitioning long before a read-heavy content site does, which might live comfortably on read replicas + caching for years. Say this explicitly in an interview: the progression is a guideline, not a law.

04Horizontal vs. vertical partitioning

Horizontal partitioning (sharding's building block)

Shard 1 → Users 1–1M
Shard 2 → Users 1M–2M
Shard 3 → Users 2M–3M

Splits rows. Every shard has the identical schema; each just owns a different slice of the key space. This is what "sharding" almost always refers to.

Vertical partitioning

User DB
 ├── User identity
 ├── User profile
 └── User preferences

Separate storage
 └── Large media / blob data

Splits columns or tables by access pattern — rarely-read blobs move to object storage, hot identity fields stay in the primary relational store. Useful before sharding: it shrinks the working set and can defer horizontal sharding entirely.

The two combine in real systems: vertically separate blobs and cold data first, then horizontally shard whatever hot, structured data remains.

05Sharding strategies

Five patterns cover essentially every sharded system you'll be asked to design. Know the failure mode of each cold.

A. Range-based sharding

user_id 1–1,000,000     → Shard 1
user_id 1,000,001–2M    → Shard 2
user_id 2,000,001–3M    → Shard 3

+ range queries+ simple to reason about− hot shards− uneven growth

Range queries (WHERE user_id BETWEEN ...) hit a single contiguous shard — huge win for time-series and analytics workloads. The cost: if the key correlates with time or insertion order, all new writes pile onto the newest, highest-numbered shard while old shards sit idle — a classic hot shard. Rebalancing means physically splitting one range into two, which requires moving real data.

Good fit: a system whose dominant query pattern is range scans over an ordered key — e.g. an analytics platform querying by date range, or a system explicitly designed to route "recent" traffic to dedicated, over-provisioned shards.

B. Hash-based sharding

shard = hash(user_id) % N

+ even distribution+ no hot ranges− range queries need scatter-gather− resizing reshuffles almost everything

A good hash function spreads keys near-uniformly across shards regardless of insertion order, eliminating the "newest range is hottest" problem. The catch is the modulo itself: changing % 4 to % 5 changes the target shard for the overwhelming majority of keys, not just the new fraction you intended to move — because hash(k) % 4 and hash(k) % 5 agree only by coincidence. That single property is why naive mod-hashing is rarely used at scale for anything that needs to grow — teams move to consistent hashing instead.

C. Consistent hashing

Nodes and keys are placed on the same conceptual ring (0 to 232−1, hashed). A key belongs to the first node clockwise from its position. Adding or removing a node only remaps the keys between it and its neighbor — not the whole ring.

              0
              │
      ┌───────┼───────┐
      │               │
 Node D           Node A
      │               │
      │       ●key1   │
 Node C           Node B
      │               │
      └───────┼───────┘
             key1 → next node clockwise = Node A

Adding Node E between A and B only steals keys
that used to belong to B — C, D, A are untouched.

Virtual nodes (many ring positions per physical node) fix the uneven-load problem that plain consistent hashing has with a small number of nodes, and make rebalancing smoother — a new physical node picks up small slices from many peers instead of one large slice from one neighbor. This is why consistent hashing underlies Cassandra, DynamoDB, and most distributed caches: it minimizes data movement on membership changes, which is the single hardest operational problem in sharding.

D. Directory-based sharding

User ID → Shard Mapping   (lookup service / metadata DB)

101 → Shard A
102 → Shard C
103 → Shard B

+ maximum flexibility (any key → any shard)+ rebalance by editing rows, not moving hash logic+ extra infrastructure− lookup service is a new single point of failure/latency

Instead of computing the shard mathematically, a lookup service stores an explicit mapping. This makes rebalancing trivial in principle (move a row, update the map) but adds a hop to every single query and turns the directory itself into critical infrastructure that needs its own replication and caching.

E. Geographic sharding

India users  → India shard
US users     → US shard
Europe users → Europe shard

+ lower latency (data near users)+ data residency / regulatory compliance (GDPR, etc.)+ regional blast-radius isolation− users who travel or relocate

A user who moves from India to the US either leaves stale data behind, needs an explicit migration job, or requires the application to query multiple regions — the "moving user" problem is the standard follow-up an interviewer will ask, and the standard answer is: keep a thin global directory of "home region" per user, and support an explicit, asynchronous re-homing migration.

06Choosing a shard key

This is the single highest-leverage decision in a sharding design — a bad shard key cannot be fixed without resharding the whole system.

A good shard key needs, simultaneously:

  • High cardinality — enough distinct values to spread across many shards (a boolean or a 3-value enum can never do this).
  • Even distribution — no single value should own a disproportionate share of rows or traffic.
  • Query locality — the majority of your real queries should be answerable by hitting one shard, not all of them.
  • Write distribution — new writes should land across many shards, not concentrate on one (see sequential-ID problem, §8).
  • Stability — the key shouldn't change after the row is written; a mutable shard key means physically moving the row.

user_id

Usually strong: high cardinality, stable, and most product queries ("this user's orders," "this user's posts") are naturally scoped to one user — excellent locality. Weakness: cross-user analytical queries ("all orders in India") become scatter-gather.

country

Low cardinality (under 200 values) and wildly uneven — a handful of countries hold most users. Guarantees hot shards. Only usable as a *secondary* dimension (e.g. combined with geographic sharding for compliance), never as the sole key at scale.

created_at

Great for range queries, terrible for write distribution — every new row has the newest timestamp, so all writes hit the same (newest) shard/range. Classic hot-shard generator; needs hashing or salting if used at all.

07Hot shards / hotspots

Shard 1 → 10% traffic
Shard 2 → 10% traffic
Shard 3 → 70% traffic   ◄── hot shard
Shard 4 → 10% traffic

A hot shard is a shard receiving disproportionate load relative to its peers, even though the sharding scheme is "correct" on paper. Common causes: celebrity users (one row gets millions of reads), viral products, recent-timestamp writes concentrating on the newest range, and geographic concentration of users.

Mitigations, roughly in order of invasiveness

  • Better shard key — if the root cause is the key itself, no amount of infrastructure fixes it.
  • Hashing — breaks correlation between key and load for most workloads.
  • Key salting — append a random suffix to a hot key so its writes fan out across multiple physical partitions, then merge on read (common for celebrity-user write fan-out).
  • Virtual shards — let one hot logical shard be backed by many small physical pieces that can be independently moved off an overloaded node.
  • Consistent hashing — spreads rebalancing cost when a hot node needs relief.
  • Splitting the hot partition — surgically break one overloaded shard into two.
  • Caching — absorb read-heavy hotspots (celebrity profile reads) before they reach the shard at all.

08Sequential IDs and hotspots

ID: 100001, 100002, 100003, 100004, ...

If shards are assigned by range over a monotonically increasing ID, every new write goes to whichever shard owns the current tail of the range — every other shard sits idle for writes. This is one of the most common real-world sharding mistakes.

AlternativeTrade-off
Hash-based distributionEven write spread; loses natural ordering / range-scan ability.
UUIDs (v4)Fully random, great spread; larger (128-bit) index footprint, no embedded ordering or timestamp.
Snowflake-style IDsTimestamp + machine ID + sequence — roughly time-ordered and distributed enough to avoid single-node hotspotting; the standard choice at scale (Twitter, Discord, Instagram).
Randomized keysSimilar to UUIDs; sometimes just a random prefix bolted onto a sequential suffix.
Time + randomness (e.g. ULID)Sortable-ish while spreading write load better than pure sequential IDs; a middle ground.

09Sharding architecture

Application-level sharding

Application
    │
    ▼
Shard Router (in-app logic: hash(key) → shard)
    │
┌───┼───────┬───────┐
▼   ▼       ▼       ▼
Shard 1  Shard 2  Shard 3

The application itself computes the target shard and opens a connection to it directly. Fast (no extra network hop) and simple to start, but every service that touches the data has to embed and keep in sync the same routing logic — a real maintenance cost as the number of services grows.

Database proxy / router layer

A dedicated proxy (e.g. Vitess's vtgate, or a custom router) sits between the application and the shards, looks up routing via a metadata service, and forwards the query. This centralizes routing logic — one place to update when shards move — at the cost of an extra network hop and a new piece of infrastructure that itself needs to be highly available.

10Sharding + replication

Production systems almost always run both, because they solve different axes of the scaling problem.

        Shard 1                    Shard 2
     ┌──────────┐               ┌──────────┐
     │ Primary  │               │ Primary  │
     └────┬─────┘               └────┬─────┘
          ▼                          ▼
     ┌──────────┐               ┌──────────┐
     │ Replica  │               │ Replica  │
     └──────────┘               └──────────┘

Sharding scales writes and storage by giving each slice of the keyspace its own primary. Replication scales reads and availability within a shard by giving that primary standby copies to read from and fail over to. Neither substitutes for the other: replication alone caps write throughput at whatever one primary can do (see §2); sharding alone with no replicas means a single disk failure on any shard takes that entire slice of your data offline with no failover target.

11Cross-shard queries

SELECT * FROM users WHERE country = 'India';

If users is sharded by user_id, "all Indian users" could be on any shard — there is no single shard to route this query to.

  • Scatter-gather — fan the query out to every shard in parallel, then merge results in the application/router. Correct but expensive: latency is bounded by the slowest shard, and load on every shard spikes for what should be a narrow query.
  • Global secondary index — maintain a separate, denormalized index (e.g. country → [user_ids]) that itself may be sharded by country, so the query becomes a single lookup instead of a fan-out.
  • Dedicated search system (Elasticsearch/OpenSearch) — for genuinely ad-hoc, multi-attribute queries, replicate the relevant fields into a search index built for exactly this access pattern instead of forcing the shards to serve it.

The performance implication to state out loud in an interview: scatter-gather turns a query's cost from O(1 shard) into O(N shards), and its tail latency into the max of N tail latencies — this is why teams route around it with secondary indexes or search systems rather than accepting it as the default.

12Cross-shard joins

SELECT * FROM orders JOIN users ON orders.user_id = users.id;

users  → Shard 1
orders → Shard 4   (different shard key!)

A relational join assumes both tables are queryable from the same engine. Across shards there is no join operator — you'd have to fetch matching rows from each shard separately and stitch them together in application code, which is slow and loses transactional consistency between the two reads.

  • Co-locate related data — shard orders by the same key as users (e.g. user_id), so a user's orders always live on the same shard as the user. This is the single most powerful lever in sharded schema design.
  • Denormalization — embed the data you'd otherwise join (e.g. store a snapshot of the user's name on the order row) so no join is needed at read time.
  • Application-side joins — fetch from each shard and merge in code, accepted only for low-frequency, low-latency-sensitivity queries.
  • Separate analytical systems — replicate all shards into a data warehouse (via CDC) where joins across the full dataset are cheap, and keep the online shards join-free.
Why this matters

Data locality — designing shard keys so that data accessed together lives together — is the difference between a sharded system that feels like a normal database and one that requires a distributed-systems PhD for every query.

13Cross-shard transactions

Transfer $100

Account A → Shard 1
Account B → Shard 5

Need atomically:  Debit A  +  Credit B

A normal ACID transaction assumes one engine coordinating one commit log. Across two shards, if the debit commits on Shard 1 and the credit then fails on Shard 5, you've silently destroyed money.

  • Two-phase commit (2PC) — a coordinator asks every participant to "prepare," then commits everywhere only if all say yes. Gives strong atomicity but blocks all participants on a slow or failed coordinator, and doesn't scale well under contention.
  • Distributed transaction protocols (e.g. Spanner's TrueTime-based commits) — some systems build genuinely consistent cross-shard transactions into the storage layer, at real latency and complexity cost.
  • Saga pattern — break the transaction into a sequence of local transactions, each with a defined compensating action if a later step fails (e.g. "credit failed → run compensating debit-reversal"). Gives eventual consistency instead of atomicity, but scales far better and avoids blocking.
  • Event-driven / compensating transactions — publish "debited" and "credited" events and let downstream consumers reconcile asynchronously, with retries and dead-letter handling for failures.

The trade-off to name explicitly: 2PC buys correctness by sacrificing availability and latency; sagas buy availability and scale by sacrificing immediate atomicity in favor of eventual, compensatable consistency. Most real payment systems co-locate accounts that transact frequently (or use a ledger service that owns all balance mutations) specifically to avoid needing cross-shard transactions at all.

14Rebalancing / resharding

Before:
Shard 1 → 500 GB
Shard 2 → 500 GB
Shard 3 → 5 TB    ◄── needs to split

After:
Shard 1 → 500 GB
Shard 2 → 500 GB
Shard 3a → 2.5 TB
Shard 3b → 2.5 TB

Rebalancing is moving data between shards to restore even load — triggered by uneven growth, a hot shard, or simply adding capacity. Approaches: adding shards and remapping a slice of the keyspace to them, splitting one oversized shard into two, and letting consistent hashing / virtual shards minimize how much data actually has to move on either operation.

Resharding without significant downtime

  1. Dual writes — start writing every new/updated row to both the old and new shard layout simultaneously.
  2. Backfill — copy historical data from the old shard into its new home in the background, at a throttled rate that doesn't compete with live traffic.
  3. Verify — checksum or spot-compare old vs. new to confirm the backfill is complete and correct.
  4. Cutover — flip reads to the new layout, typically shard by shard or via a feature-flagged percentage rollout.
  5. Stop dual writes / decommission — once fully cut over and verified, retire the old mapping.

This "dual-write → backfill → verify → cutover" sequence is the standard pattern behind essentially every large-scale online resharding (Stripe, Shopify, and others have written about variants of it) — know the shape of it, because "how do you reshard without downtime" is a near-guaranteed follow-up question.

15Consistent hashing and virtual shards, in depth

Physical Shard A          Physical Shard B
 ├── V1                    ├── V4
 ├── V2                    ├── V5
 └── V3                    └── V6

Ring position → virtual shard → physical shard (indirection layer)

Each physical shard is represented by many small "virtual shards" scattered around the hash ring instead of one large contiguous slice. Rebalancing then means reassigning a handful of virtual shards from an overloaded physical shard to a new one — a small, targeted data movement — instead of splitting one giant contiguous range and moving half of it. Virtual shards also smooth out load: with only a few physical nodes on a ring, one node can randomly land a disproportionate arc; many small virtual slices per node average that out.

16Shard metadata

Something has to answer: "user_id = 12345 lives on Shard 7." Options, roughly cheapest to most flexible:

  • Static configuration — a config file or constant baked into app code (e.g. the modulo formula). Zero infra, but changing shard count means redeploying every service.
  • Metadata database — a small, heavily-cached database holding the shard map, consulted by the router.
  • Service discovery / configuration service (etcd, ZooKeeper, Consul) — strongly consistent, watchable, built for exactly this kind of small critical mapping.
  • Consistent hashing — no metadata store needed at all for the common case; the hash function is the map, with node membership as the only external state.
  • Dedicated routing service — an internal service purpose-built to answer "which shard," fronted by its own cache and replicas.
Failure mode

If the shard metadata service goes down, every query that needs to resolve a shard is stuck — this makes the metadata layer a potential single point of failure for the entire sharded system, regardless of how many shards you have. It must be replicated, cached aggressively at the router/application layer, and designed to fail toward "serve stale-but-correct mapping" rather than "reject all traffic."

17Failure scenarios

For each scenario: What happens → Impact → Recovery → Prevention.

1. One shard goes down

What happens: queries routed to that shard fail. Impact: partial outage — only the rows on that shard are affected, not the whole system (this is sharding's key availability advantage over a single monolith). Recovery: fail over to that shard's replica. Prevention: every shard needs its own replica(s) and automated failover.

2. One shard becomes extremely slow

What happens: latency on that slice of data spikes, and scatter-gather queries touching that shard now run at its speed. Impact: can silently degrade the whole system if fan-out queries are common, even though only one shard misbehaves. Recovery: per-shard timeouts and circuit breakers so a slow shard is skipped/degraded rather than blocking everything. Prevention: per-shard health monitoring and load shedding.

3. A shard becomes full

What happens: writes to that shard start failing. Impact: localized write outage for that key range. Recovery: emergency split/rebalance, or temporary read-only mode for that shard. Prevention: capacity alerts well before the limit, and a rebalancing runbook that doesn't need to be invented under pressure.

4. Shard router goes down

What happens: nothing can be routed anywhere. Impact: total outage, regardless of how healthy the shards themselves are. Recovery: failover to a standby router instance. Prevention: the router must be built with the same HA rigor as the shards — it is a single point of failure by construction unless replicated.

5. Network partition

What happens: some shards or replicas become unreachable from others. Impact: depends on the consistency model — a system might serve stale reads or reject writes rather than risk a split-brain. Recovery: partition-tolerant design (quorum reads/writes) resolves automatically once connectivity returns. Prevention: choose a CP or AP stance deliberately per CAP trade-offs, and test partition behavior, not just node-down behavior.

6. A shard loses its primary

What happens: writes to that shard stop. Impact: localized write outage. Recovery: automated replica promotion. Prevention: health-checked automatic failover rather than manual intervention.

7. A shard loses all replicas

What happens: the primary is now a single point of failure for that shard's data. Impact: no failover target if the primary also fails — risk of data loss. Recovery: urgently provision new replicas from the primary. Prevention: alert on replica count dropping below a minimum, not just on zero replicas.

8. A bad shard key causes extreme hotspotting

What happens: one shard absorbs a large fraction of total traffic. Impact: that shard degrades or falls over while others sit idle — effectively an unplanned capacity outage. Recovery: emergency mitigations from §7 (caching, salting, splitting). Prevention: shard-key selection review (§6) before sharding, and load monitoring per-shard, not just in aggregate.

9. Resharding fails halfway through

What happens: some data has moved to the new layout, some hasn't. Impact: reads/writes may be inconsistent or missing depending on which layout they're routed against. Recovery: this is exactly why dual-writes + verification (§14) exist — the old layout stays authoritative and fully functional until the new one is verified complete, so a failed migration can pause or roll back without data loss. Prevention: never cut over reads until backfill is verified; keep the migration idempotent and resumable.

18Sharding and consistency

Clarify this explicitly

Sharding itself does not determine consistency. Sharding is purely about where data lives; consistency is about what guarantees reads and writes make relative to each other. You can build a strongly consistent sharded system (each shard uses synchronous replication and cross-shard transactions use 2PC) or an eventually consistent one (async replication, no cross-shard atomicity) — the choice is orthogonal to whether you shard at all.

What sharding does make harder: strong consistency within a shard is as easy as in a single database, but across shards it requires distributed transaction protocols (§13). Ordering guarantees (e.g. global sequence numbers) become expensive across shards, since each shard's local order says nothing about another's. Read-after-write consistency is fine for single-shard operations but requires routing a user's subsequent reads to the same shard/replica they wrote to if you want to guarantee they see their own write immediately.

19Sharding and caching

Client
  │
  ▼
CDN            ◄── static/public content, edge-cached
  │
  ▼
Redis          ◄── hot keys, shard-aware if partitioned itself
  │
  ▼
Shard Router
  │
  ▼
Database Shards

Each layer should cache what it's closest to: the CDN caches content with no per-user variance; an application-tier cache (Redis/Memcached) caches hot rows and query results, ideally partitioned the same way as the underlying shards so a cache miss and its resulting DB query land on the same node without an extra routing hop. Hot keys in the cache mirror hot shards in the DB — the same mitigations (salting, splitting a hot cache key across multiple cache nodes) apply. Invalidation gets harder with sharding because a write to one shard needs to invalidate the corresponding cache entry specifically, not flush broadly — shard-aware cache-key design (embedding the shard ID or the natural key) keeps invalidation targeted.

20Sharding and indexing

Data sharded by user_id but frequently searched by email is the canonical version of this problem: a lookup by email has no idea which shard to query.

  • Local index — an index that exists independently on each shard, useful only for queries that are already scoped to that shard.
  • Global secondary index — a separate, often independently-sharded index keyed by the secondary attribute (e.g. shard the index by hash(email)), mapping email → user_id/shard. Adds write amplification (every user write also updates the index) in exchange for O(1) lookups by the secondary key.
  • Directory lookup — a dedicated email → shard table, essentially a purpose-built global index, often the pragmatic answer for a small number of alternate lookup keys.
  • Search engine (Elasticsearch) — for open-ended, multi-field, or fuzzy search, replicate the searchable fields into a system built for exactly that, rather than trying to make the sharded OLTP store do it.

21System-design examples, worked

Framework for each: Requirements → Scale → Data Model → Access Patterns → Shard Key → Strategy → Routing → Replication → Hotspots → Rebalancing → Failure Handling → Trade-offs.

A. Instagram

Shard key: user_id for users and their own posts/comments (co-located for locality); a separate post_id-sharded store for global post lookup. Hotspots: celebrity accounts generate massive read fan-out on their own shard — mitigated with aggressive caching of celebrity profiles/feeds and, for writes, fan-out-on-read instead of fan-out-on-write for very large follower counts. Feed generation: typically a hybrid — fan-out-on-write (push new posts to followers' feed caches) for normal users, fan-out-on-read (pull at request time) for celebrities, precisely to avoid a single hot write path. Cross-shard queries: a user's home feed inherently spans many other users' shards — solved via a separate feed/timeline service that denormalizes recent posts rather than joining across user shards live.

B. E-commerce

Shard key: user_id for users/orders (co-located, so "my orders" never crosses shards); product_id or category-hash for the product catalog. Hotspots: flash-sale products create extreme read/write concentration on one shard — mitigated with caching, key salting for inventory counters, and pre-warming capacity ahead of known sale events. Inventory consistency: inventory decrement needs to be atomic per product, which is naturally single-shard if product is the key — the hard case is a cart spanning products on different shards, handled via sagas rather than a single distributed transaction. Cross-shard transactions: checkout (payment + inventory + order creation) is the textbook saga: reserve inventory, charge payment, create order, with compensating "release inventory" / "refund" steps on failure.

C. Uber

Shard key: geographic cell (e.g. geohash/S2 cell) for drivers and trip matching — riders and drivers need to be queried by "who's near me," which is inherently a geographic access pattern, not a user-ID one. Hotspots: dense, high-demand cities create hot cells — mitigated with finer-grained cell subdivision in dense areas and coarser cells in sparse ones (variable-resolution geo-sharding). Real-time workload: constant driver location pings are extremely write-heavy; often handled by a specialized in-memory/geo-indexed store rather than a general-purpose sharded RDBMS, decoupled from the durable trip/billing data which can shard by trip_id or user_id instead.

D. Twitter/X-like system (500M users, 100M posts/day)

Shard key: Snowflake-style IDs for tweets (time-ordered, distributed) sharded by hash; user data sharded by user_id. Celebrity/hot-key problem: identical to Instagram's — hybrid fan-out strategy. Timeline: a dedicated, precomputed timeline store (not a live join of "tweets from everyone I follow") because that join would be a massive scatter-gather on every single page load. Replication: heavy read-replica usage given read:write ratios often exceeding 100:1 on social platforms.

E. URL Shortener (100M writes/day, 10B reads/day)

Shard key: hash of the short code (or a Snowflake-style ID encoded into the short code itself) — read-dominated by ~100:1, so the design center is read scaling. Strategy: hash-based sharding for even write spread, extremely aggressive caching (a large fraction of reads should never reach a shard at all — cache hit rates in the high 90s are the target), read replicas per shard. Hot URLs: viral links are the celebrity-user problem again — cache-first design absorbs this almost entirely. Failover: given the read skew, losing a shard's primary is tolerable briefly if replicas can serve reads; write unavailability for that shard's key range is the acceptable degraded mode.

F. Banking system

Shard key: account ID, chosen so that an account's full transaction history and balance mutations are always local to one shard. Cross-shard transfers: unavoidable when two accounts land on different shards — this is the canonical saga-vs-2PC decision point; many real banking systems use a synchronous two-phase-commit-like protocol or route through a central ledger service specifically because financial correctness outweighs the latency/availability cost. Strong consistency is usually non-negotiable here, unlike the other examples. Regulatory requirements often mandate geographic data residency, adding a geographic-sharding dimension on top of the account-based one. Failure handling: must favor rejecting a transfer over risking a partial, non-atomic debit/credit.

Know which category a system in your design falls into.

23Sharding vs. partitioning vs. replication vs. caching

ConceptWhat it doesMain purposeExample
ReplicationCopies dataAvailability / read scalingPrimary + replicas
ShardingSplits data across machinesWrite / storage scalingUsers split across shards
PartitioningSplits data logically/physically (may stay on one machine)Manageability / performanceDate-range table partitions
CachingStores frequently accessed data closer to the clientLatency / read-load reductionRedis

A mature production architecture typically uses all four at once: partitioning keeps individual tables manageable, sharding spreads those partitions across machines for write/storage scale, replication gives each shard availability and read throughput, and caching sits in front of everything to absorb the hottest reads before they reach a shard at all.

24Capacity math

Number of shards from data size

Total data       = 20 TB
Target shard size = 500 GB
                                     20 TB
Shards needed  ≈  ───────────  =  40 shards
                     500 GB

Round up and add headroom (e.g. target 60–70% utilization per shard so growth and rebalancing have room to work) — don't plan to exactly fill shards on day one.

Then check throughput, not just storage

Peak traffic = 1,000,000 requests/sec
Each shard can sustain, say, 20,000 req/sec

                                  1,000,000
Shards needed for throughput ≈  ───────────  = 50 shards
                                    20,000

Here throughput (50 shards) demands more shards than storage alone did (40) — take the larger of the two numbers. Shard count should never be sized on storage alone: a workload with modest data volume but extreme request rate (e.g. a URL shortener, or a leaderboard) can need far more shards than its data size implies, and vice versa for a write-light, storage-heavy archive.

The same two-sided check applies to estimating data per shard (total data ÷ shard count, watched over time as data grows unevenly), queries per shard (total QPS ÷ shard count, but skewed by hot keys — always plan for the hottest shard, not the average), replication traffic (write volume × replica count, since every write is copied to every replica of its shard), and rebalancing cost (data that must move ÷ available migration bandwidth, which is why virtual shards/consistent hashing matter — they shrink the numerator).

25Fifteen shard-key examples

1Social media (posts)
Candidates: post_id, user_id, created_at · Recommended: user_id (co-locate a user's posts) with a separate hash-sharded post_id index for direct lookups · Why: most reads are "this user's posts" · Problem: celebrity accounts hot-spot · Alternative: hybrid fan-out (§21A)
2E-commerce (orders)
Candidates: order_id, user_id, product_id · Recommended: user_id · Why: "my orders" is the dominant query, and co-locates with the user shard · Problem: seller/warehouse-side analytics need cross-shard scans · Alternative: CDC pipeline into a warehouse for analytics
3Banking (accounts/transactions)
Candidates: account_id, customer_id, branch_id · Recommended: account_id · Why: transactions are almost always scoped to one account · Problem: transfers between accounts on different shards · Alternative: sagas or a coordinating ledger service (§13, §21F)
4Ride-sharing (trips/locations)
Candidates: driver_id, rider_id, geo-cell · Recommended: geo-cell (geohash/S2) · Why: the core query is "who's near me," inherently spatial · Problem: dense-city hot cells · Alternative: variable-resolution cells, finer in dense areas
5Messaging (chats/messages)
Candidates: conversation_id, sender_id, message_id · Recommended: conversation_id · Why: all messages in a thread are read/written together · Problem: huge group chats/broadcast channels become hot · Alternative: split very large conversations across sub-partitions
6IoT (device telemetry)
Candidates: device_id, timestamp, region · Recommended: device_id (hashed) · Why: queries are almost always "this device's history" · Problem: naive time-based sharding hot-spots on the newest range · Alternative: hash(device_id) combined with time-based sub-partitioning for retention/expiry
7Analytics / event logging
Candidates: event_time, tenant_id, event_type · Recommended: tenant_id + time-bucketed sub-partitions · Why: queries scope to one tenant and a time window · Problem: large tenants hot-spot · Alternative: hash sub-sharding within a large tenant
8SaaS / multi-tenant applications
Candidates: tenant_id, user_id · Recommended: tenant_id · Why: tenants never query across each other's data — perfect natural isolation and locality · Problem: a handful of very large enterprise tenants dwarf the rest ("noisy neighbor") · Alternative: dedicated shards for oversized tenants, shared shards for small ones
9Logging platforms
Candidates: service_name, timestamp, trace_id · Recommended: hash(service_name or trace_id) with time-based retention partitioning · Why: spreads write load evenly while keeping expiry cheap · Problem: a single noisy service can dominate volume · Alternative: per-service quota + salting
10Gaming (player state/matches)
Candidates: player_id, match_id, region · Recommended: player_id for profile/inventory; match_id for live match state · Why: different access patterns need different keys — this is normal · Problem: global leaderboards need cross-shard aggregation · Alternative: a separate, purpose-built leaderboard service (e.g. sorted-set store)
11Video platform (videos/views)
Candidates: video_id, channel_id, uploader_id · Recommended: video_id (hashed) for metadata/views; channel_id for a creator's video list · Why: matches the two dominant query shapes · Problem: viral videos hot-spot views/comments · Alternative: caching + counter salting for view counts
12URL shortener
Candidates: short_code, creation timestamp · Recommended: hash of short_code · Why: pure lookup workload, wants even spread, no useful range-query pattern · Problem: viral links hot-spot · Alternative: aggressive caching (§21E)
13Search platform (index shards)
Candidates: document_id, term, tenant_id · Recommended: document_id (hashed) for the primary index, replicated inverted indexes per shard · Why: search engines shard the corpus and scatter-gather queries by design · Problem: every query touches every shard (scatter-gather is the norm here, not an edge case) · Alternative: tiered indexes — small/hot indexes searched first
14Payment processing
Candidates: merchant_id, payment_id, customer_id · Recommended: merchant_id for merchant-scoped queries, payment_id (hashed) for the payment ledger itself · Why: most dashboards/reports are merchant-scoped; the ledger wants even write spread · Problem: refunds/disputes reference a payment that may live separately from the merchant view · Alternative: a canonical payment_id-sharded ledger with a merchant_id-sharded read-optimized view
15Multi-region content platform
Candidates: user_id, region, content_id · Recommended: region (geographic sharding) as the top-level split, user_id within region · Why: latency and data-residency requirements dominate · Problem: users who relocate/travel across regions · Alternative: a thin global "home region" directory plus explicit async re-homing migration (§5E)

26Common interview mistakes — and the better answer

Weak"Just shard by user_id."
BetterName the actual query patterns first — user_id is often right, but only because most queries are user-scoped. State that reasoning, and flag which queries it breaks (cross-user analytics).
Weak"Hashing is always better."
BetterHashing solves hotspotting but destroys range queries. If the workload needs range scans (time-series, leaderboards by score), range or a hybrid key may beat pure hashing.
Weak"More shards means better performance."
BetterMore shards means more cross-shard coordination overhead, more metadata to manage, and — if the key is bad — the same hotspot, just on a smaller fraction of a now-larger fleet. Right-size to the bottleneck (§24), don't over-shard by default.
Weak"Sharding solves everything."
BetterSharding solves write/storage scaling and introduces new problems (cross-shard queries, joins, transactions, rebalancing). It's a trade, not a cure.
Weak"Replication and sharding are the same."
BetterReplication copies the same data for availability/read-scale; sharding splits different data for write/storage-scale. Production systems use both, for different reasons.
Weak"Use UUIDs and hotspots disappear."
BetterUUIDs fix write-distribution hotspots from sequential IDs, but do nothing for access-pattern hotspots like a celebrity user or a viral product — those need caching, salting, or splitting.
Weak"Cross-shard joins are easy."
BetterThere is no native cross-shard join operator. It requires co-location, denormalization, application-side stitching, or a separate analytical system — each with real trade-offs.
Weak"Cross-shard transactions are just normal transactions."
BetterThey require 2PC, a saga, or a system with built-in distributed transactions (Spanner) — each trades off latency, availability, or immediacy of consistency differently.
Weak"We can add shards whenever we want."
BetterAdding shards triggers rebalancing, which moves real data and, with naive mod-hashing, can reshuffle nearly everything. Plan the strategy (consistent hashing, virtual shards) for this before you need it.
Weak"Consistent hashing means no data movement."
BetterIt means minimized data movement — only the keys near the changed node move, not zero keys.
Weak"Sharding automatically gives high availability."
BetterSharding alone means a shard's failure takes only its slice of data down, but each shard still needs its own replication and failover to actually be available — sharding without replication is many single points of failure, not one.
Weak"If one shard fails, the entire database fails."
BetterPrecisely the opposite is the point of sharding — a failed shard degrades only the fraction of data/traffic it owns, not the whole system, provided the router/metadata layer itself is resilient (§17.4).

Answers & reasoning

Q1What is database sharding?
Splitting one logical dataset into multiple independent physical databases, each owning a disjoint subset of rows, so no single machine stores or serves everything. See §1.
Q2Why not just use a bigger server?
Vertical scaling has a hard ceiling — the largest instance type available — and doesn't help once storage, CPU, IOPS, connections, or write throughput individually exceed what any single box can do. See §2, §3.
Q3Sharding vs. partitioning?
Partitioning is the general technique of splitting data; sharding specifically means those pieces live on separate physical machines. Single-instance partitioning is not sharding. See §1.
Q4Sharding vs. replication?
Replication copies the same data for availability/read scale; sharding splits different data for write/storage scale. Complementary, not interchangeable. See §1, §10.
Q5Range vs. hash sharding?
Range: great for range queries, prone to hot shards on correlated/sequential keys. Hash: even distribution, but range queries need scatter-gather and resizing (mod-N) reshuffles almost everything. See §5A–B.
Q6Consistent hashing — why does it matter?
It minimizes data movement when nodes are added/removed by only remapping the keys near the changed node, versus naive mod-hashing which reshuffles nearly the entire keyspace. See §5C, §15.
Q7What makes a good shard key?
High cardinality, even distribution, query locality, even write distribution, and stability. See §6.
Q8Why is created_at a bad shard key alone?
Every new write shares the newest timestamp, so all writes hit the same range/shard — a textbook write hotspot. See §6, §8.
Q9What is a hot shard?
A shard receiving disproportionate load relative to its peers, from celebrity users, viral content, sequential-ID writes, or geographic concentration. See §7.
Q10Fix a hot shard live?
Layer mitigations without a full reshard first: caching, key salting, splitting the hot partition into virtual shards that can be relocated — reserve a full re-key for when the shard-key choice itself is the root cause. See §7.
Q11What is resharding, and when is it needed?
Moving/redistributing data across shards, needed when a shard outgrows its capacity, becomes hot, or shard count changes. See §14.
Q12Reshard without downtime?
Dual writes to old and new layout → background backfill → verification → gradual cutover → retire the old layout. See §14.
Q13Cross-shard queries?
Scatter-gather (fan out, merge), global secondary indexes for O(1) lookups on a non-shard-key attribute, or a dedicated search system for open-ended queries. See §11.
Q14Cross-shard joins?
No native join operator across shards; solved by co-locating related data under the same shard key, denormalizing, application-side stitching, or offloading to a separate analytical warehouse. See §12.
Q15Distributed transactions across shards?
Two-phase commit for strong atomicity at a latency/availability cost, sagas for eventual consistency with compensating actions, or a system with built-in distributed transactions (Spanner). See §13.
Q162PC vs. saga?
2PC blocks all participants until every node agrees to commit — strong but fragile under slow/failed nodes. Sagas break the transaction into local steps with compensations, trading immediate atomicity for availability and scale. See §13.
Q17Global secondary index?
A separate, often independently-sharded index on a non-primary-shard-key attribute (e.g. email when sharded by user_id), needed whenever a frequent query pattern doesn't match the shard key. See §20.
Q18Multi-region sharding?
Geographic sharding for latency and data-residency, with a thin global directory for "home region" and an explicit async re-homing path for users who relocate. See §5E.
Q19Why combine sharding with replication?
They scale different axes — sharding for writes/storage, replication for reads/availability — and a shard with no replicas is a single point of failure for its slice of data. See §10.
Q20One shard goes down — walk through it.
Queries to that shard's key range fail until failover to its replica completes; other shards are unaffected — this partial-blast-radius behavior is sharding's key availability advantage. See §17.1.
Q21Shard router goes down?
Total outage regardless of shard health, since nothing can be routed — the router needs the same HA rigor (replication, failover) as the shards themselves. See §17.4.
Q22Design for 500M users, heavy reads.
Shard by user_id for locality; lean heavily on read replicas and caching given the read-heavy skew; consider whether sharding is even needed yet vs. replicas + caching alone (§3) before committing to it. See §21D, §3.
Q23Instagram, celebrity-user problem.
Hybrid fan-out: push to follower feed caches for normal accounts, pull-at-read-time for massive-follower accounts, to avoid a single hot write path fanning out to millions of feeds. See §21A.
Q24Uber's real-time location data.
Geo-cell sharding (geohash/S2), variable resolution for dense vs. sparse regions, decoupled from durable trip/billing data which shards independently by trip_id/user_id. See §21C.
Q25Twitter timeline under sharding.
A dedicated precomputed timeline/feed store rather than a live cross-shard join over "everyone I follow," because that join would be a full scatter-gather on every page load. See §21D.
Q26E-commerce checkout consistency.
Checkout (inventory reservation + payment + order creation) is a saga with compensating actions (release inventory, refund) rather than a single atomic cross-shard transaction. See §21B.
Q27Banking transfer atomicity.
Shard by account_id for locality; for cross-shard transfers, favor a stronger protocol (2PC or a coordinating ledger service) over sagas, because financial correctness usually outweighs latency/availability trade-offs here. See §21F, §13.
Q28How many shards do you need?
Take the larger of (total data ÷ target shard size) and (peak throughput ÷ per-shard sustainable throughput), with headroom for growth and rebalancing. See §24.
Q29Why not size shard count on storage alone?
Throughput and storage can diverge sharply — a small, extremely hot dataset (URL shortener, leaderboard) can need many more shards than its data volume implies, and vice versa. See §24.
Q30Biggest operational risks unique to sharding?
Cross-shard queries/joins/transactions with no native support, rebalancing that can move enormous amounts of data, a metadata/routing layer that becomes a new single point of failure, and a shard-key decision that's expensive to reverse once data is written. See §11–17.

28Final cheat sheet

Sharding strategy — how it works → best use case → main problem

Range-based

Contiguous key ranges per shard. Best for range-scan-heavy workloads. Problem: hot shards on sequential/time-correlated keys.

Hash-based

hash(key) % N. Best for even load distribution. Problem: range queries need scatter-gather; resizing reshuffles most keys.

Consistent hashing

Ring + virtual nodes. Best for systems that grow/shrink often. Problem: added complexity vs. plain hashing.

Directory-based

Explicit key→shard map. Best for maximum rebalancing flexibility. Problem: lookup service becomes critical infra.

Geographic

Region-based split. Best for latency + data residency. Problem: users who relocate across regions.

Key concepts, one line each

Shard key
The attribute used to decide which shard a row belongs to.
Partition
A subset of data split off from the whole, logically or physically.
Hot shard
A shard receiving disproportionate load relative to its peers.
Scatter-gather
Fan a query out to every shard in parallel, then merge results.
Shard router
The layer that decides which shard a given query should hit.
Virtual node
A small slice of the hash ring mapped to a physical shard, many-to-one.
Consistent hashing
Ring-based key placement that minimizes data movement on membership changes.
Resharding
Changing the shard layout or count, and moving data accordingly.
Rebalancing
Redistributing data across existing/new shards to restore even load.
Cross-shard query
A query whose answer requires data from more than one shard.
Cross-shard transaction
A transaction that must atomically touch rows on more than one shard.
Global secondary index
An index on a non-shard-key attribute, maintained independently to avoid scatter-gather lookups.
