Database Replication

Copies of the same data, kept in sync across machines, for reasons that have almost nothing to do with "reads scale better." This is the reasoning chain a strong candidate runs every time replication comes up.

01 What replication is, and why it exists

Database replication is the practice of keeping copies of the same data on more than one machine, and continuously propagating changes from one copy to the others. One copy is usually designated the place writes land — call it the primary (also: leader, master, source). The other copies receive a stream of changes and apply them — call these replicas (also: followers, slaves, standbys).

The terminology maps directly: primary = leader = master = source, and replica = follower = slave = standby. Modern systems (Postgres, GitHub, Redis) have largely moved to primary/replica or leader/follower language; older docs and some codebases still say master/slave.

fig 1 — basic primary/replica topology
            ┌──────────────┐
            │   Primary      │  ← all writes land here
            │   Database   │
            └──────┬───────┘
                   │  change stream (WAL / binlog)
         ┌─────────┴─────────┐
         ↓                   ↓
  ┌─────────────┐     ┌─────────────┐
  │  Replica 1   │     │  Replica 2   │  ← reads served here
  └─────────────┘     └─────────────┘

Writes go to the primary. The primary logs every change and ships that log to each replica. Each replica replays the log against its own copy of the data. Reads can be served from the primary or any replica, which is the lever most people reach for first — but it is not the only reason replication exists.

the interview answer

Replication is a tool that can improve read scalability, availability, and durability / disaster recovery simultaneously — but tuning it for one of those goals usually costs you on another. Never say "replication just makes things faster." Say which axis you're optimizing for and what you're trading away.

02 The four problems replication solves

A. Read scalability

A single primary handling 1,000 writes/sec and 10,000 reads/sec can offload most of that read load onto replicas, since reads vastly outnumber writes in most systems. The primary keeps taking every write; N replicas each absorb a slice of the read traffic. This is the classic "read replica" pattern and is the reason most engineers first hear about replication.

What it does not do: help you scale writes. Every replica still has to apply the exact same write volume the primary sees, in the same order. Adding replicas to fix write throughput is a category error — that's what sharding is for (see §15).

B. High availability

If the primary dies, a healthy replica can be promoted to take its place. Without replication, a primary failure means downtime until that one machine is repaired. With replication, failover can happen in seconds to minutes depending on how automated the process is.

C. Disaster recovery

Replicas placed in a different rack, a different availability zone, or a different region protect against correlated failures: a power outage, a bad kernel upgrade rolled to a whole rack, or an entire AZ going dark. The blast radius a single replica protects you from is exactly the blast radius its placement is decorrelated from the primary's.

D. Geographic distribution

fig 2 — regional read replicas
  US users    ───▶  US Replica   ─┐
  Europe users ───▶  EU Replica   ─┼──▶  Primary (writes)
  Asia users   ───▶  Asia Replica ─┘

Placing a replica close to a user population cuts read latency dramatically — a read that would cross an ocean now stays local. The trade-off: those regional replicas are, by definition, some number of milliseconds-to-seconds behind the primary, so this only works for data that tolerates being slightly stale.

GoalWhat replication changesWhat it costs you
Read scalingRead throughput scales with replica countReplication lag; more infra to run
AvailabilitySurvive a primary failure via promotionFailover complexity, possible data loss
Disaster recoverySurvive correlated hardware/AZ/region failureCross-AZ/region network cost & latency

03 Replication models

A. Primary-replica (leader-follower)

Writes
   ↓
Primary
   ↓ (async or sync)
Replica, Replica, Replica …
  • Read scaling: linear-ish with replica count, bounded by write volume every replica must also absorb.
  • Failover: promote one replica; requires deciding which one is most up to date.
  • Replication lag: replicas trail the primary by a variable amount.
  • Read-after-write: a client can read stale data from a replica right after writing to the primary — the single biggest gotcha with this model.

Examples: PostgreSQL streaming replication, MySQL replication, a single MongoDB replica set, Amazon RDS read replicas. This is the default choice for the vast majority of systems and the one you should reach for first in an interview unless requirements push you elsewhere.

B. Multi-primary (multi-leader)

Region A Primary  ←──────→  Region B Primary

More than one node accepts writes, and each propagates its writes to the others. This exists because a single-writer topology forces every write in every region to cross the network to one primary — for a globally-distributed write-heavy app that latency is unacceptable. So each region gets its own writable primary.

The cost: two clients can concurrently write different values to the same row in different regions. That's a write conflict, and someone — the database or the application — has to resolve it (§18). You also have to guard against replication loops (A sends a change to B, B echoes it back to A) with origin tags or vector clocks.

Use it when: writes must be geographically local and the data model tolerates eventual conflict resolution (collaborative documents, shopping carts, multi-region SaaS config). Avoid it when: correctness requires a single source of truth for a value at every instant (bank balances).

C. Peer-to-peer / leaderless

Node A ←→ Node B
  ↕         ↕
Node C ←→ Node D

No node is special. A client write goes to several nodes at once; a client read queries several nodes and reconciles. This is the Dynamo-style model (Cassandra, Riak, DynamoDB's internals) built around quorum reads and writes (§13) and typically eventual consistency. Conflicting versions are resolved with last-write-wins, version vectors, or CRDTs.

Use it when: you need very high write availability, can tolerate eventual consistency, and want to scale horizontally without a single-writer bottleneck at all — e.g. sensor/event ingestion, shopping carts, session stores.

04 Synchronous vs asynchronous replication

synchronous

Client → Primary → wait for replica ack → ack client. The write is not considered durable until at least one replica has it too.

asynchronous

Client → Primary → ack client immediately. The replica gets the change afterward, on its own schedule.

fig 3 — synchronous replication path
Client → Primary → Replica → ack → Primary → ack → Client
fig 4 — asynchronous replication path
Client → Primary → ack → Client
                Primary ─────────▶ Replica   (happens later, off the critical path)

Semi-synchronous sits in the middle: the primary waits for acknowledgment from at least one replica (not all of them) before acking the client. It buys a durability guarantee — the data exists on 2 machines before the client is told "done" — without the full latency cost of waiting on every replica, and without the availability cliff of requiring every replica to be up.

StrategyWrite latencyConsistencyDurabilityAvailability
SynchronousHigherStrongerHighLower
AsynchronousLowerEventualLowerHigher
Semi-synchronousMediumMedium/strongerHigherMedium
gotcha

"Asynchronous" does not mean "no data loss ever" — it means the primary can crash after acking a client but before shipping that write to any replica. That write is gone. Synchronous replication is the direct trade you make to close that window, at the cost of latency and availability when replicas are slow or down.

When to use which: synchronous (or semi-sync) for financial ledgers, order placement, anything where losing an acknowledged write is unacceptable. Asynchronous for social feeds, analytics, activity logs, anything where "we might lose the last second of writes on a rare crash" is a tolerable risk in exchange for lower latency at scale.

05 How replication actually works

Every mainstream relational database replicates by shipping a log, not by re-running application-level SQL on each replica. Postgres calls it the write-ahead log (WAL); MySQL calls it the binary log (binlog). The idea is identical: before a change is applied to the actual data files, it's appended to a sequential log with a monotonically increasing position — a log sequence number (LSN) in Postgres, a GTID/binlog coordinate in MySQL.

fig 5 — from statement to replayed row
Application
    ↓
Primary DB  — executes the write, appends to WAL/binlog
    ↓
Replication Stream  — primary ships new log entries to each replica
    ↓
Replica  — receives entries, appends to its own local log
    ↓
Replay  — replica applies the logged change to its copy of the data

Walking through UPDATE users SET name='John' WHERE id=10;:

  1. Primary executes the update against its in-memory/on-disk row for id=10.
  2. Before (or as part of) committing, the primary writes a record of that change to the WAL/binlog — physical (byte-level page changes, Postgres physical replication) or logical (a decoded "row 10's name became John", used for cross-version or selective replication).
  3. The primary's commit is only durable once it's in the log on disk — this is what "write-ahead" means.
  4. A replication stream (a persistent connection) ships new log bytes to each replica as they're generated.
  5. Each replica appends the bytes to its own copy of the log and a replay/apply process executes the equivalent change against its local data.
  6. The replica now reflects the update — some amount of time after the primary did. That gap is replication lag.

Checkpoints periodically flush all changes up to a given LSN to durable data files, so recovery after a crash only has to replay the log from the last checkpoint forward, not from the beginning of time.

06 Replication lag

Replication lag is the delay between a change committing on the primary and that same change being visible on a replica.

Primary:  transaction #1000  (latest)
Replica:  transaction #950   (lag = 50 transactions behind)

Causes

  • High write throughput on the primary — more log to ship and replay than the replica can keep up with.
  • Slow or under-provisioned replica hardware — disk, CPU, or memory bottlenecks during replay.
  • Network latency between primary and replica, especially cross-region.
  • Large transactions (bulk updates, big migrations) that must be replayed as a unit.
  • Long-running queries on the replica that block replay (lock contention with read queries).
  • Single-threaded replay in some engines — replay can't parallelize as well as the primary's writes did.
  • Replication queue buildup when any of the above persists — the gap compounds instead of catching up.

What lag causes

  • Stale reads on replicas — read-after-write problems (§7).
  • Ambiguity during failover — the most "caught up" replica isn't fully caught up either.
  • Cascading pressure — as one replica falls further behind, retries and re-reads can add even more load.
interview signal

Naming specific causes of lag (large transactions, single-threaded replay, network RTT) instead of a generic "the replica gets behind sometimes" is what separates a strong answer here.

07 Read-after-write consistency

The canonical failure case: a user does POST /profile (write hits the primary), then immediately GET /profile (read gets routed to a replica that hasn't caught up yet). The user sees their old profile and assumes the save failed.

Five ways to fix it

SolutionHowTrade-off
Read from primary post-writeRoute reads for a short window (or for that user/session) back to the primaryAdds load back onto the primary; needs a routing rule
Session stickinessPin a user's session to one replica (or the primary) for consistency within that sessionUneven load distribution; breaks if the pinned node fails
Track replication position (LSN)Client/app remembers the LSN of its last write; only reads from a replica that has caught up to that LSNExtra bookkeeping; a lagging replica means the read waits or falls back
Synchronous replicationDon't ack the write until a replica has it too, so any replica read is automatically freshHigher write latency, lower write availability
Application-level guaranteesReturn the freshly-written object directly from the write path instead of re-reading itOnly works when the client only needs to see its own write, not others'

08 Read/write splitting

Applications route writes to the primary and reads to replicas, either from application code, a database proxy (ProxySQL, PgBouncer + routing logic, AWS RDS Proxy), or a smart driver/connection pool.

fig 6 — router-mediated read/write split
                 ┌──▶ Replica 1  (reads)
Application ──▶ Router ──┤
                 ├──▶ Replica 2  (reads)
                 └──▶ Primary    (writes, and reads that need freshness)

The router decides where a query goes based on: statement type (SELECT vs INSERT/UPDATE/DELETE), an explicit hint from the application ("this read must be fresh"), a transaction context (queries inside a write transaction usually all go to the primary), or a freshness/LSN check per §7.

This is invisible plumbing in an interview answer's success — but skipping it ("the app just talks to the database") is a tell that a candidate hasn't actually built one of these.

09 Failover

fig 7 — before / after a primary failure
before:                         after:

Primary                         Primary (dead)
   ↓                                
Replica 1                       Replica 1 → New Primary
Replica 2                       Replica 2 → still a replica

Failover is the sequence: detect the primary is actually down (not just slow) → pick the best replica to promote (usually the one with the most advanced LSN) → promote it to accept writes → redirect traffic (update DNS, a service-discovery record, or a proxy's routing table) → re-point the remaining replicas to replicate from the new primary.

The dangerous part is not any one step — it's doing all of them correctly under uncertainty, fast, without accidentally creating two primaries at once (§11).

10 Automatic failover

Automated systems detect failure via health checks/heartbeats, agree on "the primary is actually down" via a consensus protocol (Raft, Paxos-derived, or a dedicated coordinator like etcd/ZooKeeper/Patroni), elect a new leader, and reconfigure the cluster — all without a human in the loop.

"If primary dies, pick any replica" is wrong for concrete reasons:

  • Which replica is most up-to-date? Promoting a replica that's further behind than another silently discards more committed data than necessary.
  • What happens to unreplicated transactions? Anything acknowledged on the old primary but never shipped is gone — the new primary has no record of it, and it may resurface as a zombie write if the old primary ever comes back.
  • How do we prevent two primaries? If the old primary isn't actually dead — just partitioned — and a replica gets promoted, you now have two nodes accepting writes (§11).
  • How do we handle network partitions? A partition can make a perfectly healthy primary look dead to the failover manager, which is exactly the scenario that produces split-brain if you're not careful.

This is why real systems use a quorum-based consensus mechanism to decide "the primary is dead," not a single health checker's opinion.

11 Split-brain

Split-brain is when two nodes both believe they are the primary at the same time — usually caused by a network partition that isolates the "real" primary from the rest of the cluster, which then promotes a replica without knowing the old primary is still alive and serving writes on its side of the partition.

          network partition
Primary A   |   Primary B  (promoted replica)
    ↑      |       ↑
  Users    |     Users        ← both sides accept writes independently

This is dangerous because both primaries independently accept writes that the other never sees — duplicate order IDs, two different "final" balances for the same account, rows that silently diverge and can't be automatically reconciled later.

Defenses:

  • Consensus / leader election — a new primary is only elected with agreement from a majority of nodes, so a minority partition can never elect one on its own.
  • Fencing — actively cut off the old primary's ability to write (revoke its storage lease, block it at the network layer, use a STONITH — "shoot the other node in the head" — mechanism) once a new one is promoted.
  • Quorum — require a majority of nodes to agree before any write or promotion is considered valid, so a partitioned minority is mathematically unable to proceed.

12 Replication and consistency

the trap

"We have replicas" says nothing about consistency. Replication is a mechanism for copying data across machines; consistency is a guarantee about what a reader is allowed to see relative to writes. You can build a strongly consistent system on top of replication (synchronous, quorum-based) or a weakly consistent one (async, leaderless) — replication itself is orthogonal to the guarantee.

ModelGuaranteeTypical replication approach
LinearizabilityEvery operation appears to happen instantaneously at some point between its start and end; all clients see the same orderSynchronous, single-writer, or consensus-backed quorum
Strong consistencyReads always reflect the latest committed writeSynchronous replication, or reads always routed to the primary
Read-after-writeA client sees its own writes immediately, but may see other clients' writes lateSession stickiness, LSN tracking, primary-read-back
Causal consistencyOperations that are causally related are seen in the same order by everyone; unrelated operations can reorderVersion vectors / logical clocks tracking causality
Eventual consistencyIf writes stop, all replicas converge — eventually, with no bound on whenAsynchronous or leaderless replication

Concrete example: a MongoDB replica set with default readConcern reading from a secondary can return data seconds old — replication exists, but the guarantee offered is eventual, not linearizable. Switch to reading from the primary with majority write concern, and you've traded some throughput for a much stronger guarantee, using the exact same replicated cluster.

13 Quorum-based replication

Define N = total replicas holding a piece of data, W = number of replicas that must acknowledge a write before it's considered successful, R = number of replicas a read must query (and reconcile) before returning a result.

the core rule

R + W > N guarantees every read quorum and every write quorum overlap by at least one node — so any read is guaranteed to see the most recent write, because at least one node in the read set also received that write.

N=3, W=2, R=2

R+W=4 > 3 ✓. Tolerates 1 node down for either reads or writes. Common default (e.g. Cassandra QUORUM with RF=3).

N=5, W=3, R=3

R+W=6 > 5 ✓. Tolerates 2 nodes down. More read/write cost per operation, more fault tolerance.

Lower W (e.g. W=1) maximizes write availability at the cost of consistency and durability. Higher R and W maximize consistency at the cost of latency and availability during node failures — the same synchronous-vs-asynchronous trade-off from §4, generalized to N nodes.

what quorum does NOT give you

R+W>N guarantees a read will see the most recent acknowledged write eventually reconciled among the nodes it contacts — it does not by itself guarantee linearizability. Concurrent writes can still race (which one "wins" needs a conflict-resolution rule, §18), and clock skew or reconciliation-by-timestamp can produce surprising results. Quorum systems are typically tuned for eventual or tunable consistency, not full linearizability, unless paired with additional coordination.

Choose single-region for most internal or regionally-scoped products. Choose primary + cross-region replicas when reads are global but writes can tolerate one authoritative region (most consumer apps). Choose multi-region primary only when write locality is a hard requirement and the data model can absorb eventual conflict resolution (collaborative tools, some SaaS config, shopping carts) — or when using a system purpose-built for this, like Spanner or CockroachDB, which hide much of the conflict machinery behind synchronized clocks and consensus.

15 Replication vs sharding

replication

Copies the same data to multiple nodes.

A → A
A → A
A → A

Scales reads and adds availability. Does not increase how much data you can store or how many writes you can absorb.

sharding

Splits different data across nodes.

Users 1–1M   → Shard 1
Users 1M–2M  → Shard 2
Users 2M–3M  → Shard 3

Scales writes and storage. Does not, by itself, add redundancy — lose a shard's only copy and that slice of data is gone.

They solve different problems and are almost always used together at real scale: shard to spread write/storage load, then replicate each shard so it isn't a single point of failure.

16 Replication is not backup

Replication faithfully copies whatever happens to the primary — including mistakes. A replica applies a bad change just as diligently as a good one, usually within seconds. That means replication offers zero protection against:

  • An accidental DELETE FROM users; with no WHERE clause.
  • A bad schema migration that corrupts or drops data.
  • Application-level corruption (a bug that writes wrong values, at scale, very fast).
  • Malicious or unauthorized modification.

In every one of those cases, the replicas dutifully replicate the disaster. What actually protects you is a backup: a point-in-time snapshot (plus WAL/binlog archives for point-in-time recovery) stored separately, ideally immutable or with delayed application, so you can restore to a moment before the mistake. Replication and backup are complementary, not substitutes — a mature system design answer always includes both.

17 Replication and transactions

Replication has to preserve the ACID guarantees a transaction already made on the primary. Consider a transaction that updates Orders, Inventory, and Payments together:

  • Atomicity: all three writes commit together on the primary, or none do. The log entries for all three are shipped and replayed as a single unit — a replica should never apply the Orders change without also getting Inventory and Payments.
  • Isolation: a replica should not expose a partially-applied transaction to readers. In physical/log-based replication, the whole transaction's log segment is applied before it becomes visible; readers querying the replica see either the full pre-transaction state or the full post-transaction state, never a partial mix — this is what "replicas can't observe partial transactions" means in a correctly implemented system.
  • Durability: whether the transaction is durable on more than one machine at ack time depends entirely on §4 — synchronous replication makes it durable on ≥2 machines before acking; asynchronous makes it durable on 1 machine (the primary) at ack time, and eventually more.

18 Replication conflicts

Conflicts arise wherever more than one node can accept a write for the same piece of data without coordinating first: multi-primary systems, multi-region setups, leaderless quorum systems, and offline-first clients that sync later.

StrategyHow it decidesDanger
Last-write-wins (LWW)Highest timestamp winsSilently discards a concurrent write; clock skew can pick the "wrong" winner
Version vectorsTrack causal history per replica; detect true concurrency vs happens-beforeDoesn't resolve conflicts itself — just detects them accurately, still need a merge policy
Timestamps (server-assigned)A synchronized clock (e.g. TrueTime in Spanner) orders writes globallyRequires specialized infrastructure (atomic clocks/GPS) to bound clock uncertainty

19 Replication, by database

PostgreSQL

  • Streaming replication ships WAL continuously to standbys — physical, byte-for-byte.
  • Logical replication decodes the WAL into row-level changes, allowing selective table replication and cross-version replication.
  • Read replicas are hot standbys that can serve reads.
  • Failover is typically handled by an external tool (Patroni, repmgr) layered on top.

MySQL

  • Binary log (binlog) is the change stream; replicas are binlog consumers.
  • GTID (global transaction ID) makes it possible to identify exactly which transactions a replica has applied, simplifying failover.
  • Semi-synchronous mode is a first-class option, not an afterthought.

MongoDB

  • Replication unit is the replica set: one primary, several secondaries.
  • Automatic elections promote a secondary if the primary is unreachable.
  • Write concern (how many nodes must ack a write) and read concern (what a read is allowed to see) are tunable per-operation — this is essentially application-level quorum control.

Cassandra

  • Leaderless — every node can accept reads and writes for the data it's responsible for.
  • Replication factor (RF) is N in the quorum formula.
  • Consistency levels (ONE, QUORUM, ALL) let each query choose its own R or W, tuning consistency vs latency per-operation.

The system-design takeaway isn't the vendor commands — it's that each engine picked a point on the same primary-replica / multi-primary / leaderless spectrum, and exposes the sync/async and quorum knobs from earlier sections in its own vocabulary.

21 Worked designs

A. E-commerce requirements → consistency

Products/catalog: read-heavy, tolerates seconds of staleness — async primary-replica, many read replicas, geo-distributed. Inventory: must not oversell — needs strong consistency at the point of decrement (synchronous or a single authoritative primary with row-level locking; some designs shard inventory by SKU and keep it single-writer). Orders/Payments: cannot lose an acknowledged write — synchronous or semi-synchronous replication, strict durability. Users/profiles: read-heavy, tolerant of async lag with read-after-write handling on the profile-edit page specifically.

B. Instagram-style feed

Profiles, posts, comments: heavily read-dominated — async primary-replica with many read replicas absorbs the vast majority of traffic. Likes: extremely high write volume on hot posts; often not written straight to the primary relational store at all but batched/aggregated (a counter service) to avoid hammering a single row. Hot users/posts (celebrity problem): a single row (a celebrity's post) can get so many reads that even replicas struggle — solved with caching (Redis) in front of replicas, not more replicas alone. Feed generation: typically a separate fan-out/precomputation system, not a live join across replicated tables.

C. Banking system

Fundamentally different from social media: correctness beats latency. Balances/transactions/transfers need strong consistency — synchronous or quorum-based replication so an acknowledged transfer is never silently lost. Failover must guarantee the promoted node has every acknowledged transaction (no "most caught-up guess"), often via consensus-backed replication (e.g. Raft-based systems, or a synchronous standby that's the mandatory failover target). Auditability requires a durable, tamper-evident log — often backed by write-ahead logs plus separate immutable audit trails, and a real backup strategy independent of replication (§16), since a bad migration touching balances is catastrophic.

D. URL shortener 100K writes/sec, 10M reads/sec

Read:write ratio of 100:1 says this is a read-scaling problem first. Shard the write path by short-code hash to spread 100K writes/sec across many primaries (single-primary can't take that write volume alone). Attach several async read replicas per shard to absorb the 10M reads/sec, fronted by a cache (most reads are redirects for a small hot set of URLs, so caching does more work than replicas here). Failover per shard: promote the most-advanced replica; a short blip in one shard's redirects is more tolerable than global downtime, so per-shard independent failover is fine. Replication lag is largely a non-issue here since redirect targets rarely change after creation.

E. Uber-like system

Driver locations: extremely high write rate, ephemeral, read for proximity queries — this is usually not a relationally-replicated table at all; it's an in-memory/geo-indexed store (Redis geo, or a purpose-built location service) with its own replication, because relational primary-replica lag would make location data stale within a design that needs sub-second freshness. Trips/payments: need strong consistency and durability like the banking case — synchronous replication, careful failover. Driver/rider profiles: standard async read-replica pattern. The lesson: not every entity in one product needs the same replication strategy — pick per data type, per this framework, not once for the whole system.

F. Global multi-region application

Users in US/EU/India/SE-Asia. Default to primary + cross-region async replicas (§14) unless a specific entity needs local writes. Writes go to one authoritative region (or per-user "home region" sharding for scale); reads are served locally from each region's replica. Failover promotes a replica within the same region first (cheaper, faster) and only fails over cross-region for a full regional outage, accepting higher latency during that window. Consistency: strong for the writer's own immediate reads (read-after-write handling for that user), eventual for cross-region reads of other users' recent writes. This is the architecture most consumer-facing global products actually run, reserving true multi-primary (§14) for the specific slice of data — e.g. per-region config — that truly needs local writes.

22 Failure scenarios, walked through

1 — Primary database crashesoutage
what happens
Writes fail until a new primary is available; reads on replicas keep working (possibly stale).
data at risk
Any write acknowledged asynchronously but not yet shipped to a replica.
recovery
Promote the most up-to-date replica; redirect writes.
prevent
Automated health checks + consensus-based promotion; semi-sync to bound loss.
2 — Primary crashes right after acking a writedata loss window
what happens
The client believes the write succeeded; it may not exist anywhere else.
data at risk
Exactly that write (and any others in-flight, unshipped).
recovery
No automatic recovery of that specific write with async replication — it's gone.
prevent
Synchronous/semi-synchronous replication for data where this is unacceptable.
3 — A replica is 30 seconds behindstale reads
what happens
Reads from that replica return data up to 30s old.
data at risk
None lost — just temporarily invisible.
recovery
Replica catches up once the bottleneck (load, network, long transaction) clears; or is taken out of the read pool until it does.
prevent
Monitor lag, auto-remove lagging replicas from rotation, right-size replica hardware.
4 — Network link between primary and replica breakspartition
what happens
Replica stops receiving new log entries; falls progressively further behind.
data at risk
None yet — data is safe on the primary, just not copied.
recovery
Reconnect and resume streaming from the last acknowledged LSN once the link is restored.
prevent
Redundant network paths; alerting on replication stream health, not just node health.
5 — Two nodes think they're primarysplit-brain
what happens
Both accept writes independently; data diverges.
data at risk
Writes on the "losing" side after reconciliation — or unreconcilable conflicting writes.
recovery
Fence one side, pick a surviving primary, manually or algorithmically reconcile diverged data.
prevent
Consensus-based promotion + fencing (§11), never promote on a single node's opinion.
6 — A replica becomes overloadeddegradation
what happens
Query latency on that replica spikes; it may also fall behind on replication.
data at risk
None directly, but user-facing latency suffers.
recovery
Remove from the read pool, scale it up, or add more replicas to spread load.
prevent
Load-based routing, autoscaling replica fleets, caching in front of hot queries.
7 — An entire region goes downregional outage
what happens
Every node in that region is unreachable — primary and/or replicas.
data at risk
Unreplicated writes if the primary was in that region; all local reads unavailable.
recovery
Fail over to a replica in another region; accept higher latency for the writer's home users until the region returns.
prevent
Cross-region replicas as a deliberate DR strategy (§2C), tested failover runbooks.
8 — Replication stops but the app keeps writingsilent divergence
what happens
The primary accepts writes normally; replicas silently stop receiving them and drift further behind — everything looks fine until someone reads a replica.
data at risk
Nothing lost yet, but availability/DR guarantees are quietly void — if the primary fails now, you lose everything since replication stopped.
recovery
Alert immediately on stream health, resync the replica from a fresh base backup once the underlying issue is fixed.
prevent
Actively monitor replication lag/stream status as a first-class metric, not just node uptime.
9 — Replication is healthy but someone deletes all usersnot a replication problem
what happens
The delete replicates perfectly and quickly to every replica.
data at risk
All user data, everywhere, almost immediately.
recovery
Restore from a backup taken before the delete — replication cannot help here at all (§16).
prevent
Backups with point-in-time recovery, guardrails on destructive queries, least-privilege access.

23 Back-of-envelope math

Example baseline: 20,000 writes/sec, 200,000 reads/sec.

  • Read capacity per replica: estimate a single node's sustainable QPS for your query shape (say, 20,000 reads/sec for typical indexed point lookups) — then 200,000 / 20,000 = 10 replicas needed for read capacity alone, plus headroom for failure and lag-induced pool shrinkage (round up, e.g. 12–14).
  • Write capacity: replication does not add write capacity — every replica must apply all 20,000 writes/sec too. If 20,000/sec exceeds what one primary (and every replica replaying its log) can sustain, the fix is sharding, not more replicas.
  • Replication bandwidth: estimate average log bytes generated per write (e.g. 1 KB/row-change) × write rate × replica count = total egress from the primary. At 20,000 writes/sec × 1 KB × 10 replicas ≈ 200 MB/sec of replication egress to provision network for.
  • Storage: dataset size × (1 primary + N replica copies); cross-region replicas also imply storage cost duplicated per region.
  • Replication lag budget: (log generation rate) ÷ (replica's sustainable replay rate) — if replay can't keep pace with generation during peak, lag grows unboundedly until peak subsides; size replica hardware so replay rate comfortably exceeds peak write rate.
  • Cross-region bandwidth: replication payload size × write rate × number of remote regions, then check against inter-region network cost and latency budgets — this is often the actual limiting factor in multi-region design, not compute.
  • Failover capacity: ensure remaining replicas (after losing one to promotion) can still absorb full read traffic — if N replicas exactly cover current read load, losing one to promotion causes an immediate overload; always provision N+1 or more.
what replication does not solve

It doesn't add write throughput (that's sharding), doesn't reduce storage needs (it multiplies them), doesn't replace backups, and doesn't automatically grant strong consistency. Say this explicitly in an interview — it shows you know the boundary of the tool.

24 Common interview mistakes

"Add replicas and the database will scale."
Replicas scale reads only; write throughput is bounded by what a single primary (and every replica's replay pipeline) can sustain. Say which axis you're scaling.
"Replication gives strong consistency."
Replication is a mechanism; consistency is a guarantee you choose on top of it via sync/async and quorum settings. Name the specific setting that produces the guarantee you want.
"Async replication means no data loss."
Async replication has an explicit data-loss window between ack and shipping to a replica. Quantify it, or switch to sync/semi-sync where it's unacceptable.
"Just promote any replica."
Promote the most caught-up replica, using consensus to avoid a stale or partitioned node winning, and fence the old primary to prevent split-brain.
"Replication is the same as backup."
Replication propagates mistakes just as faithfully as good writes. Backups (point-in-time, isolated) are the actual defense against deletion, corruption, and bad migrations.
"More replicas always improve performance."
More replicas add read capacity and replication overhead/cost; beyond your read-QPS need they add no benefit and can add coordination/network overhead.
"Use synchronous replication everywhere."
Only where the durability guarantee is worth the latency and availability cost — pick per data type, not globally.
"Use asynchronous replication everywhere."
Fine for tolerant data (feeds, logs); unacceptable for anything where an acknowledged write must never disappear (payments, transfers).
"Multi-region means high availability automatically."
Multi-region only helps if failover across regions is actually implemented, tested, and fast — otherwise it's just multiple single points of failure in different places.
"Replication solves write scaling."
It doesn't — every replica must replay the same write volume. Sharding solves write scaling.
"Sharding and replication are the same thing."
Sharding splits different data across nodes for write/storage scale; replication copies the same data for read scale and availability. Real systems combine both.

25 25 practice questions

Tap a question to reveal the ideal answer and reasoning.

01Why do we need replication?

To improve read scalability (distribute reads across copies), availability (survive a primary failure via promotion), disaster recovery (survive correlated hardware/AZ/region failures), and to place data geographically closer to distributed users. Never reduce this to just one of the four.

02Replication vs backup — what's the difference?

Replication continuously copies live data, including mistakes, near-instantly. Backup is an isolated point-in-time snapshot that lets you restore to before a mistake happened. Replication protects against hardware failure; backup protects against data corruption, accidental deletes, and bad migrations.

03Replication vs sharding — what's the difference?

Replication copies the same data to multiple nodes (scales reads, adds redundancy). Sharding splits different data across nodes (scales writes and storage). They solve orthogonal problems and are typically combined: shard for capacity, replicate each shard for resilience.

04Synchronous vs asynchronous replication — trade-offs?

Synchronous waits for replica ack before acking the client: stronger durability/consistency, higher latency, lower availability if a replica is slow/down. Asynchronous acks the client immediately and ships changes afterward: lower latency, higher availability, but a data-loss window if the primary crashes before shipping. Semi-synchronous (wait for at least one, not all) is the common middle ground.

05What is replication lag, and what causes it?

The delay between a write committing on the primary and appearing on a replica. Caused by high write throughput, slow/under-provisioned replicas, network latency, large transactions, long-running replica queries, and replay bottlenecks; these compound into queue buildup under sustained load.

06How do you handle read-after-write consistency?

Route the read back to the primary right after a write, pin the session to a consistent node, track and require a minimum LSN before reading from a replica, use synchronous replication, or return the freshly written object directly instead of re-reading it. Pick based on how much load you can put back on the primary and how strict the guarantee needs to be.

07How does failover work?

Detect the primary is actually down (via health checks/consensus, not a single observer), pick the most up-to-date replica, promote it, redirect application traffic (DNS/service discovery/proxy), and re-point remaining replicas to the new primary — all while fencing the old primary to avoid split-brain.

08What happens when a primary crashes?

New writes fail until failover completes. Any write acknowledged (under async replication) but not yet shipped to a replica is lost. Reads on replicas continue, possibly stale. Recovery is promoting the most-advanced replica and redirecting traffic.

09What is split-brain?

Two nodes simultaneously believe they are the primary — typically from a network partition isolating the real primary while a replica gets promoted on the other side. Both accept independent writes, causing data divergence and duplicate/conflicting records.

10How do you prevent split-brain?

Require consensus (majority agreement) before promoting a new primary, so a minority partition can't elect one; fence the old primary (revoke its ability to write, e.g. STONITH) once a new primary is active; use quorum-based writes so a partitioned minority can't proceed at all.

11What is quorum, and why R+W>N?

N is total replicas; W is how many must ack a write; R is how many a read must query. R+W>N guarantees the read set and write set always overlap by at least one node, so a read is guaranteed to see the latest acknowledged write. It tunes the consistency/availability trade-off without requiring every node to participate in every operation.

12What is multi-primary replication?

More than one node accepts writes and propagates them to the others — used when write locality (e.g. per-region writes) matters more than avoiding conflicts. Requires conflict resolution (LWW, version vectors, CRDTs, app-level merge) and loop prevention, making it substantially harder to operate than single-primary.

13When would you use multi-region replication?

When users are distributed globally and either (a) reads should be local for latency — solved with cross-region async read replicas under one primary — or (b) writes must also be local — which pushes toward multi-primary or a globally-consistent system like Spanner, accepting the added conflict-resolution complexity.

14How do you handle conflicting writes?

Detect concurrency with version vectors or logical clocks, then resolve with last-write-wins (simple, lossy), application-level merge logic (correct but more work), or CRDTs for data types that support conflict-free merging by construction. Choice depends on how much data loss is acceptable and whether the domain has a natural merge rule.

15How would you design a highly available PostgreSQL system?

Streaming (physical) replication to multiple standbys across AZs, at least one synchronous standby for zero acknowledged-write loss on failover, an external consensus-based failover manager (e.g. Patroni + etcd) to avoid split-brain, connection routing via a proxy that always points writes at the current primary, and independent backups (base backups + WAL archiving) for point-in-time recovery.

16How would you design a globally distributed database?

Start by asking which data needs local writes vs. can tolerate one authoritative writer region. Default to primary + cross-region async read replicas; carve out only the specific entities that truly need local writes into a multi-primary or globally-consistent (Spanner-style) subsystem. Plan region-level failover and be explicit about the consistency each read path offers.

17How do replicas affect transaction consistency?

A correctly implemented replica applies a transaction's changes atomically and doesn't expose partial application to readers — you see the whole pre- or post-transaction state, never a mix. Whether the transaction is durable on more than one node at ack time depends on sync vs async replication.

18What happens if a replica is behind?

It serves stale reads for whatever the lag window is. It becomes a worse failover candidate (more data would be lost by promoting it). If lag is severe, remove it from the read pool until it catches up, and alert on lag as a first-class metric.

19How do you choose which replica becomes primary?

Pick the replica with the most advanced log position (LSN/GTID), determined via consensus among the surviving nodes rather than a single observer's opinion, to avoid promoting a stale or partitioned node and to prevent split-brain.

20Can replication improve write scalability?

No — every replica must replay the full write volume the primary sees, so replication doesn't reduce or distribute write load. Write scalability comes from sharding (splitting data so different nodes each handle a fraction of writes).

21How would you handle 1M reads/sec?

Estimate sustainable QPS per replica for your query shape, divide 1M by that to size the replica fleet with headroom for failure, and layer caching in front of the hottest keys since even a large replica fleet struggles with extreme hotspot skew. Verify replication bandwidth and lag stay within budget as the fleet grows.

22How would you handle a region failure?

Fail over reads (and writes, if that region held the primary) to another region's replica; accept a temporary latency increase for the affected region's users; ensure cross-region replicas exist ahead of time as a deliberate DR investment, and that the failover path is tested, not theoretical.

23How would you minimize replication lag?

Right-size replica hardware above peak replay demand, keep transactions small where possible, parallelize replay if the engine supports it, reduce network RTT (place replicas closer), and monitor lag continuously so degradation is caught before it compounds.

24What happens if replication completely stops?

The primary keeps accepting writes normally, but replicas silently freeze at their last position — no immediate visible symptom until someone reads a replica or the primary fails (at which point you'd lose everything since the stoppage began). This is why replication stream health needs dedicated alerting, separate from node-up/down checks.

25Design a fault-tolerant database architecture.

Shard for write/storage scale; replicate each shard (sync or semi-sync for critical data, async for tolerant data) across AZs and, for DR, regions; use consensus-based automated failover with fencing to prevent split-brain; front reads with a router/proxy and caching; maintain independent point-in-time backups; monitor replication lag and stream health explicitly. State clearly which guarantee (availability, consistency, durability) each choice is optimizing, and what it costs elsewhere.

Decision tree

1. What's the read:write ratio?
Read-heavy → replication helps directly. Write-heavy or write volume alone exceeds one node → you need sharding first; replication is a secondary concern layered on each shard.
2. Can an acknowledged write ever be lost?
No (payments, transfers, ledgers) → synchronous or semi-synchronous replication. Yes, rarely and briefly is fine (feeds, logs, analytics) → asynchronous.
3. Do reads need to reflect the very latest write?
Always → route reads to the primary, or use synchronous replication with quorum reads. Only the writer's own data needs freshness → read-after-write techniques (§7). Slightly stale is fine → plain async read replicas.
4. Are users/writers global?
Reads only need locality → cross-region async replicas under one primary. Writes also need locality → multi-primary or a globally-consistent system (Spanner-style), and you now own conflict resolution.
5. What's the failure blast radius you must survive?
Single machine → any replication setup helps. Full AZ → replicas across AZs. Full region → cross-region replicas plus a tested failover runbook.
6. How is a new primary chosen after failure?
Never "any replica" — always the most log-advanced replica, decided by consensus, with the old primary fenced to prevent split-brain.
7. Does this protect against bad data, not just bad hardware?
No — replication propagates mistakes. Add backups with point-in-time recovery regardless of your replication topology.
Always close with:
"Why this replication strategy instead of the alternatives?" — name the specific requirement (a consistency need, a latency budget, an availability target, a data-loss tolerance) that ruled out the other options.
