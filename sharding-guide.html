01Sharding fundamentals

Get the vocabulary precise before anything else — interviewers notice when candidates use "sharding," "partitioning," and "replication" interchangeably.

What is database sharding?

Sharding is horizontal partitioning across separate database instances (or clusters). Each shard holds a disjoint subset of the rows, has its own storage, its own CPU, and typically its own primary. No single machine holds the whole dataset.

Why do we need it?

Because a single database server has a ceiling on every resource — disk, RAM, CPU, IOPS, connections — and once data or traffic exceeds that ceiling, the only way to keep serving more writes (reads can often be solved with replicas) is to split the data across multiple machines that each own a smaller slice.

Sharding vs. partitioning

Partitioning is the general concept of splitting data into smaller, manageable pieces. Sharding is a specific kind of partitioning: horizontal, and distributed across separate physical/logical database servers. A single Postgres instance can have "partitions" (e.g., by date range) that still live on one machine — that's partitioning without sharding.

Horizontal vs. vertical partitioning

Horizontal = split by rows (some users on Shard 1, others on Shard 2). Vertical = split by columns or tables (user identity in one store, user preferences in another, blobs in a third). Sharding almost always refers to the horizontal kind; vertical partitioning is usually a separate, earlier optimization.

Sharding vs. replication

Replication copies the same data onto multiple machines to improve availability and read throughput. Sharding splits different data onto different machines to improve write throughput and storage capacity. They solve different bottlenecks and, in production, are almost always combined — see Section 10.

Sharding vs. caching

Caching keeps hot data close to the application to reduce read latency and database load; it doesn't change how much data the source-of-truth database can hold or write. Caching can delay the need to shard, but it doesn't solve a write-throughput or storage-capacity problem.

02Why do we need sharding?

Name the bottleneck. "The system is slow" is not an answer — the bottleneck determines the fix, and sharding is only the right fix for some of them.

BottleneckSymptomSharding helps?Cheaper fix first
Storage20 TB dataset, disk nearly full, backups take hoursYesArchive cold data, compress, vertical partition blobs out
CPUSustained 95% CPU on the primaryYes (spreads compute)Query optimization, better indexes, read replicas for read-heavy CPU load
MemoryWorking set no longer fits in buffer cache → constant disk readsYesBigger instance, better cache hit ratio, application caching
I/ODisk IOPS saturatedYesFaster storage (NVMe), read replicas, batching writes
ConnectionsHitting max_connections under normal loadSometimesConnection pooling (PgBouncer, ProxySQL)
ReadsRead QPS exceeds one server's capacityRarely the first moveRead replicas — this is exactly the bottleneck replication was built for

Why replication alone doesn't fix write scaling: replicas serve reads, but writes still funnel through a single primary. Adding replicas increases replication traffic and lag without adding any write capacity. Sharding is the only technique here that gives every shard its own independent primary, so writes can happen in parallel.

03When should I shard?

The strongest interview signal is restraint: showing you know sharding is expensive and irreversible-feeling, so you exhaust cheaper options first.

The exact order can shift with the workload — a write-heavy time-series system might reach for partitioning before caching, for instance — but the principle holds: sharding is what you do when every cheaper technique has been tried and the bottleneck is specifically write throughput or total data size, not just "the system feels slow."

Don't say: "the system is large, so we shard." Do say: "writes are at 40K/sec and a single primary tops out around 15K/sec even after indexing and connection pooling — so we split write load across N shards."

04Horizontal vs. vertical partitioning

Horizontal — split rows

Shard 1 → Users 1–1M
Shard 2 → Users 1M–2M
Shard 3 → Users 2M–3M

Same schema, every shard, different rows. This is what "sharding" means unless stated otherwise.

Vertical — split columns/tables

User DB
 ├── identity (id, email, auth)
 ├── profile (bio, avatar, prefs)
 └── activity (last_login, etc.)

Separate blob store
 └── large media / attachments

Useful when some columns are huge (blobs), rarely queried together with the rest, or accessed by a completely different service.

They compose: vertical partitioning first (pull blobs and rarely-joined data out), then horizontal sharding on what remains, once that's still too big for one machine.

05Sharding strategies

Five approaches, each trading off even distribution against range-query support and rebalancing cost.

A. Range-based sharding

user_id 1     – 1,000,000   → Shard 1
user_id 1,000,001 – 2,000,000 → Shard 2
user_id 2,000,001 – 3,000,000 → Shard 3

Advantages

  • Range queries (WHERE id BETWEEN x AND y) stay on one or few shards
  • Simple to reason about and implement
  • Easy to add new ranges at the end for growth

Disadvantages

  • Prone to hot shards — sequential IDs mean the newest, most-active range is always on the last shard
  • Uneven distribution if key values cluster
  • Rebalancing means physically moving contiguous chunks

Good fit when: the dominant access pattern is range scans — time-series data, analytics tables, or anything queried "give me everything between X and Y."

B. Hash-based sharding

shard_id = hash(user_id) % N

Spreads rows near-uniformly regardless of key clustering, which kills most hotspots that plague range sharding. The trade-off: a query like "all users in India" can no longer be answered by hitting one shard — the hash destroys locality, so range and prefix queries now require scatter-gather across every shard.

The resharding problem: hash(user_id) % 4 and hash(user_id) % 5 send almost every key to a different shard, because the modulus changed. Going from 4 to 5 shards this way requires moving roughly 80% of all data — not just the fraction that "should" move. This is exactly the problem consistent hashing exists to solve.

C. Consistent hashing

              0
              │
     ┌────────┼────────┐
     │        │         │
  A1 ●        │         ●  D1
     │                   │
  B1 ●   hash ring   ●  C1
     │     (0–2^32)      │
     │        │         │
     └────────┼────────┘
              │
  key "u:88213" hashes here ──► walk clockwise ──► lands on nearest node: C1 (physical Shard C)

Each physical shard owns several points ("virtual nodes") scattered around the ring, not just one. A key maps to whichever node is next clockwise from its hash. When a shard is added or removed, only the keys between its neighbors on the ring move — typically ~1/N of the data, not most of it. This is why distributed systems (Cassandra, DynamoDB, many caching layers) default to consistent hashing over naive modulus hashing.

D. Directory-based sharding

User ID → Shard Mapping (stored in a lookup service)

101 → Shard A
102 → Shard C
103 → Shard B

A metadata/lookup service holds an explicit mapping instead of computing it. Advantage: maximum flexibility — you can move any single key to any shard, ideal for splitting hot keys individually. Cost: that lookup service is now extra infrastructure, an extra network hop on every request, and — unless it's itself replicated — a single point of failure and a scaling bottleneck of its own.

E. Geographic sharding

India users  → India shard  (Mumbai)
US users     → US shard     (Virginia)
EU users     → EU shard     (Frankfurt)

Optimizes for latency (data lives near the user) and data residency/compliance (GDPR-style requirements that EU user data stay in the EU). It also gives natural regional failure isolation. The catch: what happens when a user travels or permanently relocates? Their data either needs a costly cross-region migration, or the application accepts higher latency serving them from their "home" shard indefinitely — a real design decision, not a footnote.

06Choosing a shard key

This is the single highest-leverage decision in any sharded design, and the question interviewers probe hardest.

What makes a good shard key

  • High cardinality — enough distinct values to spread across many shards (a boolean is a terrible shard key; a UUID is not).
  • Even distribution — no single value should own a disproportionate share of rows or traffic.
  • Matches your dominant query pattern — most queries should be answerable by hitting one shard, not all of them.
  • Even write distribution — not just even storage, even write rate per value.
  • Stable over the record's lifetime — changing a shard key means physically moving the record between shards.
  • Predictable — the application (or router) should be able to compute it without an extra lookup, where possible.
Candidate keyGood forRisk
user_idHigh cardinality, most queries are per-user, stableCelebrity/power users can still create hot shards; queries not scoped by user (e.g. "all orders today") need scatter-gather
countryGreat for data residency, low cardinality is fine if traffic is evenTerrible cardinality relative to population — India/US/China shards will dwarf small-country shards; classic hot shard
created_at (range)Great for time-series/analytics range scansAll new writes land on the most recent range → the "last shard is always hot" problem (see Section 8)

The pattern across all three: cardinality and distribution matter more than intuition about "the natural identifier." A key can be semantically obvious and still be a bad shard key.

07Hot shards / hotspots

Shard 1 → 10% traffic
Shard 2 → 10% traffic
Shard 3 → 70% traffic   ◄── hot shard
Shard 4 → 10% traffic

Common causes: a celebrity account or viral post concentrating reads on one user's shard; a flash-sale product concentrating writes on one product's shard; time-based keys concentrating all current writes on the newest range; or geographic sharding when one region is simply much larger than the others.

Mitigations

  • Better shard key — sometimes the fix is upstream: pick a key that doesn't correlate with popularity.
  • Hashing — breaks up natural clustering that a range key would expose.
  • Key salting — append a random suffix to a hot key (celebrity_id#3) to spread its writes across several shards, then fan-in on read.
  • Virtual shards / consistent hashing — makes it possible to move only the hot slice, not the whole shard.
  • Splitting hot partitions — detect the hot range/key and split it into its own dedicated shard(s).
  • Caching — absorb read hotspots in front of the database entirely (see Section 19).

09Sharding architecture

Application-level sharding

Application
    │  (computes shard via hash/range)
    ▼
Shard Router (library, in-process)
    │
┌───┴───┬───────┬───────┐
Shard 1 Shard 2 Shard 3

The application (or a library it embeds) knows the sharding scheme and routes directly. No extra network hop, but every service needs the routing logic, and changing the scheme means redeploying application code.

Database proxy / router

Application
    │  (talks to proxy like a normal DB)
    ▼
Proxy / Router  ◄── metadata service
    │
┌───┴───┬───────┬───────┐
Shard 1 Shard 2 Shard 3

A dedicated layer (e.g. Vitess, ProxySQL) owns routing and metadata. Applications stay simple and the scheme can evolve independently — at the cost of an extra hop and another piece of infrastructure to run and scale.

Trade-off in one line: application-level sharding is faster and simpler at small scale but couples every service to the sharding scheme; a proxy/router centralizes that knowledge at the cost of latency and operational surface area.

10Sharding + replication

Production systems use both, because they solve different problems.

        Shard 1                      Shard 2
     ┌──────────┐                ┌──────────┐
     │ Primary  │                │ Primary  │
     └────┬─────┘                └────┬─────┘
          │ replicates                │ replicates
          ▼                           ▼
     ┌──────────┐                ┌──────────┐
     │ Replica  │                │ Replica  │
     └──────────┘                └──────────┘
  • Sharding scales writes and storage — more independent primaries, each owning less data.
  • Replication scales reads and availability — each shard survives its primary failing, and read traffic can be spread across replicas.
Why replication alone can't replace sharding: replicas are copies of the same data — adding more of them never increases how many distinct writes the system can absorb, because every write still has to reach every replica of that one primary eventually. Only splitting the data itself (sharding) parallelizes writes.

11Cross-shard queries

SELECT * FROM users WHERE country = 'India';

If users is sharded by user_id, this predicate has no relationship to the shard key — the row for any given Indian user could be on any shard. The system has two options:

  • Scatter-gather: fan the query out to every shard in parallel, then merge results in the application or router. Correct, but latency is bounded by the slowest shard, and it multiplies load across the whole cluster for one logical query.
  • Secondary index / search system: maintain a separate index (often in Elasticsearch or a dedicated global index service) keyed by country that points back to the owning shard, so the query hits one targeted lookup instead of fanning out.

The general lesson: any query that doesn't filter on the shard key is expensive by default in a sharded system, and the fix is either accepting the scatter-gather cost for rare queries or building dedicated indexing infrastructure for frequent ones.

12Cross-shard joins

SELECT * FROM orders JOIN users ON orders.user_id = users.id;
users  → Shard 1
orders → Shard 4     ◄── join now requires two round trips across the network

A relational join assumes both tables are reachable in one query engine. Across shards, there's no server that can execute the join directly — the database would need to pull rows from both shards and join them in application code or middleware, which is slow and loses transactional guarantees.

Alternatives

  • Co-locate related data — shard orders by the same key as users (e.g. both by user_id) so a user's orders always live with that user.
  • Denormalization — embed the fields you'd have joined for directly in the row (store the user's display name on the order itself).
  • Application-side joins — fetch from both shards separately and join in code; acceptable for small result sets.
  • Separate analytical systems — ETL into a data warehouse where joins across the full dataset are cheap, for reporting-style queries that don't need to be real-time.
Data locality is the real lesson: the best sharded schemas are designed so that data accessed together lives together. Shard key choice isn't just about distribution — it's about which joins you're implicitly making impossible.

13Cross-shard transactions

Transfer $100

Account A → Shard 1   (debit)
Account B → Shard 5   (credit)

Both must succeed, or neither should.
ApproachHow it worksTrade-off
Two-phase commit (2PC)Coordinator asks all shards to "prepare," then commits only if all agreeStrong atomicity, but blocks on the slowest participant and a coordinator failure mid-commit can leave shards in limbo
Distributed transaction protocolsBuilt into some databases (Spanner, CockroachDB) using consensus + synchronized clocksStrong guarantees, but requires the underlying database to support it — not a bolt-on
Saga patternBreak the transaction into a sequence of local transactions, each with a compensating action if a later step failsNo cross-shard locking, better throughput, but only eventual consistency during the saga's execution window
Event-driven / compensating transactionsPublish "debit happened" as an event; a consumer applies the credit, retries, or triggers a compensating reversal on failureHighly scalable and decoupled, but the system is briefly inconsistent and needs idempotent, retry-safe handlers

The honest interview answer: cross-shard transactions are one of the reasons teams pick a co-location strategy (keep related accounts on the same shard when possible) or a database purpose-built for distributed transactions (Spanner/CockroachDB) rather than bolting 2PC onto a system that wasn't designed for it.

14Rebalancing / resharding

Before:                       After split:
Shard 1 → 500 GB              Shard 1 → 500 GB
Shard 2 → 500 GB              Shard 2 → 500 GB
Shard 3 → 5 TB   ◄── too big  Shard 3a → 2.5 TB
                               Shard 3b → 2.5 TB

Zero/low-downtime resharding, step by step

  1. Add capacity — provision the new shard(s) or split target.
  2. Dual writes — start writing every new change to both the old and new location.
  3. Backfill — copy existing historical data from the old shard into the new one in the background.
  4. Verify — compare checksums/row counts between old and new to confirm consistency.
  5. Cutover — flip the routing metadata so reads (and eventually writes) go to the new location.
  6. Stop dual writes, decommission — once fully cut over, remove the old copy.

Consistent hashing (Section 5C) and virtual shards (Section 15) exist specifically to make step 1–3 cheaper: they minimize how much data has to move in the first place, which is the dominant cost of any reshard.

15Consistent hashing and virtual shards

Physical Shard A            Physical Shard B
 ├── V1  (ring pos 12)       ├── V4  (ring pos 55)
 ├── V2  (ring pos 30)       ├── V5  (ring pos 71)
 └── V3  (ring pos 44)       └── V6  (ring pos 90)

Without virtual nodes, each physical shard is one point on the ring, so removing it dumps its entire range onto exactly one neighbor — a lopsided rebalance. With many virtual nodes per physical shard, that same removal spreads its data thinly across every remaining shard, and the new load lands roughly evenly instead of doubling one neighbor's load. Virtual nodes are what make "add one more shard" a routine, low-risk operation instead of a major migration event.

16Shard metadata

How does the system know user_id = 12345 belongs to Shard 7?

ApproachDescriptionFailure mode
Static configurationHard-coded ranges/hash formula, baked into app configSimple, but every rebalance needs a coordinated config rollout
Metadata databaseA small, heavily-replicated DB storing the current mappingMust be highly available itself — it's a dependency of every single query
Service discovery / config serviceetcd, ZooKeeper, Consul holding routing state with watches for change notificationBattle-tested for exactly this; still a critical-path dependency

If the metadata service goes down: new requests can't be routed at all, even though the shards themselves are healthy. This is why metadata/routing layers are typically the most heavily replicated, cached, and monitored piece of a sharded architecture — clients often cache the mapping locally with a short TTL specifically to survive brief metadata-service outages.

17Failure scenarios

For each: what happens → impact → recovery → prevention.

01One shard goes down
What happens
All reads/writes targeting that shard's key range fail; other shards are unaffected.
Impact
Partial outage — proportional to that shard's share of users/data, not total.
Recovery
Promote a replica of that shard to primary; router redirects traffic once promotion completes.
Prevention
Every shard replicated with automatic failover; health checks with fast detection.
02One shard becomes extremely slow
What happens
Requests to that shard queue up or time out; scatter-gather queries are bottlenecked by this one slow shard.
Impact
Often worse than a hard failure — no clean failover trigger, and it can cascade (thread/connection pool exhaustion in callers).
Recovery
Timeouts + circuit breakers to fail fast; investigate (bad query plan, disk issue, noisy-neighbor if multi-tenant hardware).
Prevention
Per-shard latency SLOs and alerting; isolate hardware/resources per shard where possible.
03A shard becomes full
What happens
Writes to that shard start failing while other shards have headroom.
Impact
Write outage for that shard's key range only.
Recovery
Emergency split of the hot/full shard, or fast-track a planned reshard.
Prevention
Capacity alerts well before the limit; proactive splitting based on growth trend, not just current size.
04Shard router goes down
What happens
No request can be routed anywhere, even though every shard is healthy.
Impact
Total outage — this is a single point of failure for the entire system if not itself redundant.
Recovery
Failover to a standby router instance; clients fall back to cached routing table.
Prevention
Run the router/metadata layer as a highly-available cluster, never a single instance.
05Network partition
What happens
Some shards or replicas become unreachable from the router or from each other.
Impact
Depends on CAP trade-offs made per shard — some may reject writes to preserve consistency, others may serve stale reads.
Recovery
Partition heals; reconcile any divergent writes (conflict resolution or last-writer-wins, depending on design).
Prevention
Design each shard's replica set with an explicit consistency model in advance; don't discover it during an incident.
06A shard loses its primary
What happens
That shard can't accept writes until a new primary is elected/promoted.
Impact
Write outage scoped to that shard; reads may continue from replicas.
Recovery
Automatic leader election (if supported) or manual promotion of the most caught-up replica.
Prevention
Automated failover tooling, tested regularly — not just configured and forgotten.
07A shard loses all replicas
What happens
The primary is now a single point of failure for that shard's data.
Impact
No availability protection; a primary failure now means real data-loss risk, not just a brief outage.
Recovery
Provision new replicas immediately and re-sync from the primary or latest backup.
Prevention
Alert loudly on replica-count drops; never let replication factor silently degrade.
08A bad shard key causes extreme hotspotting
What happens
One shard absorbs a hugely disproportionate share of traffic or data.
Impact
That shard degrades or fails while the rest of the cluster is idle — poor resource utilization plus a real outage risk.
Recovery
Short-term: cache in front of the hot shard, salt the hot key. Long-term: redesign the shard key.
Prevention
Model expected traffic distribution against the candidate shard key before launch, not after.
09Resharding fails halfway through
What happens
Some data has migrated to the new shard, some hasn't; routing metadata may be inconsistent.
Impact
Risk of reads/writes hitting the wrong copy, or missing data entirely, if not handled carefully.
Recovery
Dual-write design (Section 14) means both copies exist during migration — pause, diagnose, and resume or roll back safely.
Prevention
Always migrate with dual writes + verification steps, never a one-shot cutover with no rollback path.

18Sharding and consistency

Sharding itself does not determine consistency — it determines how data is distributed, not how updates propagate or how reads are ordered. Consistency comes from the replication and transaction design layered on top of the shards.

  • Strong consistency is achievable within a single shard (it's just one primary handling writes) but requires 2PC, consensus (Raft/Paxos), or a purpose-built system like Spanner across shards.
  • Eventual consistency is the common default across shards when using async replication or event-driven cross-shard updates — cheaper and more available, but reads can be stale.
  • Ordering is easy within one shard (it has one write path) and hard across shards (there's no natural global clock unless you build one, à la Spanner's TrueTime).
  • Read-after-write consistency within a shard is straightforward if reads go to the primary; it gets complicated the moment reads are allowed to hit replicas or a different shard than the one just written.

19Sharding and caching

Client
  │
  ▼
CDN            ◄── static/public content, edge-cached
  │
  ▼
Redis          ◄── hot keys, session data, computed aggregates
  │
  ▼

Database Shards  ◄── source of truth, only hit on cache miss
  • What each layer caches: CDN — static assets and public, cacheable responses; Redis/app cache — per-entity hot reads and expensive aggregations; the shards remain the source of truth for everything.
  • Hot keys: a single celebrity record can overwhelm a single Redis node too — the same salting/replication techniques from Section 7 apply one layer up.
  • Cache invalidation: writes must invalidate or update the cache for the same key — this is the classic hard problem, made harder because the write and the cache entry may not be co-located.
  • Shard-aware caching: caching layers can mirror the shard topology (a cache node per shard) so cache hit/miss patterns match the database's actual hot spots.

21System-design examples

Framework for each: Requirements → Scale → Data model → Access patterns → Shard key → Strategy → Routing → Replication → Hotspots → Rebalancing → Failure handling → Trade-offs.

A. Instagram

UsersPostsFollowersComments

Shard key: user_id for users and their own posts/comments (keeps a user's content co-located). Hotspots: celebrity accounts with millions of followers create both a write hotspot (fan-out on post) and a read hotspot (everyone loading their profile). Mitigation: hybrid fan-out — push updates to most followers' feeds immediately, but "pull" celebrity posts into feeds on read instead of fanning out to millions of followers synchronously. Cross-shard problem: generating a feed requires reading posts from every followed user, who are scattered across shards — solved with a dedicated feed/timeline service rather than a live join.

B. E-commerce

UsersProductsOrdersInventory

Shard key: user_id for orders (co-locate a customer's order history); products often sharded by product_id hash. Hotspots: flash sales concentrate reads/writes on a handful of product shards — mitigated with aggressive caching and, for inventory decrement, a queue-based or dedicated fast-path counter rather than hitting the sharded row directly. Cross-shard transactions: "reserve inventory + create order + charge payment" spans shards/services — typically implemented as a saga with compensating steps (release reservation, refund) if any step fails.

C. Uber

DriversRidersTripsLocation

Shard key: geographic — often a geohash or city/region ID, since almost every query ("drivers near me") is inherently location-scoped. Hotspots: dense city centers or major events create geographic hotspots; mitigated with finer-grained geo-cells in busy areas (effectively more virtual shards per unit area downtown than in rural regions). Real-time workload: constant location pings are extremely write-heavy — often handled by a separate high-throughput location-update pipeline rather than the primary trip/rider database.

D. Twitter/X-like system

500M users100M posts/dayvery high read traffic

User sharding: by user_id hash for even distribution. Post storage: often a separate, append-heavy store keyed by post ID, sharded independently from users. Timeline/feed: precomputed and cached per-user (fan-out-on-write) for most users, with pull-based fan-out for celebrities to avoid a single tweet triggering tens of millions of writes. Replication: heavy read-replica use given the read:write ratio is enormous — reads vastly outnumber writes on this workload.

E. URL shortener

100M writes/day10B reads/day

Shard key: hash of the short code (or the short code itself, generated to be evenly distributed, e.g. base62 of a Snowflake ID). Strategy: hash-based, since lookups are always by exact short code — no range queries needed, so hash sharding's weaknesses don't apply. Read scaling: given the ~100:1 read:write ratio, this system leans almost entirely on caching (a small in-memory cache can absorb a huge fraction of reads) and read replicas rather than adding shards for read capacity. Hot URLs: a viral link is a single-key hotspot — solved with caching in front of the shard, not more shards.

F. Banking system

AccountsTransactionsTransfers

Shard key: account_id, chosen so a single account's transaction history stays co-located. Cross-shard transfers: the unavoidable hard case (Section 13) — typically 2PC or a database with native distributed transactions, because "money got debited but not credited" is not an acceptable eventual-consistency window. Consistency: strong consistency is a hard requirement here, unlike social/e-commerce systems, which materially narrows the acceptable architecture choices. Regulatory: data residency rules may force geographic sharding regardless of the traffic-distribution trade-offs it introduces.

24Important calculations

Sizing by storage

Total data      = 20 TB
Target shard sz = 500 GB
Shards needed   = 20,000 GB / 500 GB = 40 shards

Then check throughput, don't stop at storage

Peak traffic        = 1,000,000 requests/sec
Assume each shard   can sustain ~15,000 req/sec comfortably
Shards for traffic  = 1,000,000 / 15,000 ≈ 67 shards

Final shard count = max(storage-driven count, traffic-driven count) = 67 shards
(then add headroom, e.g. +20–30%, for growth and hotspots)
Why shard count shouldn't be based only on storage size: a shard sized correctly for disk capacity can still be far too small for its share of query throughput, especially under a skewed access pattern. Always compute both the storage-driven and traffic-driven shard counts and take the larger one.

Other quantities worth estimating before designing

  • Data per shard — total data ÷ shard count, tracked over time to predict when a split is needed.
  • Queries per shard — total QPS ÷ shard count, compared against a single node's sustainable QPS.
  • Storage growth rate — GB/month, to forecast when the current shard count runs out of runway.
  • Replication traffic — write rate × replica count × average row size, since replication itself consumes bandwidth and I/O.
  • Rebalancing cost — bytes that must move × network bandwidth available = estimated migration duration, used to decide if a reshard can be done live or needs a maintenance window.

26Common interview mistakes

"Just shard by user_id."

Better: "user_id is a strong candidate because most access is per-user, but I'd check for hot users first and confirm whether any frequent queries aren't user-scoped before locking it in."

"Hashing is always better."

Better: "Hashing fixes distribution but kills range-query locality — I'd only choose it if range scans aren't a dominant access pattern."

"More shards means better performance."

Better: "More shards means more parallelism, but also more cross-shard queries, more operational overhead, and more replication traffic — I'd size shards to the actual bottleneck, not maximize count."

"Sharding solves everything."

Better: "Sharding solves write throughput and storage limits specifically — it doesn't fix bad queries, and it introduces new problems like cross-shard joins and transactions."

"Replication and sharding are the same."

Better: "Replication copies the same data for availability/read scale; sharding splits different data for write/storage scale — production systems use both."

"Use UUIDs and hotspots disappear."

Better: "UUIDs fix sequential-ID write hotspots specifically, but a popular entity (celebrity, viral product) is still a hotspot regardless of ID format."

"Cross-shard joins are easy."

Better: "They're one of the hardest problems in sharded systems — I'd design for data locality up front to avoid needing them at all."

"Cross-shard transactions are just normal transactions."

Better: "They require 2PC, sagas, or a database with native distributed transaction support — normal single-node ACID guarantees don't extend across shards for free."

"We can add shards whenever we want."

Better: "Adding shards triggers a rebalance that can move significant data — with naive hashing, most of it. I'd use consistent hashing specifically to make this cheap."

"Consistent hashing means no data movement."

Better: "It minimizes data movement to roughly 1/N of the data, not zero — some keys always have to move when topology changes."

"Sharding automatically gives high availability."

Better: "Sharding by itself creates more single points of failure, one per shard, unless each shard is independently replicated."

"If one shard fails, the entire database fails."

Better: "Only the key range on that shard is affected — that's actually one of sharding's benefits: failure is partial, not total, assuming the router itself stays up."

2730 sharding interview questions — with answers

Attempt each one mentally before expanding it. They progress from fundamentals to full system designs.

FundamentalsStrategyShard keysHard problemsMulti-regionFailuresFull designs
Q1What is sharding?

Horizontal partitioning of a dataset across multiple independent database servers, each holding a disjoint subset of rows, so that no single machine has to store or serve the entire dataset.

Q2Why do we need sharding?

A single server has finite CPU, memory, disk, and connection capacity. Once write throughput or total data size exceeds what one machine (even a large one) can handle, splitting data across multiple machines is the only way to keep scaling.

Q3Sharding vs. partitioning — what's the difference?

Partitioning is the general idea of splitting data into smaller pieces; sharding is specifically horizontal partitioning distributed across separate physical/logical database servers. All sharding is partitioning; not all partitioning is sharding.

Q4Sharding vs. replication — what's the difference?

Replication copies the same data to multiple machines for availability and read scaling. Sharding splits different data across machines for write throughput and storage scaling. They're complementary, not substitutes.

Q5Range vs. hash sharding — when would you pick each?

Range sharding when range scans dominate the access pattern (time-series, ordered scans) despite the hotspot risk. Hash sharding when even distribution matters more than range-query locality — most OLTP point-lookup workloads.

Q6Explain consistent hashing and why it matters.

Keys and nodes are placed on a hash ring; a key belongs to the next node clockwise. Adding or removing a node only reassigns the keys between it and its neighbors — roughly 1/N of the data — instead of the near-total reshuffle a naive modulus hash causes.

Q7What makes a good shard key?

High cardinality, even distribution of both storage and traffic, alignment with the dominant query pattern, and stability over the record's lifetime.

Q8What is a hot partition and how do you fix it?

A shard receiving disproportionate load, usually from a popular entity or a poorly chosen key. Fixes include key salting, caching in front of the hot shard, splitting the hot range into its own shard, or redesigning the shard key entirely.

Q9How do you reshard with minimal downtime?

Provision new capacity, start dual-writing to old and new locations, backfill historical data, verify consistency between the two, then cut over routing metadata, and finally stop dual writes and decommission the old copy.

Q10How do you handle a query that doesn't filter on the shard key?

Either scatter-gather across all shards and merge results in the router/application, or maintain a secondary index / search system keyed on the non-shard-key field that points back to the owning shard.

Q11Why are cross-shard joins hard?

A join engine assumes both tables are reachable in one query execution context. Across shards, rows must be fetched from each shard separately and joined outside the database, losing the query planner's optimizations and any transactional guarantee.

Q12How would you design around cross-shard joins?

Co-locate frequently-joined data under the same shard key, denormalize fields you'd otherwise join for, or push true cross-entity analytics into a separate warehouse where joins across the full dataset are cheap.

Q13How do you implement a cross-shard transaction?

Two-phase commit for strong atomicity at the cost of blocking and coordinator risk; a saga pattern with compensating actions for higher throughput at the cost of only eventual consistency during execution; or use a database with native distributed transactions (Spanner, CockroachDB).

Q14What is a global secondary index and when do you need one?

An index maintained separately from the primary shard layout, itself sharded by a different key, that lets you look up records efficiently by a field other than the primary shard key without scatter-gather.

Q15How would you design a multi-region sharded system?

Shard primarily by geography for latency and data-residency compliance, then sub-shard within each region (typically by a hashed user/entity ID) for even distribution. Explicitly decide how to handle users who move or travel between regions.

Q16Why combine sharding with replication instead of using either alone?

Sharding alone gives every shard a single point of failure; replication alone can't scale writes past one primary. Together, each shard gets independent write capacity and each shard's primary gets availability protection via its own replicas.

Q17What happens when a shard fails, and how do you recover?

Only that shard's key range is affected — other shards keep serving normally. Recovery is promoting a healthy replica of that shard to primary and updating routing once promotion completes.

Q18What happens when the shard router/proxy fails?

Total outage, since no request can be routed anywhere even if every shard is healthy — this is why the router itself must run as a highly-available cluster, not a single instance.

Q19Walk through designing a sharded database from scratch.

Start with requirements and scale estimates, identify the actual bottleneck (storage vs. write throughput), pick a shard key based on dominant access patterns, choose a partitioning strategy, decide on routing architecture, layer replication for availability, plan for hotspots and rebalancing up front, and enumerate failure scenarios before calling the design done.

Q20Design the sharding strategy for Instagram.

Shard by user_id to co-locate a user's own content; handle celebrity hotspots with hybrid fan-out (push for normal users, pull for celebrities); build a dedicated feed service rather than doing live cross-shard joins to construct a timeline.

Q21Design the sharding strategy for Uber.

Shard geographically (geohash/region) since nearly every core query is location-scoped; use finer-grained geo-cells in dense areas to avoid hotspots; handle high-frequency location pings through a separate write-optimized pipeline rather than the primary trip database.

Q22Design the sharding strategy for a Twitter-like system.

Shard users by hashed user_id; store posts in a separate, independently-sharded append-heavy store; precompute and cache timelines with fan-out-on-write for most users and pull-based fan-out for celebrities to avoid write storms.

Q23Design the sharding strategy for an e-commerce system.

Shard orders by user_id and products by hashed product_id; handle flash-sale hotspots with caching and queue-based inventory updates; implement checkout as a saga spanning inventory, order, and payment services with compensating actions on failure.

Q24Design the sharding strategy for a banking system.

Shard by account_id to keep transaction history co-located; require strong consistency for transfers via 2PC or a distributed-transaction database; consider geographic sharding constraints from regulatory data-residency requirements.

Q25How do you decide the number of shards?

Compute a storage-driven shard count (total data ÷ target shard size) and a traffic-driven shard count (peak QPS ÷ sustainable QPS per shard), and take the larger of the two — never size purely on storage.

Q26How does sharding interact with consistency guarantees?

Sharding doesn't determine consistency by itself — strong consistency is native within a single shard but requires consensus or distributed-transaction protocols across shards; most sharded systems default to eventual consistency across shard boundaries because it's cheaper and more available.

Q27How would you add a global secondary index without breaking write performance?

Maintain it asynchronously (e.g. via change-data-capture or an event stream) rather than synchronously on every write, accepting brief lag between the primary write and index update in exchange for not slowing down the write path.

Q28What's the risk of a resharding operation failing halfway?

Data can exist inconsistently between old and new locations, and routing metadata can point to the wrong place. Mitigated by always migrating via dual writes plus a verification step, so the operation can be safely paused, resumed, or rolled back.

Q29How do virtual nodes improve on plain consistent hashing?

Without virtual nodes, removing one physical node dumps its entire range onto a single neighbor. With many virtual nodes per physical shard, that same removal's load is spread thinly across every remaining shard, keeping rebalancing events low-risk and even.

Q30An interviewer says "just add more shards" to fix a hot shard. How do you respond?

Adding shards only helps if the new key distribution actually spreads the hot key's load — if the hotspot is a single celebrity/entity, more shards don't split that one entity's traffic. The real fix is addressing the specific key (salting, caching, dedicated handling), not blindly increasing shard count.

Key concepts, one line each

  • Shard key — the field used to decide which shard a row lives on.
  • Partition — a smaller, logically or physically split piece of a dataset.
  • Hot shard — a shard receiving disproportionate load relative to its peers.
  • Scatter-gather — fanning a query out to every shard and merging results.
  • Shard router — the layer that maps a request to the correct shard.
  • Virtual node — a synthetic point on a hash ring owned by a physical shard, used to smooth rebalancing.
  • Consistent hashing — a hashing scheme where topology changes move only ~1/N of the data.
  • Resharding — changing the number of shards or the sharding scheme.
  • Rebalancing — moving data between existing shards to restore even distribution.
  • Cross-shard query/transaction — an operation that must touch more than one shard.
  • Global secondary index — an index on a non-shard-key field, maintained separately to avoid scatter-gather.

Sharding decision tree

Is a single database server the bottleneck right now? │ ├─ No → don't shard. Fix the actual bottleneck (indexes, queries, caching, connection pooling). │ └─ Yes → Is the bottleneck read throughput only? │ ├─ Yes → add read replicas. Re-measure before sharding. │ └─ No (write throughput and/or storage) → │ Does the dominant access pattern need range scans? │ ├─ Yes → range-based sharding (accept hotspot risk on newest range, │ mitigate with virtual shards / splitting). │ └─ No → Do you need per-key rebalancing flexibility? │ ├─ Yes → directory-based sharding. │ └─ No → hash-based sharding, implemented via consistent hashing (never naive modulus) so future rebalancing is cheap. Then, regardless of branch: → Replicate every shard for availability. → Design the schema for data locality to minimize cross-shard joins. → Decide the cross-shard transaction strategy (2PC / saga) BEFORE you need it. → Instrument for hotspot detection from day one. → Have a resharding playbook (dual writes + backfill + verify + cutover) ready before you're forced to use it under pressure.
The one question every design must answer: "Why this shard key and this strategy instead of the alternatives?" A good answer names the actual bottleneck, explains why cheaper techniques (indexing, caching, replicas) weren't enough, and is honest about the new problems — cross-shard joins, transactions, rebalancing cost — that the chosen approach introduces.
