SYSTEM DESIGN / BACKEND / HTTP SEMANTICS

301 vs 302, and everything that actually depends on it

A response code is a promise. 301 tells every cache, browser, and crawler between you and the client "stop asking, this is permanent." 302 tells them "ask again next time." That one bit of intent ripples through caching, SEO, load balancers, OAuth, payment APIs, and multi-region failover — which is exactly why it's a favorite system-design interview thread.

Request→ Server→ 3xx + Location→ Client decision→ Cache?→ New request

01 HTTP Basics & the Redirect Flow

An HTTP redirect is nothing exotic at the protocol level: it's an ordinary HTTP response whose status code falls in the 3xx class, carrying a Location header that tells the client where to go instead. The server never fetches the new resource on the client's behalf — it hands back a pointer and steps out of the way. That's the whole mechanism.

The Location header can be absolute (https://example.com/new) or relative (/new); browsers resolve relative locations against the request URL. Nothing about a 3xx response contains a body the client is meant to render — some servers send a small HTML fallback body for non-following clients, but it's not the mechanism.

GET /old-url HTTP/1.1
Host: example.com

→

HTTP/1.1 301 Moved Permanently
Location: https://example.com/new-url
Content-Length: 0

The client — a browser, a curl process, an SDK — reads the status code, decides whether to follow it, and if so, issues a brand-new HTTP request to the URL in Location. Two full request/response cycles happen where the caller only asked for one.

KEY MENTAL MODEL

A redirect is a response, never an internal server-side rewrite. The server that issued the 301 is not necessarily the server that serves the final content, and the client — not the server — decides whether, and how, to follow it. That distinction is the seed of almost every trade-off in this document.

02 301 vs 302 — Core Difference

301 Moved Permanently asserts that the resource has moved for good — bookmark the new URL, update your links, transfer any authority you associated with the old one to the new one. 302 Found (historically "Moved Temporarily") asserts the opposite: this is a detour, the old URL is still the "real" one, don't update anything durable.

That single bit of intent is read by three different audiences, each of which reacts differently:

  • Clients / browsers may cache a 301 indefinitely and stop hitting the old URL at all on future navigations. A 302 is refetched from the origin every time unless explicit cache headers say otherwise.
  • Caches / CDNs / proxies treat 301 as a candidate for long-lived, heuristic caching per RFC 7231 even with no explicit Cache-Control; 302 is not cached by default.
  • Search engines transfer ranking signal ("link equity") from the old URL to the new one on a 301, and index the new URL as canonical. On a 302, they keep the old URL indexed and treat the new one as a temporary destination.

03 The Semantics Get Messy: 301, 302, 303, 307, 308

301 and 302 both predate a clean specification of what should happen to the HTTP method and body across the redirect. In practice, most browsers historically converted a POST into a GET on both 301 and 302 — a quirk of early Netscape/IE behavior that got baked into the ecosystem long before it was written down properly. That ambiguity is exactly why 303, 307, and 308 exist: they disambiguate intent that 301/302 left fuzzy.

  • 303 See Other — explicitly says "the result of your request is over there; go fetch it with GET," regardless of what method the original request used. This formalizes the informal POST→GET behavior instead of leaving it to convention.
  • 307 Temporary Redirect — behaves like 302 but guarantees the method and body are preserved. A redirected POST stays a POST.
  • 308 Permanent Redirect — behaves like 301 but guarantees method/body preservation. A redirected POST stays a POST, permanently moved.

301 vs 308

Both say "this moved for good." The only difference is contract strength on the method: 301 leaves method handling to client convention (usually GET-coercion for old clients), 308 makes preservation mandatory. Prefer 308 for any permanent move where the endpoint accepts non-GET methods — API base-path migrations, for example.

302 vs 307

Same relationship, one rung down the permanence ladder. 302 is the historically ambiguous "temporary, probably becomes GET." 307 is "temporary, and I promise your method and body survive." Use 307 for temporary redirects in front of anything that isn't a plain GET — feature-flagged traffic shifting in front of a write API, for instance.

04 GET vs POST — Why This Is the Interview Trap

This is where the interview usually pivots from trivia to real engineering judgment. The historical behavior — many browsers convert POST → GET on a 301 or 302 — is not part of the original HTTP spec; it's convention that RFC 7231 later documented as "widely deployed" so implementers wouldn't have to guess.

POST /payment            (client submits a charge)
      │
      ▼
    302 Found
Location: /success
      │
      ▼
GET /success              ← body/method silently dropped

That's usually harmless for a "thanks for your order" page. It is not harmless if the redirect target is meant to re-execute the write — a client naively retrying, or a proxy following a 302 blindly, can drop the payload of a payment or state-changing call, or worse, resubmit a GET that was never meant to trigger a side effect.

POST /payment
      │
      ▼
    307 Temporary Redirect
Location: /payment-v2
      │
      ▼
POST /payment-v2          ← method AND body preserved intact
WHY THIS MATTERS FOR MONEY-MOVING ENDPOINTS

If a payment gateway migrates its charge endpoint and redirects with 301/302, a strict client that preserves the method (many modern HTTP libraries do, breaking the old convention) will resend the POST — potentially double-charging. If a loose client instead drops it to GET, the charge silently never happens. Neither behavior is guaranteed by 301/302, which is precisely the danger: the outcome depends on the client, not the server's intent. 307/308 remove that ambiguity, and idempotency keys remove the remaining risk from client retries.

General rule for non-GET methods (POST, PUT, PATCH, DELETE): if you need the method preserved, use 307/308, never 301/302. Combine with an idempotency key on the write itself so that even a legitimate retry after a redirect can't double-apply.

05 Browser Behavior

On receiving 301 Location: /new, a browser updates the address bar to the new URL, issues the follow-up request automatically (invisible to the user beyond a possible flicker), and typically records only the final URL in history — the intermediate hop usually isn't a separate back-button stop.

The important system-design detail: browsers are allowed to cache the redirect mapping itself, separate from caching the eventual page content. Once a browser has cached a 301 from http://example.com to https://example.com, it may go straight to HTTPS on the next visit without ever issuing the HTTP request — no round trip to your server at all.

Visit 1:  http://example.com → 301 → https://example.com   (cached)
Visit 2:  browser rewrites to https://example.com internally, no HTTP hop

This is a double-edged sword: it's why 301 is the right tool for HTTP→HTTPS upgrades (fewer round trips over time), and it's exactly why a mistaken 301 is painful — some fraction of returning users will have it burned into their browser cache long after you've fixed the server, with no user-facing way to know that's happening. Redirect chains (A→B→C) and redirect loops (A→B→A) both show up here too — browsers cap the number of hops they'll follow (Chrome/Firefox: 20) and fail with an error rather than spin forever.

06 Caching Behavior

301 responses are heuristically cacheable under HTTP caching rules even without an explicit Cache-Control header — browsers, CDNs, and proxies are all permitted to store them and skip the origin on future requests. 302 responses are not cached by default; they require an explicit Cache-Control: max-age=... to become cacheable at all, and most real deployments don't add one, precisely because the whole point of a 302 is that it might change.

301 + Cache-Control: max-age=31536000, immutable
  → CDN edges, browsers, and proxies may serve this redirect
    for a year without touching your origin.

302 (no Cache-Control)
  → every hit re-executes the redirect logic at the origin.

ETag and Vary matter less for redirects themselves than for the destination resource, but they still apply if you explicitly opt a 302 into caching — e.g. Vary: Accept-Language for a geo/language redirect you're willing to cache per-locale.

THE OPERATIONAL TRAP

"What happens if I return a 301 and later want to change the destination?" — the honest answer is: it's expensive to undo. Browsers, corporate proxies, and CDN edges may have cached the old mapping for months. Practically: keep 301 TTLs bounded (days, not "forever," despite the RFC allowing indefinite heuristic caching) unless you're certain the move is truly final, and treat any 301 rollout as a one-way door.

07 SEO

Search engines use the 301/302 distinction as an explicit signal for what to do with ranking authority. A 301 tells the crawler to fold the old URL's backlinks, authority, and indexing history into the new URL and eventually drop the old one from the index. A 302 tells the crawler "keep the old URL as the canonical, indexed page; this destination is transient" — link equity stays put.

Permanent migration → 301

/blog/old-post
     │
     ▼
    301
     │
     ▼
/blog/new-post

Correct: rankings and backlink equity transfer to the new URL over time.

Temporary promotion → 302

/product
     │
     ▼
    302
     │
     ▼
/sale

Correct: /product stays the canonical, indexed page after the sale ends.

Using a 302 for what is actually a permanent migration is a common, costly mistake: the old URL keeps its indexing and the new one never accrues authority, so organic traffic to the new location stays artificially low indefinitely — this is a frequent root cause of "SEO traffic dropped after our redesign" incidents.

That said, SEO should not be the only reason to pick 301 vs 302. The correct choice is determined by whether the move is actually permanent; SEO behavior is a downstream consequence of getting that call right, not an independent lever to optimize. Choosing 301 purely to "get the SEO benefit" for something you might revert is how teams end up with the caching trap above.

09 Redirect vs Rewrite

These get conflated constantly, and the distinction is one of the most common interview clarifying-question moments.

Redirect

Client → GET /old
Server → 301 Location:/new
Client → GET /new (new request!)

Browser URL changes. A second, fully independent network round trip occurs. Visible to SEO crawlers as a URL change.

Internal rewrite

Client → GET /old
Server → internally serves /new's content
Client ← 200 OK (as /old)

Browser URL stays /old. One network round trip. Invisible to the client and to crawlers.

Performance-wise, a rewrite avoids the extra RTT entirely — it's resolved inside the web server or app layer (NGINX rewrite/try_files, Apache mod_rewrite without [R]). Use a rewrite when you want two URLs to serve identical content without exposing the mapping to the client (clean URLs in front of a query-string-based backend, for example). Use a redirect when the URL itself is the thing that changed and you want the client, caches, and search engines to know about it.

10 Redirect Chains & Loops

A → 301 → B → 301 → C → 200 OK

Every extra hop is a full round trip, so a two-hop chain roughly doubles pre-content latency versus a direct redirect, compounds on high-latency mobile networks, and complicates SEO crawlers' ability (and budget) to follow the chain to a final canonical URL. CDNs and browsers alike impose maximum hop counts and will hard-fail past them — which is also how redirect loops (A→B→A) get caught in practice, rather than through explicit server-side detection.

Prefer:  A → 301 → C → 200
Avoid:   A → 301 → B → 301 → C → 200

The fix is almost always the same: when you migrate a URL that's already the target of an existing redirect, update the original source to point straight at the new final destination instead of layering a new hop on top — treat your redirect map as a graph you flatten on every change, not an append-only log.

11 Redirects in System Design

Client → DNS → CDN → Load Balancer → API Gateway → Application Servers

Redirects can be generated at essentially every layer, and where you generate one is itself a design decision with real trade-offs:

LayerWhy generate hereAdvantageDisadvantage
CDN / edgeStatic, high-volume, geography-agnostic redirects (HTTP→HTTPS, retired domains)Lowest latency — never touches origin; scales infinitelyHarder to change quickly; propagation delay across edge nodes
Load balancerProtocol upgrades, host-based routing, maintenance modeCheap, centralized, no application code involvedLimited logic — usually rule-based, not content-aware
API gatewayAPI version deprecation, endpoint consolidationCentralized policy across many backend servicesAdds a hop for every request even non-redirected ones if misconfigured
Application serverBusiness-logic-dependent redirects (auth state, A/B assignment)Full context available (session, user, feature flags)Highest latency and cost per redirect — full app stack is invoked just to say "go elsewhere"
NGINX / reverse proxyURL restructuring, legacy path cleanupFast, configuration-driven, no code deploy neededConfig sprawl over time if not carefully maintained

General principle: push a redirect as far toward the edge as the decision logic allows. A redirect that only needs to know "is this HTTP or HTTPS" belongs at the load balancer or CDN, not at an application server three hops deeper into the stack.

12 CDN + Redirects

CDNs can cache redirect responses at the edge just like any other cacheable response, governed by the same Cache-Control/TTL rules. The distinction that matters operationally is edge-generated vs origin-generated redirects:

User in India
     │
     ▼
CDN Edge (Mumbai)
     │
     ▼
301 → https://example.com     ← never touched the origin at all

An edge-generated 301 (configured directly in the CDN, e.g. a "redirect rule" for HTTP→HTTPS or a retired hostname) answers in single-digit milliseconds worldwide and never costs the origin a request. An origin-generated redirect (the app server decides and returns the 301) still benefits from CDN caching on subsequent requests, but the first hit at each edge node pays the full round trip to origin.

Cache invalidation is the operational cost of this speed: once a redirect is cached globally across edge nodes, changing the destination requires an explicit purge/invalidation across every point of presence — and until that propagates, different users in different regions can be redirected to different places simultaneously. Bounded TTLs (rather than "cache forever") are the usual mitigation.

13 Load Balancer Use Cases

Client → HTTP Load Balancer → 301 → HTTPS

Terminating the HTTP→HTTPS upgrade at the load balancer means plaintext requests never reach an application server at all — cheaper, and it keeps "does this app speak HTTP" out of every service's concern entirely. It's also the natural place for:

  • Host-based routing combined with redirects for retired or merged hostnames.
  • Path-based routing where an old top-level path permanently maps to a new service.
  • Temporary migration redirects during a phased cutover, removed once the migration completes.
  • Maintenance mode — a single LB rule can 302 all traffic to a static status page without touching any backend deploys.
  • Region routing hints, though pure geographic routing is usually better handled at DNS/anycast (see §20).

14 Authentication & Login

User → GET /dashboard
     → 401 or redirect
     → 302 Location: /login?returnUrl=/dashboard
     → user authenticates
     → 302 Location: /dashboard

Login redirects are 302 (sometimes 303 after a POST-based login form, to avoid a resubmission prompt on refresh) because the destination is entirely session-dependent — it must never be cached, and it's never "permanent" in the HTTP sense. The returnUrl/next query parameter is what makes "log in, then land back where you were" work.

OPEN REDIRECT

Blindly trusting ?redirect=https://evil.com and 302-ing the authenticated session there is a classic open redirect vulnerability — attackers craft links through your trusted domain that ultimately land the user on a phishing page, benefiting from your domain's reputation right up to the final hop. Safe handling means validating that the return target is a relative path (or matches an explicit allow-list of your own hosts) before ever placing it in a Location header — never redirect to a raw, unvalidated absolute URL supplied by the client.

15 OAuth

Browser → Application
        → 302 → Authorization Server
        → user authenticates + consents
        → 302 → Application callback (with code/token)

Redirects aren't incidental to OAuth/OIDC — they're the entire transport mechanism for moving the browser (and only the browser, carrying the user's authenticated session) between the relying party and the identity provider without either party needing direct access to the other's session cookies. That's also precisely why callback URL validation is non-negotiable: an authorization server that redirects to an attacker-supplied callback hands over an authorization code or token to whoever controls that URL. Registered, exact-match redirect URIs (not prefix-matched, not wildcarded) are the standard mitigation.

It's worth being explicit about the difference between the browser-mediated 302s in the flow above and the server-to-server token exchange that follows — the application's backend calls the authorization server's token endpoint directly (no redirect, no browser involvement) to trade the authorization code for tokens. Conflating "redirect the browser" with "make a backend call" is a common source of confused OAuth implementations.

16 API Design

Should GET /v1/users redirect to /v2/users? Generally, no — or at least, not as the primary versioning strategy. Redirects assume a browser-like client that transparently follows 3xx responses, and a large share of API consumers don't behave that way:

  • Many SDKs and HTTP clients don't follow redirects by default for non-GET verbs, or require explicit opt-in.
  • A redirect silently adds a full extra round trip to every call — invisible latency that's hard to diagnose downstream.
  • Authorization headers are, by design and by browser security policy, not automatically forwarded across a cross-origin redirect in many client implementations — a redirected API call can arrive at the new host unauthenticated.
  • Retries, circuit breakers, and observability tooling built around "one request → one response" get harder to reason about when a single logical call is actually two.
  • Mobile and embedded clients often have stricter or non-configurable redirect-following behavior.

Compare the three real options:

ApproachWhat it isTrade-off
API redirect (3xx)Old endpoint returns a redirect to the new oneSimple to add, but breaks non-browser clients silently and adds latency to every call
API versioning/v1/ and /v2/ coexist; clients opt in explicitlyMost predictable; requires maintaining both versions during a deprecation window
Server-side routingGateway internally routes /users to whichever backend implementation is currentZero client-visible change, but hides breaking changes that clients may need to know about

When an endpoint is truly and permanently retired, 308 (method-preserving) is the least-bad redirect choice — but pairing it with clear deprecation headers (Deprecation, Sunset) and version negotiation is usually a better system than relying on 3xx as the migration mechanism itself.

18 Performance

Client → GET /old → 301 → GET /new → 200

Every redirect hop adds a full request/response cycle — DNS resolution (if the new host differs and isn't already resolved), a new TCP/TLS handshake (if the connection can't be reused, e.g. cross-origin), and the round-trip time itself. On a mobile network with 100–300ms RTT, a single avoidable redirect hop can add a noticeable, user-visible delay before any content starts loading — and that cost is paid on every uncached hit.

Same-origin redirects reuse the existing TLS connection and pay only the RTT cost; cross-origin redirects pay DNS + TLS + RTT stacked. A CDN-cached (or browser-cached) 301 pays none of this after the first hit — which is the concrete performance argument for making permanent redirects cacheable rather than dynamically computed on every request.

19 Redirects and Distributed Systems

User → Global Traffic Manager → Region A
                                    │
                          (incident) │
                                    ▼
                                Region B

Should a regional failover be implemented as an HTTP redirect? Generally no. An HTTP redirect requires the client to already have successfully reached Region A to be told to go to Region B — which is exactly backwards during an outage where Region A might be unreachable or slow in the first place. It also bakes a full extra round trip into every failover event, at the worst possible moment.

MechanismTrade-off
HTTP redirectClient-visible, cacheable, but requires reaching the failing region first — wrong tool for failover
DNS-based routingClient-transparent, but bounded by DNS TTL — propagation can take minutes even with low TTLs
Anycast / CDN routingNear-instant, network-layer rerouting with no client cooperation needed — best for latency-sensitive failover
Load-balancer routingFast within a region/data-center scope, but not inherently global

Blue-green deployments, canary releases, and active-active traffic shifting belong at the routing/load-balancer layer for the same reason: they need to be invisible to the client and reversible in milliseconds, neither of which an HTTP redirect — a client-cooperative, potentially-cached, extra-round-trip mechanism — is built for.

Use an HTTP redirect when the URL identity itself has changed and you want that reflected to the user, search engines, and bookmarks. Use DNS-based (or anycast/CDN) routing when the URL should stay exactly the same but the underlying destination — region, data center, deployment — needs to change transparently.

22 Troubleshooting Scenarios

Scenario 1 — Browsers keep hitting the old destination after the server config changed

What happened
Users still land on the retired page days after the redirect target was updated.
Root cause
The original redirect was a 301 with a long/implicit cache lifetime; browsers cached the old mapping.
Misused code
301 (cached too aggressively for a mapping that turned out to change)
Debug
Reproduce in an incognito window / with cache disabled; check Cache-Control on the original 301 response via browser devtools or curl -I.
Fix
Serve a fresh 301 to the correct destination; affected users self-heal once their local cache expires or is cleared — there's no server-side way to force it.
Prevent
Use bounded TTLs on permanent redirects until you're fully confident the mapping is final.

Scenario 2 — A POST unexpectedly becomes a GET after redirect

What happened
A form submission's side effect doesn't happen; the destination page loads fine but the data wasn't saved.
Root cause
The redirect used 302, and the client (browser or HTTP library) coerced the method to GET per legacy convention, dropping the body.
Misused code
302 (should have been 307, or 303 if a GET was actually intended)
Debug
Inspect the network tab for the redirected request's method; confirm the original was POST with a body.
Fix
Switch to 307 if the POST must be replayed as-is, or explicitly redesign as a POST/Redirect/GET (303) flow if the intent was always "show a result page."
Prevent
Never use 301/302 in front of non-idempotent writes; reserve them for GET-safe resources.

Scenario 3 — Redirect loop between HTTP and HTTPS

What happened
Users see "too many redirects" errors.
Root cause
TLS is terminated at the load balancer, which forwards plaintext HTTP to the app; the app also enforces HTTPS and redirects, unaware the LB already handled it.
Misused code
301 (correct code, wrong layer — duplicated logic)
Debug
Trace headers like X-Forwarded-Proto between LB and app; confirm the app is checking the wrong signal for "was this originally HTTPS."
Fix
Have the app trust X-Forwarded-Proto from a trusted LB instead of re-deriving scheme from the (already-downgraded) connection it received.
Prevent
Enforce HTTPS upgrade at exactly one layer, and document which layer owns it.

Scenario 4 — CDN keeps serving an old redirect

What happened
Origin was updated, but edge nodes globally still return the stale destination.
Root cause
The redirect was cached at the edge with a long TTL and no invalidation was issued after the change.
Misused code
301 (long TTL without an invalidation plan)
Debug
Compare response from origin directly (bypassing CDN) vs. through the CDN; check cache-status headers per edge POP.
Fix
Issue an explicit cache purge/invalidation across all edge nodes for the affected path.
Prevent
Bake invalidation into the redirect-change deploy process; don't rely solely on TTL expiry for corrections.

Scenario 5 — SEO traffic drops after a site migration

What happened
Organic search traffic falls sharply in the weeks after a redesign/domain move.
Root cause
Migration used 302s (or no redirects at all) for URLs that were actually permanent moves, so link equity never transferred.
Misused code
302 (should have been 301)
Debug
Crawl the old URL list and check response codes; confirm whether they 302, 404, or 301.
Fix
Convert the migration redirects to 301 and resubmit a sitemap to search engines.
Prevent
Treat "is this permanent" as the deciding question before any migration redirect ships, not an afterthought.

Scenario 6 — OAuth login redirects to an attacker-controlled domain

What happened
Users report being sent to a phishing page that looks like the login provider.
Root cause
The redirect_uri/callback validation was prefix-matched or wildcarded, letting an attacker register a look-alike subpath.
Misused code
302 (correct code, unvalidated destination)
Debug
Review the authorization server's redirect URI matching logic; look for wildcard or "starts with" matching instead of exact match.
Fix
Move to exact-match, pre-registered callback URLs only.
Prevent
Never allow wildcard or partial matching on OAuth redirect URIs, regardless of convenience during development.

Scenario 7 — An API client fails after an endpoint starts returning redirects

What happened
A backend service or SDK integration starts throwing errors or silently losing auth after an API endpoint was "helpfully" redirected to a new path.
Root cause
The client library doesn't follow redirects for non-GET requests by default, or strips the Authorization header across the (possibly cross-origin) hop.
Misused code
301/302 used as an API versioning strategy
Debug
Check the client library's redirect-following configuration and whether the failure correlates with non-GET calls specifically.
Fix
Support both old and new endpoints in parallel (real versioning) instead of relying on the client to follow a redirect correctly.
Prevent
Treat redirects as unsuitable for API contract changes; use explicit versioning and deprecation headers instead.

23 25 System Design Interview Questions

1. What is HTTP 301?
Expected: A permanent redirect status telling the client the resource has a new, definitive URL. Testing: Basic protocol literacy. Common mistake: Describing it as "an error." Strong answer: Ties it to caching and SEO consequences, not just the definition.
2. What is HTTP 302?
Expected: A temporary redirect; the original URL remains canonical. Testing: Same as above, contrast with 301. Common mistake: Treating 301/302 as interchangeable. Strong answer: Notes the historical "Found" naming and the ambiguity around method handling.
3. What's the difference between 301 and 302?
Expected: Permanence, caching default, and SEO signal all differ. Testing: Whether the candidate sees beyond "one says permanent, one doesn't." Common mistake: Only mentioning SEO. Strong answer: Covers caching, client behavior, and SEO together, and flags the method-preservation ambiguity unprompted.
4. When would you use 301?
Expected: Domain migrations, HTTP→HTTPS, permanent URL restructuring. Testing: Practical judgment. Common mistake: Suggesting it for anything reversible. Strong answer: Flags the "hard to undo due to caching" risk.
5. When would you use 302?
Expected: A/B tests, campaigns, maintenance pages, login flows. Testing: Same as above, inverse case. Common mistake: Using it for a migration "just to be safe" — this actually breaks SEO transfer. Strong answer: Connects the choice to what should stay canonical.
6. What is 307?
Expected: A temporary redirect that guarantees method and body preservation. Testing: Depth beyond 301/302. Common mistake: Confusing it with 303. Strong answer: Gives a concrete POST example.
7. What is 308?
Expected: A permanent redirect that guarantees method and body preservation — the 301 analog to 307. Testing: Full 3xx family knowledge. Common mistake: Not realizing it exists. Strong answer: Applies it to API endpoint migrations specifically.
8. Why do 307/308 exist?
Expected: To remove the ambiguity that 301/302 inherited from inconsistent early browser behavior around method coercion. Testing: Historical/spec awareness. Common mistake: "Because more codes are better." Strong answer: Explains the POST→GET convention that motivated them.
9. What's the difference between redirect and rewrite?
Expected: Redirect changes the client-visible URL and costs a round trip; rewrite is invisible and internal, one round trip. Testing: Whether the candidate conflates client-visible vs server-internal behavior. Common mistake: Saying they're "basically the same." Strong answer: Gives an NGINX example of each.
10. Can redirects be cached?
Expected: Yes — 301 is heuristically cacheable by default, 302 is not without explicit headers. Testing: Cache-control literacy. Common mistake: Assuming neither is cached without explicit headers. Strong answer: Distinguishes browser cache from CDN/proxy cache.
11. How does CDN caching affect redirects?
Expected: Edge-cached redirects avoid hitting origin but require explicit invalidation to update, risking stale global state. Testing: Distributed caching trade-offs. Common mistake: Ignoring the invalidation-propagation delay. Strong answer: Distinguishes edge-generated vs origin-generated redirects.
12. Why are redirect chains bad?
Expected: Compounding latency, SEO crawl-budget waste, operational complexity. Testing: Performance awareness. Common mistake: Only mentioning SEO. Strong answer: Quantifies the added RTT and proposes flattening the redirect graph.
13. How would you implement HTTP → HTTPS?
Expected: 301 at the load balancer/CDN edge, not the application layer. Testing: Layer placement judgment. Common mistake: Implementing it in application code, adding unnecessary latency. Strong answer: Notes browsers can skip the HTTP hop entirely once cached.
14. How would you migrate millions of URLs?
Expected: Bulk 301 mapping table, likely served from the edge/CDN for scale, with bounded TTLs and sitemap resubmission. Testing: Scale thinking. Common mistake: Assuming per-URL manual redirect rules. Strong answer: Discusses a lookup-table-backed redirect service (see §24).
15. How would you avoid redirect loops?
Expected: Careful ownership of upgrade logic at a single layer, hop-count limits, and testing the redirect graph for cycles before deploy. Testing: Operational rigor. Common mistake: Relying solely on the browser's hop cap as the safety net. Strong answer: Ties it to the LB/app duplicated-logic failure mode from Scenario 3.
16. How do redirects affect API clients?
Expected: Inconsistent following behavior across SDKs, dropped auth headers cross-origin, extra latency, complicated retries. Testing: Non-browser client awareness. Common mistake: Assuming API clients behave like browsers. Strong answer: Recommends versioning over redirects for APIs.
17. How do redirects interact with POST?
Expected: 301/302 historically risk method coercion to GET; 307/308 guarantee preservation. Testing: The GET/POST trap from §4. Common mistake: Assuming POST always survives a redirect. Strong answer: Brings up idempotency keys as a complementary safeguard.
18. How do redirects affect OAuth?
Expected: They're the core transport for moving the browser between parties; callback URL validation is critical. Testing: Security-aware protocol knowledge. Common mistake: Not mentioning open-redirect/callback risk. Strong answer: Distinguishes browser redirects from the server-to-server token exchange.
19. How would you design a global redirect service?
Expected: See the full design in §24 — edge-cached lookup table, replicated storage, invalidation pipeline. Testing: End-to-end system design synthesis. Common mistake: Designing it as a single-region database lookup. Strong answer: Reasons explicitly about consistency vs latency trade-offs.
20. Where should redirects be generated in a large-scale architecture?
Expected: As close to the edge as the required logic allows — see the layer table in §11. Testing: Layered-architecture judgment. Common mistake: Defaulting to "always in the application." Strong answer: Matches each redirect type to the cheapest layer capable of deciding it.
21. Should DNS or HTTP redirects handle regional failover?
Expected: DNS/anycast routing — HTTP redirects require reaching the failing region first. Testing: Failure-mode reasoning under distributed systems. Common mistake: Proposing an HTTP redirect for failover. Strong answer: Explains the chicken-and-egg problem explicitly.
22. What's an open redirect and why is it dangerous?
Expected: A redirect target influenced by user input without validation, enabling phishing via a trusted domain. Testing: Security fundamentals. Common mistake: Underestimating the impact ("it's just a redirect"). Strong answer: Proposes an allow-list/relative-path-only fix.
23. Why shouldn't APIs rely on redirects for versioning?
Expected: Inconsistent client behavior, dropped headers, added latency, complicated observability. Testing: API design maturity. Common mistake: Treating it as equivalent to browser navigation. Strong answer: Proposes explicit versioning + deprecation headers instead.
24. How would you debug "too many redirects"?
Expected: Trace the actual chain (curl -I in a loop, or browser devtools), look for duplicated upgrade logic across layers. Testing: Practical debugging skill. Common mistake: Guessing without tracing the real header chain. Strong answer: References the TLS-termination-at-LB failure mode.
25. How would you estimate capacity for a redirect service handling billions of requests/day?
Expected: Back-of-envelope QPS, cache-hit-ratio-adjusted origin load, storage/replication needs — see §25. Testing: Estimation rigor. Common mistake: Skipping peak-to-average ratios. Strong answer: Shows the math, not just a final number.

24 Design a Large-Scale Redirect Service

"Design a globally distributed URL redirect service capable of handling billions of redirects per day."

Requirements → Traffic estimation → Data model → Storage → Caching →
CDN → Routing → Redirect lookup → Consistency → Replication →
Cache invalidation → Failure handling → Monitoring → Scaling

Requirements

  • Billions of requests/day, global user base, sub-50ms redirect latency at p99.
  • Support both permanent (301/308) and temporary (302/307) mappings, plus custom domains for tenants.
  • Per-tenant redirect rules, click analytics, and abuse prevention (malicious/spam destinations).

Data model

redirect {
  short_key       : string (partition key)
  destination_url : string
  status_code     : int (301|302|307|308)
  owner_id        : string
  created_at, expires_at (nullable)
  active          : bool
}

Storage

A key-value store keyed by short_key (e.g. a partitioned/replicated KV store) is the natural fit — lookups are single-key, read-heavy, and don't need relational joins. Write volume (new/updated redirects) is orders of magnitude lower than read volume (redirect resolution), so the system should be optimized aggressively for reads.

Caching & CDN

Put a CDN edge cache in front of the lookup, keyed by short_key, with TTL matching the redirect's own permanence: long TTL (or edge-computed, e.g. Workers/Lambda@Edge) for 301/308, short-or-no-cache for 302/307. This is where the overwhelming majority of the "billions/day" traffic gets absorbed without ever reaching the origin KV store.

Routing

GET https://example.com/abc
      │
      ▼
CDN edge: cache hit? ── yes ──► 301 Location: https://newsite.com/page  (done, ~ms)
      │ no
      ▼
Origin lookup service → KV store fetch by "abc"
      │
      ▼
Build 301/302 response, populate edge cache per TTL policy
      │
      ▼
301/302 Location: https://newsite.com/page

Consistency & replication

Redirect mappings are a good fit for eventual consistency — a few seconds of staleness after a rule update is an acceptable trade for global low-latency reads. Multi-region replication of the KV store (active-active, async replication) keeps reads local to each region; writes propagate asynchronously and get pulled into each region's local cache/store.

Cache invalidation

On update, invalidate the specific short_key at all CDN edges (targeted purge, not a full flush) and let regional KV replicas converge on their normal replication lag. Because 301s are expected to be long-cached by clients as well, treat any change to an existing permanent mapping as an exceptional, audited operation.

Failure handling

If the origin lookup service is unreachable and the edge has no cached entry, fail toward a safe default (a branded "link not found" page) rather than a 5xx that a client might interpret as retriable in a way that hammers the origin.

25 Capacity Estimation

Assume 5 billion redirects/day as the target scale.

Average QPS   = 5,000,000,000 / 86,400 ≈ 58,000 req/s
Peak QPS      = average × peak factor (assume 4×) ≈ 230,000 req/s

Storage:
  Assume 500M active short_key → destination mappings
  ~300 bytes/record (key + URL + metadata)
  500,000,000 × 300B ≈ 150 GB raw
  ×3 replication factor ≈ 450 GB total

Cache:
  Hot-set assumption: 5% of keys drive 80% of traffic (Pareto)
  25M keys × 300B ≈ 7.5 GB per edge cache — comfortably fits in-memory

Bandwidth:
  Response size ≈ 300 bytes (headers + empty body)
  230,000 req/s × 300B ≈ 69 MB/s at peak — trivially small per edge node

Origin load (after CDN absorption):
  Assume 95% edge cache hit ratio → 5% falls through to origin
  230,000 × 0.05 ≈ 11,500 req/s to the origin lookup service at peak

Servers (origin lookup tier):
  Assume 2,000 req/s per instance sustainable
  11,500 / 2,000 ≈ 6 instances minimum, provision ~3× for redundancy/headroom ≈ 18

The headline takeaway: with a well-tuned edge cache hit ratio, the origin tier handles a small fraction of nominal "billions/day" traffic — the design problem is really "build a cache-friendly, highly-cacheable redirect layer," not "build a KV store that can do 230K QPS directly."

26 Observability

Metrics worth alerting on, not just graphing:

  • Redirect QPS, broken down by status code (301/302/303/307/308 rates) — a sudden shift in the ratio often signals a misconfiguration.
  • Redirect latency (p50/p95/p99), separated by cache hit vs origin fallthrough.
  • Redirect error rate (destination returns 4xx/5xx, or the redirect itself fails to resolve).
  • Detected redirect loops/excessive chain length.
  • CDN/edge cache hit ratio for redirect lookups specifically.
  • Destination failure rate — the new URL itself becoming unreachable.

Structured log fields per redirect event:

{
  "source_url": "...", "destination_url": "...",
  "status_code": 301, "timestamp": "...",
  "region": "ap-south-1", "user_agent": "...",
  "referrer": "...", "request_id": "..."
}
PRIVACY & CARDINALITY

Full URLs, referrers, and user agents are high-cardinality and can carry personally identifiable or sensitive data (session tokens embedded in query strings, for instance) — hash or truncate sensitive fields before long-term storage, apply retention limits, and be deliberate about which fields feed low-cardinality dashboards (status code, region) versus which stay in short-retention raw logs (full URL, request ID) for incident debugging only.

27 15 Common Interview Mistakes

  1. Treating 301 and 302 as interchangeable.They differ in caching default, SEO transfer, and client memory — picking the wrong one is a one-way door in production.
  2. Ignoring HTTP method semantics.301/302 don't guarantee method preservation; assuming a POST survives can silently break or duplicate writes.
  3. Forgetting caching entirely.A 301 without a TTL plan is effectively permanent in practice, regardless of server-side intent.
  4. Ignoring browser behavior.Browsers can skip the origin entirely after caching a 301 — "fixing the server" doesn't always fix the client.
  5. Using redirects where internal routing/rewrite is better.Adds an unnecessary client-visible round trip for something that should be invisible.
  6. Using HTTP redirects for DNS-level routing problems.Failover and geo-routing need to work before the origin is reachable — redirects can't do that.
  7. Ignoring redirect chains.Each hop compounds latency and complicates crawling; chains should be flattened, not layered.
  8. Ignoring redirect loops.Usually caused by duplicated upgrade logic across layers (e.g. LB and app both enforcing HTTPS).
  9. Ignoring OAuth callback security.Loose redirect URI matching is a direct path to token/code theft.
  10. Assuming all API clients behave like browsers.SDKs, mobile clients, and server-to-server calls often don't follow redirects the way a browser does.
  11. Ignoring CDN caching.Edge-cached redirects require explicit invalidation — TTL expiry alone isn't a fix plan.
  12. Using 301 for something temporary.Caches and search engines may adopt it as permanent long after you've reverted the server.
  13. Using 302 for a permanent migration.Link equity and indexing never transfer, quietly capping the new URL's organic traffic.
  14. Ignoring 307/308.Missing the method-preservation guarantee they provide is the single most common gap in an otherwise solid answer.
  15. Forgetting the additional network round trip.Every redirect hop is real, measurable latency — not a free abstraction.

The 60-second answer

"301 means the resource permanently moved — browsers and CDNs can cache that mapping and skip the old URL entirely, and search engines transfer ranking signal to the new URL. 302 means it's temporary — the original URL stays canonical, and nothing downstream is supposed to treat the new location as permanent. Neither code, historically, guarantees the request method survives the hop — many clients coerce POST into GET — which is why 307 and 308 exist: they're the method-preserving versions of 302 and 301 respectively. In system design terms, I pick 301/308 for actual permanent moves like domain migrations or HTTP-to-HTTPS, 302/307/303 for anything contextual or reversible like A/B tests or login flows, and I push the decision as far toward the edge — CDN or load balancer — as the required logic allows, since caching a redirect there is what lets it scale to billions of requests without the origin ever seeing most of the traffic."
