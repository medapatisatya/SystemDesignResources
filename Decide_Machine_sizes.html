4-Vector Sizing Framework Cheat Sheet

The 4-Vector Sizing Framework calculates server cluster sizes by isolating four key constraints: storage capacity, network bandwidth, RAM volume, and CPU/IOPS throughput. The final capacity planning size equals the maximum machine count required by any single resource vector.

Part 1: The Sizing Formulas & Core Logic

1. The Formulas

  • Storage Count (Nstorage):
    Total Data Volume (Data/Day × Retention Days) / Single Node SSD Capacity
  • Bandwidth Count (Nbandwidth):
    Peak Ingress or Egress Throughput (Gbps) / Single Node Network Interface Limit (Gbps)
  • RAM Count (Nram):
    Active Hot Working Set (e.g., 20% of Daily Unique Records) / Single Node Available Memory (RAM)
  • Throughput Count (Ncompute):
    Peak Read + Write Operations per Second (QPS) / Single Node Max Query Processing Limit

2. Golden Rules for Interviews

  • The Max Rule: Final Fleet Size = max(Nstorage, Nbandwidth, Nram, Ncompute)
  • Safety Headroom: Always add a 30% capacity buffer to the final count to absorb unexpected traffic spikes.
  • Asymmetric Pipes: Always evaluate Ingress vs. Egress network paths independently. Systems like video streaming or URL shorteners are heavily egress-bound.

Part 2: Cloud Instance Cheat Sheet

When sizing systems in design interviews, map your final vector bottlenecks directly to standard machine profiles or cloud tiers. Assume a baseline Standard Production Node (8 vCPUs, 32 GB RAM, 2 TB NVMe SSD, 15 Gbps network, 10,000 QPS limit) for generic calculations.

1. Baseline Configurations (General Purpose)

  • Standard Medium Worker Node: 4 vCPUs, 16 GB RAM, 12.5 Gbps network. Used for stateless web servers, small API services, and microservices.
  • Standard Large Worker Node: 8 vCPUs, 32 GB RAM, 15 Gbps network. Best for standard application logic layers and mid-size caching fleets.

Part 3: Concrete System Design Examples

These examples illustrate how different workloads force you to scale for a single specific bottleneck using our standard baseline node specifications.

Scenario A: The Network Bandwidth Bottleneck (Static Asset/URL Delivery)

System Requirements: 10 GB total storage, 45 Gbps peak egress throughput, 5 GB hot data, 15,000 read QPS.

  • Nstorage = 10 GB / 2,000 GB = 0.005 nodes
  • Nbandwidth = 45 Gbps / 15 Gbps = 3.0 nodes
  • Nram = 5 GB / 32 GB = 0.15 nodes
  • Ncompute = 15,000 QPS / 10,000 QPS = 1.5 nodes

Verdict: You must provision 3 nodes minimum (plus buffer). The network card is the single bottleneck. Data is fully duplicated across nodes, leaving hard drives completely empty.

Optimized Instance Choice: Network Optimized profile to drop required node count down to 1 machine via a 50 Gbps pipe.

Scenario B: The RAM / Memory Bottleneck (Session Store Cluster)

System Requirements: 100 GB total storage, 5 Gbps throughput, 120 GB active hot session data, 8,000 QPS.

  • Nstorage = 100 GB / 2,000 GB = 0.05 nodes
  • Nbandwidth = 5 Gbps / 15 Gbps = 0.33 nodes
  • Nram = 120 GB / 32 GB = 3.75 nodes → 4 nodes
  • Ncompute = 8,000 QPS / 10,000 QPS = 0.8 nodes

Verdict: You must provision 4 nodes minimum. CPU, disk, and network interfaces remain highly underutilized, but the fleet size is entirely forced by the requirement to hold live states in memory.

Optimized Instance Choice: Memory Optimized profile (e.g., 64 GB RAM per node), lowering node requirements down to 2 machines.

Scenario C: The Storage Bottleneck (Compliance Log Aggregator)

System Requirements: 12 TB total storage (due to long retention), 3 Gbps network throughput, 20 GB active hot data, 2,000 write QPS.

  • Nstorage = 12 TB / 2 TB = 6.0 nodes
  • Nbandwidth = 3 Gbps / 15 Gbps = 0.2 nodes
  • Nram = 20 GB / 32 GB = 0.62 nodes
