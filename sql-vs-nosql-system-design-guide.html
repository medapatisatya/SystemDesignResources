SQL vs NoSQL — The System Design Interview Playbook

Framework to hold in your head for every question in this guide: Requirements → Access Patterns → Data Model → Database Choice → Scaling Strategy → Trade-offs

1. Fundamentals

What is SQL (Relational)?

A relational database stores data in tables (rows × columns), where each table has a fixed schema (defined columns and types). Relationships between tables are expressed via foreign keys, and you query across tables using joins. Examples: PostgreSQL, MySQL, SQL Server, Oracle.

What is NoSQL (Non-relational)?

"NoSQL" is an umbrella term for databases that don't use the rigid row/column/join model. They optimize for flexible schemas, horizontal scale, and specific access patterns instead of general-purpose querying. Examples: MongoDB (document), Redis/DynamoDB (key-value), Cassandra (wide-column), Neo4j (graph).

Relational vs Non-relational, in plain English

  • Relational = "I have well-structured entities with clear relationships, and I need to ask complex, ad-hoc questions across them, with strong guarantees on correctness." Think spreadsheets that reference each other.
  • Non-relational = "I know exactly how I'll access this data (usually by a key), I need it to scale to huge volume/velocity, and I can relax some consistency/structure guarantees to get that scale and speed."

2. SQL Deep Dive

ACID transactions — Atomicity, Consistency, Isolation, Durability. A transaction either fully happens or doesn't happen at all, even across multiple tables/rows. This is why banking uses SQL: "debit account A, credit account B" must be all-or-nothing.

Strong consistency — Every read sees the latest committed write. No stale data (within a single node/cluster using synchronous replication).

Joins — Combining rows from multiple tables based on a related column (e.g., orders JOIN users ON orders.user_id = users.id). This is what lets you normalize data without duplicating it.

Indexing — A B-tree (or similar) structure built on a column to make lookups on that column fast (O(log n) instead of full table scan). Cost: extra storage, slower writes (index must be updated).

Normalization vs denormalization - Normalization: splitting data to eliminate redundancy (3NF etc.) — a users table and a separate orders table, linked by user_id. Pro: no duplicate/inconsistent data. Con: requires joins. - Denormalization: duplicating data to avoid joins (e.g., storing user_name directly in the orders row). Pro: faster reads. Con: risk of stale/inconsistent copies.

Foreign keys and constraints — Foreign keys enforce referential integrity (you can't insert an order for a user that doesn't exist). Constraints (UNIQUE, NOT NULL, CHECK) enforce data correctness at the DB layer.

Vertical vs horizontal scaling - Vertical: bigger machine (more CPU/RAM/disk). Simple, but has a ceiling and single point of failure. - Horizontal: more machines. SQL databases are historically harder to scale this way because joins/transactions across shards are complex.

Read replicas — Copies of the primary database that serve read traffic, replicated asynchronously (or semi-synchronously). Scales reads, not writes. Introduces replication lag (eventual consistency on replicas).

Sharding — Splitting a single logical table across multiple physical databases by a shard key (e.g., user_id % N). Scales writes too, but joins/transactions across shards become expensive or impossible, and re-sharding is operationally painful.

When SQL becomes a bottleneck - Write throughput exceeds what a single primary can handle, and sharding is impractical for your query patterns. - You need massive horizontal scale with very high write volume (e.g., billions of events/day). - Your data is naturally schema-less or highly variable in shape. - You're doing simple key-based lookups at extreme scale and paying join/relational overhead for nothing.

3. NoSQL Deep Dive

The four major types

Key-value (Redis, DynamoDB, Memcached) - Model: key -> opaque value. No querying by value content (usually). - Best for: caching, session storage, feature flags, rate limiting, simple lookups.

Document (MongoDB, Couchbase, Firestore) - Model: JSON-like documents, can be nested/embedded, flexible schema. - Best for: content that's naturally hierarchical (user profile + preferences + addresses), rapidly evolving schemas, product catalogs.

Wide-column (Cassandra, HBase, Bigtable, ScyllaDB) - Model: rows keyed by a partition key + clustering columns; each partition can have different columns; optimized for range scans within a partition. - Best for: time-series data, huge write volumes, IoT telemetry, messaging history.

Graph (Neo4j, Amazon Neptune) - Model: nodes + edges + properties, optimized for traversals. - Best for: social graphs, recommendation engines, fraud-ring detection.

Core concepts

Eventual consistency — After a write, reads might momentarily return stale data, but all replicas converge to the same value eventually (usually within milliseconds to seconds).

BASE — Basically Available, Soft state, Eventually consistent. The NoSQL counter-philosophy to ACID: favor availability and partition tolerance over immediate consistency.

Horizontal scaling — NoSQL databases are designed from the ground up to add nodes and automatically redistribute data (via consistent hashing typically), unlike bolted-on SQL sharding.

Partitioning — Data is split across nodes based on a partition/hash key. Good partition key design = evenly distributed load, no hot spots.

Replication — Data is copied across multiple nodes/regions for durability and availability, often with tunable consistency (e.g., DynamoDB's eventually-consistent vs strongly-consistent reads).

High availability — No single point of failure; the system keeps serving reads/writes even if some nodes go down, at the cost of consistency guarantees during a partition (per CAP).

Denormalization is the default in NoSQL — Because joins are expensive or unsupported at scale, you model data the way you'll read it, duplicating data across documents/rows as needed.

CAP theorem — During a network partition, you must choose between Consistency and Availability (Partition tolerance is assumed for any distributed system). SQL systems typically lean CP (or single-node, sidestepping the issue); most NoSQL systems let you tune between CP and AP (Cassandra/DynamoDB default AP-leaning, MongoDB defaults more CP-leaning per replica set).

When NoSQL is a better fit - Access pattern is simple and known ahead of time (get-by-key), and scale is massive. - Write volume is extremely high (telemetry, logs, events). - Schema will change frequently and you don't want migrations. - You need multi-region, always-on availability more than you need instant consistency. - Data is naturally hierarchical/document-shaped, or naturally graph-shaped.

5. System Design Examples (the most important section)

For each: Requirements → Access Patterns → Data Model → Choice → Why → Alternatives → Scaling → 10x/100x

A. E-commerce System

Requirements: Users, products, orders, payments, inventory, cart — correctness matters a lot (money, stock counts).

Access patterns: Get product by ID/category (high read), place order (write, must be transactional with inventory decrement), view order history (by user), search products (full-text/filter).

Data model: Relational core — users, products, orders, order_items, payments, inventory tables with foreign keys.

Choice: PostgreSQL/MySQL for users/orders/payments/inventory. Redis for cart (ephemeral, fast). Elasticsearch for product search.

Why: Orders + payments + inventory need ACID — you cannot allow an order to be placed against out-of-stock inventory, or a payment to be double-charged. That's a textbook transaction (BEGIN; decrement inventory; create order; charge payment; COMMIT;). Product catalog browsing is read-heavy and can be served via cache/search index, but the source of truth for stock/orders stays relational.

Alternatives considered: Pure NoSQL (MongoDB) for everything — rejected because multi-document transactions across orders/inventory/payments are harder to reason about and historically weaker (even though modern MongoDB supports multi-doc transactions, it's not its strength).

Scaling strategy: Read replicas for product/browse queries. Cache hot product data in Redis. Move cart to Redis entirely (no need for durability guarantees of SQL). Shard orders by user_id or region once write volume outgrows a single primary.

10x/100x: At 10x, add caching layers and read replicas. At 100x, shard the orders DB by region/user, move inventory to an event-driven model (reserve stock via a message queue to avoid lock contention), and consider CQRS (separate write model in SQL, read model denormalized in a NoSQL/search store).

B. Instagram-like System

Requirements: Users, posts, likes, comments, followers, personalized feed generation at massive read scale.

Access patterns: Fetch a user's feed (fan-out read, extremely frequent), post a photo (write), like/comment (very high write volume, low complexity per write), follower/following lookups.

Data model: User and post metadata can be relational-ish, but likes/comments/feed are extreme write-volume, simple-shape data.

Choice: PostgreSQL/MySQL for core user/post metadata. Cassandra or DynamoDB for likes, comments, and the feed/timeline itself. Redis for feed caching and hot counters (like counts). Graph DB (optional) for follow-recommendation ("people you may know").

Why: A feed is fundamentally a "get me the last N items for this partition key (user_id)" query at massive scale — exactly what wide-column/key-value stores are built for. Likes/comments have no need for joins and are enormous in write volume; relational DBs would buckle under that write load with row-lock contention. Follower graphs at "who follows whom, mutual friends" scale benefit from graph traversal, though many systems fake this with adjacency tables in NoSQL for cost reasons.

Alternatives considered: Pure SQL — rejected past a certain scale because of write-heavy like/comment tables and feed fan-out queries that don't parallelize well with joins. Pure NoSQL for user profiles — rejected because user account data benefits from strong consistency and relational integrity (email uniqueness, etc.) at a scale where it's not the bottleneck anyway.

Scaling strategy: Fan-out-on-write (precompute each follower's feed on new post — good for users with few followers) vs fan-out-on-read (compute feed at request time — needed for celebrities with millions of followers) — most real systems use a hybrid. Cache feeds in Redis. Partition likes/comments by post_id.

10x/100x: At 100x scale, fan-out-on-write becomes infeasible for celebrity accounts (writing to millions of feeds per post) — you switch to hybrid fan-out and cache aggressively. Shard wide-column stores by user_id/post_id to keep partitions from getting too hot.

C. URL Shortener

Requirements: Map short code → long URL. Extremely high read:write ratio (reads dominate massively). Low-latency lookups. Modest write complexity (just generate a unique code and store it).

Access patterns: GET /{shortcode} — pure key lookup, needs to be sub-millisecond, at huge QPS. Write is infrequent by comparison.

Data model: Trivial key-value: shortcode -> long_url (+ metadata: created_at, expiry, click count).

Choice: Key-value store — DynamoDB or Redis (with a durable KV store like DynamoDB as source of truth, Redis as a cache in front).

Why: There's no relational structure here at all — no joins, no transactions across entities. It's the purest possible key-value access pattern, and it needs to scale reads horizontally and cheaply. Using SQL here would work functionally but adds unnecessary overhead (schema, joins you'll never use) without extra benefit.

Alternatives considered: SQL with an indexed shortcode column — perfectly workable at moderate scale, and a fine interview answer if you scale it correctly (read replicas + cache), but interviewers usually want you to recognize this is the canonical key-value use case.

Scaling strategy: Cache aggressively (Redis/CDN) since reads are the bottleneck. Use a distributed ID generator (e.g., base62 counter, or Snowflake-style ID) to avoid collisions when writing at scale.

10x/100x: At 100x, the cache layer does almost all the work (cache hit rate >99%), and you push cache to the edge (CDN) since redirects are effectively static once created.

D. Uber-like Ride-hailing System

Requirements: Drivers, riders, real-time location updates (very high write frequency, small payloads), nearby-driver queries (geospatial), trip lifecycle, payments.

Access patterns: "Find nearby drivers" (geospatial range query, needs to be fast and fresh), continuous location pings (huge write volume, ephemeral — old locations don't matter), trip state transitions (needs consistency), payment settlement (needs ACID).

Data model: Location data is ephemeral/high-velocity — not a good fit for a relational table. Trips/payments/accounts are transactional.

Choice: Redis (with geospatial commands) or a specialized geo-index for live driver locations. Cassandra/DynamoDB for trip history/events at scale. PostgreSQL/MySQL for accounts, trip billing, payments.

Why: Live location is write-extreme and read-latency-critical, but doesn't need durability (a driver's location from 10 seconds ago is worthless) — perfect for an in-memory geospatial store. Payments and account balances need ACID guarantees, so they stay relational. Trip history at scale (every trip, every event) is high volume with simple access patterns (by trip_id, by driver_id) — a good wide-column/NoSQL fit.

Alternatives considered: Storing live location in SQL — rejected because the write rate (potentially every few seconds per active driver, across millions of drivers) would overwhelm a relational primary, and the data has no need for the durability/consistency SQL provides.

Scaling strategy: Geo-shard the location store by city/region (a driver in Hyderabad never needs to be matched against a rider in Delhi). Use read replicas/sharding for the payments DB partitioned by region.

10x/100x: At 100x, location updates might move to a streaming pipeline (Kafka) feeding regional in-memory geo-indexes, so no single store has to absorb global write load.

E. Chat / Messaging System

Requirements: 1:1 and group messages, message history, online/offline presence, delivery guarantees.

Access patterns: "Get last N messages in this conversation" (range query by conversation_id, time-ordered), send message (write, needs to be fast and durable), presence status (very high write frequency, ephemeral, eventually consistent is fine).

Data model: Messages are naturally partitioned by conversation_id with a time-ordered clustering key — the classic wide-column shape.

Choice: Cassandra or DynamoDB for message storage (partition key = conversation_id, clustering key = timestamp). Redis for presence/online status and for pub-sub delivery to connected clients. Possibly PostgreSQL for user accounts and group/conversation metadata.

Why: Message history access is always "give me messages for this conversation, most recent first" — no joins needed, extremely high write volume across millions of conversations, and it needs to scale horizontally without hot spots (partitioning by conversation_id achieves this). Presence status changes constantly and staleness of a few seconds is acceptable — ideal for an in-memory/eventually-consistent store.

Alternatives considered: SQL for messages — works at moderate scale (many real chat systems started this way), but write volume and required horizontal scalability push toward wide-column stores as the system grows.

Scaling strategy: Partition messages by conversation_id (with occasional bucketing by time window to avoid unbounded partition growth for very long-lived group chats). Use a message queue (Kafka) to decouple message ingestion from fan-out delivery to online clients.

10x/100x: At 100x, watch for "hot partition" problems in massive group chats (millions of members) — you may need to bucket messages by time windows within the partition key, and separate the "delivery" fan-out problem (like Instagram's feed fan-out) from the "durable storage" problem.

F. Banking / Payment System

Requirements: Accounts, transactions, balances, transfers, audit history — correctness and auditability are non-negotiable; money cannot be created or destroyed by a bug.

Access patterns: Transfer funds (must be atomic across two accounts), get balance (must be strongly consistent, no stale reads), audit trail queries (historical, can be less latency-sensitive).

Data model: Purely relational — accounts, transactions, ledger_entries, with strict foreign keys and constraints.

Choice: PostgreSQL/MySQL, full stop, for the core ledger. Possibly a separate NoSQL/analytics store for read-only reporting/audit dashboards fed asynchronously.

Why: This is the canonical ACID use case. A transfer is "debit account A, credit account B" and must never partially apply — that's exactly what SQL transactions guarantee. Eventual consistency is unacceptable here: showing a stale balance, or allowing a double-spend during a network partition, is a business-ending bug, not a UX inconvenience.

Alternatives considered: NoSQL for scale — generally rejected for the core ledger. Even the largest banks and fintechs (many built on distributed SQL like Google Spanner or CockroachDB) prioritize strong consistency; they achieve scale via horizontally-scalable SQL databases with distributed consensus (Spanner, CockroachDB, YugabyteDB) rather than giving up ACID.

Scaling strategy: Vertical scaling first; then read replicas for reporting; then a distributed SQL system (Spanner/CockroachDB) if true horizontal write scale is needed, since it preserves ACID across shards via consensus protocols (Paxos/Raft).

10x/100x: At high scale, most banks don't move to eventual-consistency NoSQL — they move to distributed SQL to keep ACID while scaling horizontally. This is a key interview insight: scale ≠ automatically go NoSQL.

6. Hybrid Architecture (Polyglot Persistence)

Real large-scale systems almost never use one database. Example composition:

                     ┌─────────────┐
   Client  ────────► │   API layer  │
                     └──────┬──────┘
                            │
        ┌───────────────────┼───────────────────────┐
        ▼                   ▼                        ▼
 ┌──────────────┐   ┌───────────────┐        ┌────────────────┐
 │ PostgreSQL    │   │ Redis         │        │ Elasticsearch    │
 │ users/orders/ │   │ cache/session/│        │ search/discovery │
 │ payments      │   │ rate limiting │        └────────────────┘
 └──────────────┘   └───────────────┘
        │
        ▼
 ┌──────────────┐        ┌────────────────┐
 │ Kafka         │───────►│ Cassandra/      │
 │ event stream  │        │ DynamoDB        │
 │               │        │ (high-scale     │
 │               │        │ access patterns)│
 └──────────────┘        └────────────────┘

Why multiple databases beats one database for everything: Each data access pattern has different requirements — some need ACID (payments), some need blazing key lookups (sessions), some need full-text search (product/content search), some need to absorb huge write volume cheaply (event logs, activity feeds). Forcing all of these into a single database means you either over-engineer the simple cases (paying SQL's overhead for a cache) or under-serve the hard cases (trying to do full-text search or huge-scale writes in a relational table). The cost is added operational complexity (more systems to run, keep in sync, and reason about) — which is why you only split when the access-pattern differences genuinely justify it, not by default.

7. Decision Framework — "If X, then Y, because Z"

If your requirement is... Consider... Because...
Multi-entity ACID transactions (money, inventory) SQL (or distributed SQL for scale) Only relational engines guarantee atomicity across multiple rows/tables by default
Complex ad-hoc queries/joins across entities SQL Query flexibility is SQL's core strength
Simple, known access pattern (get-by-key) at huge scale Key-value / wide-column No need to pay for relational overhead you'll never use
Extremely high write volume, simple shape (logs, telemetry, messages) Wide-column (Cassandra/DynamoDB) Built for horizontal write scaling via partitioning
Flexible/evolving schema, hierarchical data Document store (MongoDB) No migrations needed; natural JSON mapping
Relationship-heavy traversal queries (friend-of-friend) Graph DB Traversals are native and fast, vs recursive joins in SQL
Sub-millisecond lookups, ephemeral data Redis / in-memory KV In-memory access, no durability overhead
Global, always-on availability more important than instant consistency AP-leaning NoSQL (Cassandra/DynamoDB) CAP tradeoff favors availability under partition
Strong consistency is non-negotiable SQL or CP-leaning NoSQL (MongoDB w/ majority writes) Guarantees no stale reads
Full-text search / fuzzy matching Elasticsearch (alongside your primary DB) Purpose-built inverted indexes

Questions to ask yourself in the interview

  1. Do I need multi-row/multi-table ACID transactions?
  2. Do I need joins, or is my access pattern always "by key"?
  3. What are my read/write ratios and volumes?
  4. What's the expected scale (current and 10x/100x)?
  5. Do I need strong consistency, or can I tolerate eventual consistency?
  6. Is my data naturally relational (fixed structure, clear entities) or naturally hierarchical/graph-shaped?
  7. How often will the schema change?
  8. What will my partition/shard key be, and will it distribute load evenly?
  9. What's my latency requirement (single-digit ms? sub-second is fine?)?
  10. Is this data the "source of truth" (needs durability/correctness) or derived/cache-able (can be rebuilt)?

Answers

  1. Banking balances/transfers → SQL. Needs ACID, strong consistency, and auditability; money bugs are unacceptable.
  2. Social feed → NoSQL (wide-column/KV) + cache. Massive read fan-out, simple per-user partition access pattern, denormalized for speed.
  3. Product catalog → Document store (or SQL with a search index). Schema varies by product category; read-heavy; often paired with Elasticsearch for search.
  4. Inventory counts → SQL. Needs strong consistency and often atomic decrement-on-purchase to avoid overselling.
  5. Analytics/BI → Columnar/OLAP store (e.g., Redshift, BigQuery, Snowflake) — technically a specialized SQL-family system, not transactional SQL or typical NoSQL; optimized for large aggregate scans, not row lookups.
  6. Logging → NoSQL (wide-column) or specialized log store (Elasticsearch/Kafka+storage). Extreme write volume, simple append-only pattern, rarely needs joins.
  7. Chat messages → NoSQL (wide-column), partitioned by conversation_id. High write volume, time-ordered range reads, no joins needed.
  8. Leaderboard → In-memory KV with sorted sets (Redis). Needs fast ranked reads/writes; Redis sorted sets are purpose-built for this.
  9. Payment processing/ledger → SQL. Same reasoning as banking — ACID is mandatory.
  10. IoT telemetry → Wide-column (Cassandra/Timeseries DB). Enormous write throughput, simple time-series access pattern.
  11. Full-text search → Elasticsearch (alongside a primary DB of record). Purpose-built inverted index; not a fit for either plain SQL or plain NoSQL.
  12. Session storage → Key-value (Redis). Simple key lookup, ephemeral, needs to be extremely fast.
  13. GPS location tracking → In-memory geospatial store (Redis) or specialized geo-index. High write frequency, ephemeral data, needs geospatial range queries.
  14. Recommendation engine → Graph DB (for relationship-based recs) or NoSQL feature store (for ML-based recs). Depends on whether recommendations come from graph traversal or ML embeddings.
  15. Order management → SQL. Orders touch inventory, payments, and users — needs transactional integrity, though very large scale may pair it with an event-driven/CQRS pattern.

9. Common Mistakes Candidates Make

  • "NoSQL is always faster." False in general — it's faster for the access patterns it's designed for (key lookups, high write volume). For complex queries needing joins/aggregation, a well-indexed SQL database easily beats forcing that logic into application-side NoSQL joins.
  • "SQL cannot scale horizontally." False — it's harder, not impossible. Sharding, read replicas, and modern distributed SQL (Spanner, CockroachDB, Vitess for MySQL) all scale SQL horizontally, sometimes while preserving ACID.
  • "NoSQL means no schema." Misleading — most NoSQL systems have an implicit schema enforced at the application layer, or partial schema validation (e.g., MongoDB schema validation rules). "Schema-flexible," not "schema-free."
  • "Eventual consistency is always bad." False — for many use cases (likes, view counts, presence status), a few seconds of staleness is completely invisible to the user and a fine trade for availability/scale.
  • Choosing MongoDB/Cassandra/DynamoDB without considering access patterns. In wide-column/NoSQL systems, your partition key design is your query design — picking the wrong one means expensive scans or hot partitions. This should always be explicitly discussed in an interview.
  • Choosing SQL just because the data "looks" relational. Just because entities have relationships doesn't mean your access pattern needs joins at query time — sometimes denormalizing and using NoSQL is the better engineering trade-off even for relational-looking data (e.g., Instagram posts/comments).
  • Choosing NoSQL just because "the system needs to scale." Scale alone doesn't dictate NoSQL — distributed SQL exists precisely to scale while keeping ACID, and many "needs to scale" systems have transactional cores that shouldn't be denormalized just for throughput's sake.

10 Rules of Thumb

  1. Default to SQL when in doubt — it's the safer general-purpose choice.
  2. If money/inventory/anything "cannot be wrong" is involved, use SQL/ACID.
  3. If your access pattern is 100% "get by key," NoSQL key-value is usually cheaper and faster.
  4. Design your partition key before you pick your NoSQL database — it determines everything.
  5. Cache aggressively; caching solves more scaling problems than switching databases does.
  6. Read replicas solve read scale; sharding solves write scale; know which problem you actually have.
  7. "Eventually consistent" is fine for anything a user wouldn't notice being a few seconds stale.
  8. Polyglot persistence (multiple DBs) is normal and expected at scale — don't force one DB to do everything.
  9. Search is its own problem — reach for Elasticsearch, don't fake full-text search in SQL or NoSQL.
  10. Always state trade-offs out loud in an interview — the "why," not just the "what," is what's being graded.

Common Database Choices Cheat List

  • PostgreSQL/MySQL — transactional core: users, orders, payments, inventory.
  • Redis — cache, sessions, rate limiting, leaderboards, live geospatial data.
  • MongoDB — flexible/evolving schemas, content/catalog-like data.
  • Cassandra/DynamoDB — massive write volume, simple access pattern, feeds, messages, telemetry.
  • Neo4j — social graphs, fraud detection, recommendation traversal.
  • Elasticsearch — full-text search, log search/analytics.
  • Kafka — event streaming/decoupling, not a database but often part of the architecture.
  • Spanner/CockroachDB — need ACID and horizontal write scale simultaneously.

Sample 2-Minute Interview Answer

"For this system, I looked at the access patterns first rather than jumping to a database. The core entities — orders, payments, inventory — have hard correctness requirements: if I decrement stock and create an order, those need to happen atomically, and I can't tolerate a stale inventory count causing an overselling bug. That's a textbook case for ACID transactions, so I chose PostgreSQL as the source of truth for that data.

On the other hand, the shopping cart and product search have completely different requirements — carts are ephemeral and don't need durability guarantees, so I'd put those in Redis for speed, and product search needs full-text/fuzzy matching that relational databases aren't built for, so I'd add Elasticsearch fed asynchronously from the primary database.

I considered putting everything in a single NoSQL store for simplicity, but that would mean either giving up transactional guarantees on money-related operations, or fighting the database to get joins/consistency it wasn't designed for. So instead I went with a polyglot approach: SQL for the transactional core, and purpose-built stores for the access patterns that need to scale independently. As traffic grows, I'd scale the SQL layer with read replicas first, then shard by user/region if write volume demands it, while the cache and search layers scale horizontally by design."
