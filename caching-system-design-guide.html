Caching for System Design Interviews — Complete Guide

Before anything else, lock in one mental model. These four things are not competitors — they answer different questions:

Question Answer category Examples
Where does caching happen? Cache location Browser, CDN, reverse proxy, app-local, distributed, DB
What tool implements it? Cache technology Redis, Memcached, Caffeine, Cloudflare, Varnish
How does the app talk to the cache? Caching pattern / mechanism Cache-aside, read-through, write-through, write-back
When do entries leave? Eviction / invalidation strategy LRU, LFU, TTL, event-driven invalidation

An interviewer is testing whether you can compose these four independently. "Redis vs LRU" is a nonsense comparison (technology vs eviction policy). "CDN vs cache-aside" is a nonsense comparison (location vs pattern). Keep them in separate mental buckets throughout.

1. Caching Fundamentals

What is a cache? A small, fast storage layer that sits between a consumer and a slower source of truth, holding copies of data so repeat access is cheap.

Why cache? - Reduce latency (memory access ~100ns vs disk/DB round trip ~1–10ms+) - Reduce load on the source of truth (database, upstream service) - Reduce cost (fewer expensive compute/DB operations, less bandwidth) - Improve availability (serve stale-but-available data when the source is down)

Core vocabulary - Cache hit: requested data found in cache. - Cache miss: not found; must fetch from source. - Hit ratio: hits / (hits + misses). The single most important cache health metric. - Cache latency: time to read/write the cache itself (should be far lower than the source). - Cache capacity: how much data fits (RAM-bound, forces eviction decisions). - TTL (time to live): how long an entry is considered valid before automatic expiry. - Cache invalidation: deliberately removing/updating an entry before its TTL, because the source changed. - Freshness vs performance: the central tension in every caching design — longer TTL = more speed and DB protection, but more risk of stale data. - Why caching reduces DB load: every hit is a request the DB never sees; at scale, a 10-point improvement in hit ratio can remove millions of DB queries a day (see Section 17 math).

Basic flow

Client → API Server → Cache → Database
  • Cache hit: API server checks cache, finds data, returns immediately. DB untouched.
  • Cache miss: API server checks cache, nothing there, queries DB, returns result to client, and (in cache-aside) writes result into cache for next time.
  • Cache failure: cache is down/unreachable. Well-designed systems fail open to the DB (slower, but system stays up) rather than fail closed (return errors). More on this in Section 16.

2. Where Caching Happens (Cache Locations)

Think of this as a pipeline from the user's browser to the disk. Caching can be inserted at almost every hop, and each layer caches a different kind of data for a different reason.

Client-side / Browser cache

  • HTTP caching via Cache-Control, ETag, Last-Modified headers — browser stores static assets, avoids re-downloading.
  • LocalStorage/SessionStorage — app-controlled key-value storage in the browser, useful for user preferences, draft form state, auth tokens (with care), not for shared/sensitive data.
  • Fastest possible cache — zero network hop — but only benefits a single user's single device.

CDN / Edge cache

Examples: Cloudflare, Amazon CloudFront, Fastly. - Caches content geographically close to the user, at edge points of presence. - Best for: static assets (images, video, CSS/JS, fonts), and increasingly cacheable API responses (public, non-personalized, e.g., a product catalog page). - Not suitable for: personalized or highly dynamic data (a user's private dashboard), unless carefully scoped per-user with cache keys.

Reverse proxy cache

Examples: NGINX, Varnish. - Sits in front of the application servers, inside your infrastructure (not geographically distributed like a CDN). - Caches full HTTP responses close to your compute, cutting out application/DB work for identical requests. - Fits between load balancer and app servers:

Client → NGINX/Varnish → Application → Database
  • Useful when many requests are identical and cacheable at the HTTP level (e.g., public blog pages, category listings) without needing global edge distribution.

Application / local (in-process) cache

Examples: Caffeine (Java), Guava Cache, Ehcache. - Lives in the memory of a single application instance. - Extremely fast (no network hop at all — nanoseconds). - Use local cache when: data is read very frequently, is small, tolerates slight staleness across instances, and per-instance duplication is acceptable (e.g., feature flags, config, small reference/lookup tables, compiled regex, rarely-changing metadata). - Downside: if you have N app servers, you have N independent copies — no shared state, and invalidating one instance's cache doesn't invalidate the others (see Section 2's Caffeine problem below).

Distributed cache

Examples: Redis, Memcached, Amazon ElastiCache, Amazon MemoryDB, Google Cloud Memorystore, Azure Cache for Redis. - A separate, shared service that all app instances talk to over the network. - One copy of the data, visible to every app server — solves the "10 servers, 10 different answers" consistency problem that local caches have. - Costs a network round trip (still far faster than DB), but buys consistency and much larger effective capacity (scales independently of app servers).

Database-level caching

  • Query/result caching: DB caches results of repeated queries (mostly deprecated in modern MySQL/Postgres in favor of external caches, because invalidation on writes is hard to get right).
  • Buffer/page cache: DB engine caches disk pages in memory (e.g., Postgres shared_buffers, InnoDB buffer pool) — this is about speeding up the DB's own I/O, not about serving your application layer.
  • Prepared statement caching: DB/driver caches compiled query plans, so repeated queries with different parameters skip re-parsing/re-planning.
  • Read replicas vs caching: replicas scale read throughput by adding more DB instances that serve the same authoritative data (still doing real queries, same schema, same consistency model). A cache scales by avoiding the DB entirely for repeat reads, trading some freshness for speed. They solve different problems and are often used together.

Why DB cache ≠ application cache: A DB cache only ever holds what the DB engine decides is useful, is invisible to your application code, and disappears if the DB restarts or the query changes shape at all. An application cache is deliberately populated and shaped by your code around your actual access patterns (e.g., an assembled JSON blob of "user profile + their last 5 orders" — something no DB buffer cache would ever produce as a single unit).

3. Cache Technologies

Redis

What it is: An in-memory, network-accessible data structure server. Single-threaded execution model per core (with I/O threading in newer versions), extremely fast, and rich beyond simple key-value.

Architecture & operational features - In-memory: data lives in RAM; that's the source of its speed and its capacity ceiling. - Persistence (optional): RDB (periodic snapshots) and/or AOF (append-only log of writes) let Redis survive restarts — this is what differentiates it from Memcached. - Replication: primary-replica async replication for read scaling and failover. - High availability: Redis Sentinel monitors primaries and promotes a replica on failure. - Redis Cluster: shards data across multiple nodes using hash slots (16384 slots), giving horizontal scalability beyond one machine's RAM. - Sharding: either client-side, via Cluster, or via a proxy (e.g., Twemproxy) — spreads keys across nodes. - Pub/Sub: lightweight messaging between clients — not a durable queue, just fire-and-forget broadcast. - Streams: an append-only log data type (XADD/XREAD) that does support consumer groups and replay — closer to a lightweight Kafka than Pub/Sub. - Lua scripting: atomic multi-step server-side scripts. - Transactions (MULTI/EXEC): queue commands and execute atomically (optimistic, via WATCH). - TTL: per-key expiration, EXPIRE/PEXPIRE. - Eviction policies: configurable (noeviction, allkeys-lru, volatile-lru, allkeys-lfu, volatile-ttl, allkeys-random, etc.) for when memory fills up.

Data structures and practical use cases

Structure Use case
String Simple key-value: cached API response body, session token → user ID
Hash Object-like data: a user profile or session with multiple fields, updated field-by-field without re-serializing the whole object
List Ordered sequence: recent activity feed, simple queue (though Streams/dedicated queues are usually better for real queueing)
Set Unique membership: unique visitor IDs, tag sets, "has this user already voted"
Sorted Set (ZSet) Ranked data: leaderboards, rate-limiter sliding windows, priority queues, "top N trending"
Bitmap Compact boolean flags at scale: daily active user tracking (1 bit per user per day)
HyperLogLog Approximate distinct counts at fixed tiny memory: "how many unique visitors today" without storing every ID
Stream Ordered, replayable event log with consumer groups: activity/event pipelines, lightweight message queue

When Redis is a good choice: you need more than plain key-value (ranking, counting, atomic operations), you need durability options, you need pub/sub or lightweight streaming, or you need a single technology to cover several caching sub-problems at once.

When Redis is overkill: you just need dead-simple, massively-parallel key-value caching with no persistence and no data structure needs — the operational simplicity of Memcached may beat Redis's extra feature surface.

Memcached

What it is: A purely in-memory, multi-threaded, distributed key-value store built only to cache. No persistence, no data structures, no replication, no clustering logic built in — deliberately minimal.

  • Simple key-value only: get/set/delete on byte strings (typically ≤1MB values).
  • Distributed architecture: sharding logic lives in the client (consistent hashing across a list of servers) — the servers themselves don't know about each other.
  • Memory usage: slab allocator, generally very memory-efficient for uniform small object sizes.
  • No persistence: a restart wipes everything — this is a deliberate design choice (its only job is fast, disposable caching).
  • No complex data structures: no lists, sets, sorted sets.
  • Horizontal scaling: just add nodes and update the client's hash ring; each node is independent.
  • Eviction: LRU (approximate), per-slab.
  • Multi-node behavior: no node communicates with any other node — no cluster protocol, no coordination, no single point of failure at the protocol level. This is simpler than Redis Cluster but also means the client fully owns the sharding logic.
  • Multi-threaded: can use multiple CPU cores natively, which historically gave it an edge in raw throughput for simple GET/SET workloads on multi-core boxes (Redis has narrowed this gap with I/O threading, but the simplicity story still stands).

Concrete scenarios to deliberately pick Memcached: You're caching millions of small, uniform, disposable objects (e.g., rendered page fragments, serialized DB rows) at very high QPS, you have no need for persistence or replication, and you want the absolute simplest thing to operate. Historically common at very large web properties (Facebook's original photo-caching tier, for instance) precisely because "dumb and fast" was the requirement, not "featureful."

Caffeine / Local in-memory cache

  • What it means: cache lives inside the JVM/process heap of a single running instance — no network call at all.
  • Why it's extremely fast: it's just a hash map with eviction bookkeeping — sub-microsecond access.
  • Eviction: Caffeine specifically uses a highly efficient approximation of LFU (window TinyLFU) combined with LRU-like recency, giving very good hit ratios for the memory used.
  • TTL: supported per-entry or per-cache.
  • Per-instance: this is the crux of its main limitation.

The N-server consistency problem: If you have 10 API servers, each with its own Caffeine cache, and the underlying data changes (e.g., a product price update), only the server that handles the write knows about it. The other 9 servers keep serving stale cached data until their local TTL expires. There is no built-in mechanism for one instance to tell the other nine "invalidate key X now."

Solutions: (a) accept the staleness window if it's short and tolerable, (b) publish invalidation events over Pub/Sub or a message bus that every instance subscribes to and evicts locally, or (c) simply don't local-cache data that changes with any meaningful frequency — push it to a distributed cache instead, where there's exactly one copy to keep fresh. Many real systems use both: local cache as an L1 in front of Redis as an L2, and use pub/sub invalidation to clear L1 caches when writes happen (see multi-level caching, Section 13).

CDN caches (Cloudflare, CloudFront, Fastly)

  • Edge locations: many physical points of presence close to users worldwide; a request is served from the nearest one that has the content.
  • Cache-Control / max-age: server-set header telling caches (browser and CDN) how long content is fresh.
  • ETag: a content fingerprint; lets a client/cache do a conditional GET ("still valid?") without re-downloading the body if unchanged.
  • stale-while-revalidate: serve the (slightly) stale cached copy immediately while asynchronously fetching a fresh one in the background — great for perceived latency.
  • Cache invalidation/purging: explicit API call to evict content across all edge nodes when it changes (e.g., after deploying new CSS/JS, or removing a product image).

Good CDN candidates: images, video segments, CSS/JS bundles, product images, and public, non-personalized API responses (e.g., a public list of countries, a public leaderboard snapshot).

Why CDN is usually not a Redis replacement: a CDN caches whole HTTP responses/files keyed by URL, is not designed for per-user or highly dynamic, frequently-mutating data, has no rich data structures, and purging is typically URL/path-based rather than fine-grained key-based. Redis is for application-level, structured, low-latency, frequently-changing data close to your compute.

NGINX / Varnish (reverse proxy cache)

Client
  ↓

  ↓

Database

Makes sense when: many requests hit identical, cacheable HTTP responses (public pages, API GETs with shared cache keys), and you want to shield your application tier — not just your database — from repeated work, without needing full geographic edge distribution like a CDN. Often used as an internal caching layer even when a CDN also sits in front of it (CDN for global users, reverse proxy for internal/backend protection and for content not suited to public edge caching).

4. Caching Patterns (Mechanisms)

Cache-aside (Lazy loading) — the default

App checks Cache
  hit  → return
  miss → App queries DB → App writes result to Cache → return

Why it's the most common pattern: the application has full control over what gets cached and when — only data that's actually requested ever ends up in cache (no wasted memory on unused data), and it degrades gracefully (if the cache is empty or down, the app can still hit the DB directly). Its downside is a "cold" miss always pays full DB latency, and there's a small window where cache and DB can disagree if not paired with an invalidation strategy.

Read-through

App → Cache → (on miss) Cache itself fetches from DB → Cache stores it → returns to App

Here the cache layer/library, not the application, is responsible for fetching on a miss (common in cache libraries/frameworks that wrap a data-access layer). Functionally similar to cache-aside from the app's point of view, but the fetch-on-miss logic is centralized in the caching layer rather than scattered through application code.

Write-through

App writes → Cache → Cache synchronously writes → DB
  • Consistency: cache and DB are updated together, so cache is never stale as of the last write.
  • Write latency: higher, because every write pays the cost of both cache and DB writes before returning.
  • Advantages: strong read-after-write consistency, no separate invalidation logic needed.
  • Disadvantages: extra write latency on every write; you're paying to cache data on write even if it's never read again (wasted cache memory for cold data).

Write-back (Write-behind)

App writes → Cache (fast ack to App) → Cache asynchronously flushes → DB
  • Why it's fast: the app gets an immediate response after only the cache write; the DB write happens later, batched/async.
  • Durability risk: if the cache crashes before flushing, that write is lost — the DB never sees it.
  • Failure scenarios: cache node dies mid-batch, network partition between cache and DB, or the DB rejects a batched write out of order.
  • When appropriate: high write-throughput scenarios that can tolerate small data loss risk or that have external durability guarantees elsewhere (e.g., analytics counters, view counts, non-critical telemetry) — essentially never for money or safety-critical writes.

Write-around

App writes → DB directly (cache untouched)

Cache is populated only later, on a subsequent read (falls into cache-aside from that point). Useful when written data is rarely re-read soon after being written (e.g., bulk imports, logs, write-heavy/read-rarely data) — avoids polluting the cache with data that's unlikely to be requested again soon.

5. Cache Eviction Policies

Policy How it works Best when Trade-off
LRU (Least Recently Used) Evicts the entry that hasn't been accessed longest Access pattern has strong recency bias (recently viewed items likely viewed again) A single scan of many items (e.g., a bulk export) can wipe out a warm cache ("cache pollution")
LFU (Least Frequently Used) Evicts the entry with the lowest access count Popularity is stable over time, and you want to protect perennially-hot items from being evicted by a one-time burst Slow to adapt when popularity shifts (an old "frequency count" can keep a now-cold item around)
FIFO Evicts oldest-inserted entry, regardless of usage Simplicity matters more than optimality; roughly-uniform access patterns Ignores usage entirely — can evict something that's still hot just because it's old
TTL Entry expires after fixed time regardless of access Freshness matters more than access pattern (e.g., a price that must not be stale for more than 30s) Not usage-aware; can evict hot data early or keep cold data around until expiry
Random Evicts a random entry Extremely simple, low bookkeeping overhead, works surprisingly well under uniform access No optimality guarantees; can evict something hot purely by chance

LRU vs LFU — Instagram feed example: Recently viewed posts (LRU-favored) are likely to be revisited briefly (user scrolls back up) — LRU protects this well. But a globally popular post (viral, LFU-favored) might not have been touched in the last few minutes yet is requested constantly across many users — pure LRU could evict it if a burst of one-time scroll traffic pushes it out. This is why Caffeine's default policy (window TinyLFU) blends recency and frequency — it protects consistently-popular items ("celebrity post") while still adapting to genuinely new trending content.

Product catalog analogy: a flash-sale item (sudden, sustained popularity) is better protected by LFU; a "recently viewed products" widget is inherently an LRU concept.

6. Cache Invalidation Strategies

  • TTL-based expiration: simplest — set-and-forget, but you're always trading off freshness window vs DB load.
  • Explicit invalidation: application code deletes/updates the cache key at the moment the underlying data changes (e.g., on updateProductPrice(), call cache.delete("product:123")).
  • Event-driven invalidation: a change event (DB change-data-capture, message queue event) triggers invalidation across all consumers/instances — decouples "who wrote the data" from "who needs to invalidate," which matters a lot with local caches spread across many servers.
  • Versioned cache keys: instead of invalidating, change the key itself (product:123:v7) whenever data changes; old versions simply age out via TTL/eviction, and readers always ask for the latest version pointer. Avoids race conditions inherent in delete-then-repopulate.
  • Refresh-ahead: proactively refresh a cache entry before it expires (typically once it crosses some threshold, e.g., 80% of TTL elapsed), so users rarely see a miss.
  • Stale-while-revalidate: serve the current (slightly stale) value immediately, kick off an async refresh in the background, update the cache when it completes — used heavily at the CDN/HTTP layer.

Example — product price: DB has ₹100, cache has ₹100. DB updates to ₹120. - With TTL only: cache keeps serving ₹100 until TTL expires — staleness window = TTL. - With explicit invalidation: the price-update code path also calls cache.delete("product:123:price") (or writes the new value directly, i.e., write-through) — near-zero staleness. - With versioned keys: the update writes product:123:price:v2, and a pointer/index is flipped so subsequent reads fetch v2. Old v1 just expires normally.

How to keep cache and DB consistent — there is no free lunch; you're choosing a point on the freshness/complexity/performance triangle. The general rule interviewers want to hear: invalidate on write, expire with TTL as a safety net. Relying on TTL alone is acceptable only when a bounded staleness window is genuinely fine for the business.

7. Cache Stampede / Thundering Herd

Scenario: a hot cache entry expires. 10,000 concurrent requests all miss simultaneously and all hammer the DB at once — potentially enough to take the DB down.

Before (naive):

10,000 requests → all miss → all query DB → DB overloaded

After (fixed):

10,000 requests → 1 acquires lock/leads refresh → DB queried once
                → other 9,999 either wait briefly for the result, or get slightly-stale data

Solutions - Distributed locks: only the first request to detect a miss acquires a lock and refreshes; others wait or fall back. - Request coalescing / single-flight: the app layer collapses many concurrent identical requests into a single in-flight DB call, fanning the one result out to all waiters (common library pattern, e.g., Go's singleflight). - Refresh-ahead: expire proactively before the crowd arrives, so there's never a true "everyone misses at once" moment. - Probabilistic early expiration: each reader has a small, increasing chance of triggering an early refresh as TTL approaches, spreading refreshes out probabilistically instead of all-at-once. - Stale-while-revalidate: just keep serving the (barely) expired value while one request refreshes in the background.

8. Cache Penetration

Scenario: requests for data that doesn't exist, e.g., GET /users/999999999. Since it's never cached (there's nothing to cache), every such request bypasses the cache entirely and hits the DB — repeatable, and exploitable by an attacker probing random IDs.

Solutions - Negative caching: cache the absence too (user:999999999 → NOT_FOUND, short TTL) so repeat lookups of the same non-existent ID are absorbed by the cache. - Bloom filters: a compact probabilistic structure that can definitively say "this ID was never inserted" — filters out impossible lookups before they even reach the cache/DB, with a small false-positive rate (never false negatives). - Input validation: reject obviously malformed/out-of-range IDs before they ever reach the cache or DB layer. - Rate limiting: cap how many misses/lookups a single client can generate, limiting the blast radius of an attack or bug.

9. Cache Avalanche

Scenario: a large number of keys were all set with the same TTL (e.g., a bulk cache warm at 00:00 with TTL=1hr) — they all expire at once at 01:00, and the DB is suddenly hit with the full, un-cached load simultaneously.

Solutions - TTL jitter: add a random offset to each TTL (baseTTL + random(0, 300s)) so expirations spread out over time instead of landing on the same instant. - Staggered refresh: proactively refresh keys on a rolling schedule rather than a synchronized bulk load. - Multi-level caching: an L1 (local) cache plus an L2 (Redis) means even if L2 has a mass expiry, L1 absorbs some of the shock temporarily. - Graceful degradation: if the DB does get overwhelmed momentarily, serve stale data, degrade non-critical features, or apply backpressure/circuit breakers rather than letting the DB fall over entirely.

10. Hot Keys

Scenario: one specific key gets disproportionate traffic — e.g., a celebrity's post that millions of users request in the same minute. Even though Redis Cluster distributes different keys across nodes, a single hot key still lives on exactly one node/shard — that one node becomes a bottleneck no matter how many other nodes exist.

Why Redis Cluster alone doesn't solve it: sharding distributes key space, not per-key load. All 5 million requests for the same key hash to the same slot, hence the same node.

Solutions - Key replication: manually replicate the hot key's value across multiple nodes/shards (e.g., key:1, key:2, ... key:N) and have clients pick one at random — spreads read load. - Local cache in front: cache the hot key inside each app instance's local memory (Caffeine) for a very short TTL — absorbs the vast majority of the traffic before it even reaches the distributed cache. - CDN: if the hot content is public and cacheable as an HTTP response, push it to the edge entirely. - Request coalescing: as with stampede, collapse concurrent requests for the same hot key into one backend fetch. - Read replicas: for the Redis node itself, add local replicas to spread read traffic for that shard. - Splitting hot keys: shard the logical key into sub-keys(e.g., partition a hot counter into N sub-counters, sum on read) so no single physical key/node bears the full load.

Mental model for choosing: Ask, in order — (1) Is this public, static-ish, and consumed by many geographically distributed users? → CDN. (2) Is this a repeated, identical HTTP request pattern that I want to shield my app tier from? → reverse proxy. (3) Is this small, hot, per-instance data that tolerates slight staleness across servers? → local cache. (4) Does everything else need a single shared, low-latency, structured store? → Redis (default) or Memcached (if you truly only need dumb key-value at extreme simplicity/scale).

13. Multi-Level Caching

Client
  ↓
CDN            (public static assets, public API responses)
  ↓
NGINX          (HTTP-level response caching, shields app tier)
  ↓
Local Cache    (per-instance hot/reference data, nanosecond access)
  ↓
Redis          (shared structured/session/ranking data)
  ↓
Database       (source of truth)

Why multiple layers exist: each layer removes load from everything below it and serves a different kind of data at a different speed/consistency trade-off point. No single layer is right for everything.

What belongs where (e-commerce example): - CDN: product images, category banners, static JS/CSS. - NGINX: fully-rendered public category/listing pages that don't vary per user. - Local cache: currency exchange rates, tax rules, feature flags — small, globally-shared-ish, rarely-changing. - Redis: shopping cart contents, session data, live inventory counts, price (with short TTL + invalidation on update). - Database: authoritative order records, payment records, anything requiring strong consistency.

How misses propagate: a miss at CDN falls to NGINX; a miss at NGINX falls to the app, which checks local cache; a local miss checks Redis; a Redis miss finally hits the DB. Each layer that gets a fresh answer typically re-populates the layers above it on the way back out.

How invalidation works across layers: this is the hard part. A price change must invalidate Redis (source for the app), and ideally purge any CDN/NGINX-cached pages that embedded that price, and trigger local-cache eviction on all app instances (commonly via a pub/sub "invalidate key X" broadcast). Missing any one layer means stale data can surface intermittently depending on which path a given request takes.

Failure scenarios: if Redis goes down, does NGINX have a stale-but-servable copy? If the CDN is purged incorrectly, does NGINX still serve the old page? Multi-level caching increases resilience (many layers can independently keep serving during a lower-layer outage) but also increases the surface area for "why am I seeing stale data" bugs — always design invalidation before you design the layering.

14. System Design Examples

Format: Requirements → Access Pattern → Cache Location → Technology → Pattern → TTL → Eviction → Invalidation → Failure Handling → Scaling

A. URL Shortener

  • Requirements: extremely read-heavy (redirects), low-latency redirect, occasional writes (new short URL creation).
  • Access pattern: skewed — a small fraction of URLs get the vast majority of clicks (power law).
  • Cache location: distributed cache in front of DB; CDN generally not useful (redirects are per-key lookups, not static assets); local cache for the very hottest URLs.
  • Technology: Redis (or Memcached — data here is truly just key→URL, so Memcached is a legitimate, even preferable, simpler choice given no need for structures or persistence).
  • Pattern: cache-aside (miss → DB lookup → populate cache).
  • TTL: long (hours–days) since short URL mappings essentially never change once created.
  • Eviction: LRU is fine — genuinely cold URLs should fall out.
  • Extremely popular URLs (hot key): replicate the key across shards or push it into local per-instance caches to avoid one node/shard bottlenecking.
  • Failure handling: fail open to DB lookup if cache is down (redirects just get slower, not broken).
  • Scaling: Redis Cluster/Memcached horizontal scaling as QPS grows; consider CDN-style edge redirect caching for extreme scale.

B. E-commerce

  • Product details: Redis, cache-aside, medium TTL (minutes) + explicit invalidation on edit.
  • Product images: CDN, long TTL, versioned URLs to bust cache on update instead of purging.
  • Prices: Redis, short TTL + explicit invalidation on price change (freshness matters for trust/legal reasons).
  • Inventory: cache very cautiously or not at all for exact counts near zero stock — risk of overselling; often cache an approximate count with short TTL and re-verify against DB at checkout ("cache for display, verify at commit").
  • Shopping carts: Redis (hash per user), since carts are per-user, frequently read/written, and don't need to be durable at DB-grade (though many systems also persist carts to DB for recovery).
  • User sessions: Redis, write-through-ish (session data written to cache immediately, DB async or not at all for ephemeral sessions).
  • What should NOT be cached: real-time exact inventory at the moment of checkout, payment status, and anything where a stale read could cause a business-incorrect outcome (overselling, double charging).

C. Instagram

  • User profiles: Redis hash, cache-aside, long-ish TTL + invalidate on profile edit.
  • Posts: Redis (metadata) + CDN (media itself); post content rarely changes once published.
  • Feed: classic fan-out decision — fan-out on write (precompute each follower's feed in Redis lists when a post is made; fast reads, expensive/heavy writes for high-follower-count accounts) vs fan-out on read (assemble the feed at read time by merging followed users' recent posts; cheaper writes, more expensive reads). Real systems use a hybrid: fan-out on write for normal users, fan-out on read for celebrity accounts (avoids "write amplification" of pushing one post to tens of millions of follower feeds).
  • Likes/comments counts: Redis counters (INCR), periodically flushed to DB — trades small precision windows for huge write scalability.
  • Hot posts: local cache + key replication + CDN for media, same hot-key techniques as Section 10.

D. YouTube / Netflix

  • CDN: video segments are the primary cached artifact — chunked (e.g., HLS/DASH segments), cached at edge, by far the largest data volume in the system.
  • Metadata (title, description, view count): Redis/app cache, moderate TTL.
  • Recommendations: often precomputed offline and cached with a TTL measured in hours, since recomputing per-request is expensive and slight staleness is fine.
  • Popular content: naturally benefits most from CDN edge caching — the more popular, the higher the edge cache hit ratio.
  • Why not Redis for actual video files: Redis is RAM-based and priced/sized for structured, small, hot objects — storing multi-gigabyte video files in RAM-backed Redis is both cost-prohibitive and architecturally wrong; video delivery is a bytes-over-HTTP problem best solved by object storage + CDN, not an in-memory key-value store.

E. Uber

  • Driver locations: Redis, using geospatial commands (GEOADD/GEOSEARCH) — a sorted-set-based structure purpose-built for "find nearby drivers" queries; extremely short TTL or continuous overwrite since location changes every few seconds.
  • Nearby drivers query: Redis geospatial index, very short-lived cache, essentially a live index rather than a "cache" in the traditional sense.
  • User info: Redis, cache-aside, normal TTL.
  • Pricing (surge pricing): cached briefly (seconds) per geo-cell, recomputed frequently — freshness matters a lot here.
  • Trip metadata: DB is authoritative (needs durability/audit trail); Redis may hold the "current active trip" state for fast access during the ride, synced to DB on state transitions.
  • Local cache: could hold static reference data like city zone boundaries, rarely-changing pricing rules.

F. Chat application

  • Recent messages: Redis list/stream per conversation, holding the most recent N messages for fast initial load; full history lives in DB.
  • Conversation metadata: Redis hash, cache-aside.
  • User presence (online/offline/typing): Redis with very short TTL (essentially a heartbeat — client marks itself present, TTL expiry means "went offline").
  • Unread counts: Redis counters, incremented on new message, reset on read-receipt — needs to be reasonably accurate but not perfectly durable second-to-second.
  • Consistency requirements: message content itself needs strong consistency (users must not lose messages) — DB/durable log is authoritative; presence and unread counts can tolerate looser, eventually-consistent behavior.

G. Banking / payment system

  • What can be cached: read-mostly, non-sensitive-to-staleness reference data — exchange rates (short TTL), merchant/category metadata, UI configuration, rate limit counters.
  • What must NOT be cached (or cached very carefully): account balances (must reflect the authoritative ledger at time of decision), transaction records, payment status.
  • Idempotency: payment APIs typically use an idempotency key stored in a fast store (often Redis, sometimes DB) to detect and safely no-op duplicate retries — this is a caching-adjacent pattern, but its purpose is correctness, not performance.
  • Strong consistency: for balance checks before authorizing a debit, you generally read from the DB (or a cache updated synchronously, write-through, with strict invalidation) — never rely on a possibly-stale cached balance to authorize money movement.
  • Security: cached data should never include full card numbers/secrets; anything cached must respect the same encryption-at-rest and access-control requirements as the source system.

15. Decision Framework — "If I need..."

Need Consider
Extremely fast, per-instance reads of small, semi-static data Local in-memory cache (Caffeine)
Simple distributed key-value caching at massive, uniform scale Memcached
Distributed cache with rich data structures (ranking, counters, geospatial, pub/sub) Redis
Persistent, Redis-compatible durable store Managed durable Redis-compatible services (e.g., AWS MemoryDB)
Global caching of static/public content CDN
HTTP response caching in front of application servers Reverse proxy (NGINX/Varnish) or CDN
Complex leaderboard/ranking queries Redis Sorted Sets
Very high-volume, simple object caching (no structure needed) Memcached

Reasoning, not rules: none of these are absolute. E.g., you can build a leaderboard on Memcached (store a serialized list, re-sort in app code), but you'd be reimplementing what Redis Sorted Sets already give you for free, at higher latency and complexity. The right answer in an interview is always "here's what I need, here's what maps to it, and here's the trade-off I'm accepting" — not a memorized rule.

16. Cache Failure Scenarios

Failure Strategy
Redis fully down Fail open: fall back to DB directly (slower but system stays up), ideally with a circuit breaker to avoid hammering a possibly-struggling DB with sudden full load
One Redis node fails (in Cluster) Only that shard's keys are affected; replicas can be promoted automatically if HA is configured; other shards unaffected
Entire Redis cluster fails Fail open to DB with aggressive rate limiting/circuit breaking to protect the DB from the full traffic surge; consider a secondary/warm-standby cache region
Network partition Cache and app may disagree on state; Redis Sentinel/Cluster has quorum-based failover, but during the partition itself, expect brief inconsistency or unavailability of writes
Cache becomes slow Set aggressive timeouts on cache calls + fall back to DB rather than waiting indefinitely (avoid cascading latency into the app tier)
Cache returns stale data Acceptable if within your defined freshness SLA; unacceptable → add explicit invalidation, shorten TTL, or move to write-through for that data
Cache is full Eviction policy kicks in (LRU/LFU/etc.); monitor eviction rate — high eviction rate signals your cache is undersized for the working set
Hot key overloads one node See Section 10 — replication, local cache, request coalescing, splitting the key

General strategies: fail open for read-heavy, availability-prioritized systems (most consumer apps); fail closed only where serving wrong/incomplete data is worse than an error (rare, mostly safety/compliance-critical paths); circuit breakers to stop retrying a dead dependency; rate limiting to protect the DB during degraded-cache periods; replication and multi-region caching for geographically distributed resilience.

17. System Design Calculations

Example: 100,000 requests/sec, 90% cache hit rate. - Requests hitting DB = 100,000 × (1 − 0.90) = 10,000 req/sec

At 95% hit rate: - DB load = 100,000 × 0.05 = 5,000 req/sec (half the DB load of 90%, for a "only" 5-point hit-ratio improvement)

At 99% hit rate: - DB load = 100,000 × 0.01 = 1,000 req/sec (10x less than the 90% case)

Why small hit-ratio improvements matter enormously at scale: DB load scales with the miss rate, not the hit rate, and the miss rate shrinks multiplicatively as hit rate approaches 100%. Going from 90%→99% hit rate isn't "9% better" — it's a 10x reduction in absolute DB traffic. This is the single most persuasive number to bring up in an interview when justifying investment in a better caching/eviction strategy or higher cache capacity.

Estimating cache size / memory: (average object size) × (number of "hot" objects you intend to keep resident) × (replication factor, if any) — then size Redis/Memcached nodes with headroom (never plan to run at ~100% memory; leave room for fragmentation and traffic spikes) and add eviction policy as a safety valve for anything beyond that.

TTL impact: shorter TTL → lower average staleness, more DB load (more frequent misses); longer TTL → less DB load, higher staleness risk. Model this explicitly: if writes to a given entity happen roughly every X minutes, a TTL far shorter than X buys you little freshness benefit but costs real DB load; a TTL far longer than X risks meaningfully stale reads.

18. Common Interview Mistakes

Weak answer Why it's weak Stronger framing
"Just use Redis." Skips the actual decision process; ignores cases where simpler/cheaper tools fit better "Given the access pattern is X and I need Y capability, Redis fits because Z — though Memcached would also work if I don't need structures."
"Redis is always faster." Not universally true (Memcached can beat it on raw multi-threaded key-value throughput); latency also depends on network, data size, serialization "They're comparable for simple key-value; the choice is about feature needs, not raw speed."
"Memcached is obsolete." Still used at massive scale (simplicity is a feature, not a limitation) "Memcached is the right tool when I truly only need simple, disposable, high-throughput key-value caching."
"Cache everything." Wastes memory, adds staleness risk, and can actively cause correctness bugs on sensitive data "I cache based on access frequency and tolerance for staleness — not everything benefits equally."
"Use a 5-minute TTL." Arbitrary, ignores the actual write frequency and business tolerance for staleness "TTL should be derived from how often the underlying data changes and how stale is acceptable."
"Use LRU for everything." Ignores workloads where LFU, TTL, or a hybrid fits the actual access pattern better "LRU is my default, but I'd consider LFU for stable long-term popularity, e.g. viral content."
"CDN can replace Redis." Different data shapes and use cases entirely (static/public vs dynamic/structured) "CDN handles static/public content at the edge; Redis handles dynamic, structured, shared application state."
"Redis can replace the database." Redis is not built as a durable, queryable system of record by default (even with persistence, it lacks rich querying, strong transactional guarantees at scale, etc.) "Redis complements the database; the database remains the source of truth."
"NoSQL is basically a cache." Conflates a durable, queryable data store with a fast, ephemeral acceleration layer "Some NoSQL stores can serve cache-like read patterns, but they're built for durability and querying, not primarily for eviction-based, ephemeral speed."
"If Redis goes down, the system goes down." Signals no failure planning — should almost always design for fail-open/degraded-mode operation "I design for graceful degradation: if Redis is down, we fail open to the DB with circuit breakers to protect it."
"We don't need cache invalidation." Nearly always wrong once data changes — leads to silently wrong cached data "I pair TTL with explicit invalidation on write paths that matter for correctness."

20. Final Cheat Sheet

Caching Technology

Technology What it is Best use case Why Main trade-off
Redis In-memory data-structure server Sessions, leaderboards, rate limiting, structured shared caching Rich data types + optional persistence + HA More operational complexity than Memcached
Memcached In-memory key-value store Simple, massive-scale object caching Extremely simple, very fast, memory-efficient No persistence, no structures, no built-in HA
Caffeine In-process local cache Small, hot, per-instance data Zero network latency No cross-instance consistency
CDN (generic) Edge caching network Static/public global content Geographically close to users Not suited for dynamic/personalized data
Cloudflare CDN + edge/security platform Global static & public API caching + DDoS protection Broad edge network, built-in security features Vendor-specific config/limits
CloudFront AWS CDN Static/public content, AWS-native origins Tight AWS integration (S3, ALB, Lambda@Edge) Best value inside AWS ecosystem specifically
Varnish HTTP reverse-proxy cache High-performance backend HTTP acceleration Purpose-built for HTTP caching, very fast HTTP-only, not for general app-level caching
NGINX cache Reverse proxy + cache HTTP response caching + routing/LB Multi-purpose (proxy, LB, cache) already in most stacks Less specialized than Varnish for pure caching

Caching Pattern

Pattern Best use case Main trade-off
Cache-aside General-purpose default First read after a miss/expiry always pays full latency
Read-through Systems where the cache library should own fetch logic Less app-level control over what/when to cache
Write-through Strong read-after-write consistency needs Higher write latency
Write-back Very high write throughput, tolerant of some data-loss risk Durability risk if cache fails before flush
Write-around Write-heavy, rarely-re-read-soon data First read after write is always a miss

Problems

Problem Why it happens Solution
Cache stampede One hot key expires; many concurrent requests all miss at once Locking, request coalescing/single-flight, refresh-ahead
Cache penetration Requests for data that doesn't exist, bypassing cache every time Negative caching, bloom filters, input validation
Cache avalanche Many keys expire at the same time TTL jitter, staggered refresh, multi-level caching
Hot keys One key gets disproportionate traffic Key replication, local cache layer, CDN, request coalescing, splitting the key
Stale data Cache updated less often/differently than source Explicit invalidation, versioned keys, shorter TTL, write-through where needed
Cache failure Node/cluster/network outage Fail open to DB, circuit breakers, replication, multi-region

The One Decision Tree to Memorize

1. REQUIREMENTS
   What data? How often does it change? How critical is freshness/correctness?
        ↓
2. ACCESS PATTERNS
   Read-heavy or write-heavy? Skewed (hot keys) or uniform? Per-user or shared/global?
        ↓
3. FRESHNESS
   Can this tolerate seconds/minutes of staleness, or must it be exact (money, inventory at checkout)?
        ↓
4. CACHE LOCATION
   Public/static → CDN
   Repeated identical HTTP responses → Reverse proxy
   Small, hot, per-instance-safe → Local cache
   Shared, structured, app-level → Distributed cache
        ↓
5. CACHE TECHNOLOGY
   Need structures/pubsub/persistence → Redis
   Need dead-simple massive key-value → Memcached
   Need in-process speed → Caffeine
   Need global edge delivery → CDN
        ↓
6. CACHING PATTERN
   Default → Cache-aside
   Need strict consistency on write → Write-through
   Need max write throughput, can risk loss → Write-back
   Rarely-reread writes → Write-around
        ↓
7. TTL / EVICTION
   Set TTL from actual data-change frequency + business tolerance for staleness
   Pick LRU (recency-driven), LFU (popularity-driven), or TTL-only based on access pattern
        ↓
8. INVALIDATION
   Pair TTL with explicit invalidation on writes that matter; consider versioned keys or event-driven invalidation across instances/layers
        ↓
9. FAILURE HANDLING
   Default to fail-open with circuit breakers and DB fallback; fail-closed only where wrong data is worse than downtime
        ↓
10. SCALING
    Add replicas/shards/clustering as load grows; watch hit ratio and eviction rate as your primary health signals

Recite this top to bottom for any caching question, filling in the specifics of the system you're asked about — that structure alone signals strong system-design thinking, independent of which exact technology you land on.
