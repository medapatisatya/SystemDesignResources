Problem 1 — URL Shortener

Basic Utility

Problem statement: Design a service that converts long URLs into short, shareable links and redirects users from the short link back to the original URL.

Context / scenario: A marketing team wants to share short links in emails and social posts, and later see how many times each link was clicked.

What you are expected to determine:

  • What functionality is actually needed (custom aliases? expiration? analytics?)
  • How many shorten and redirect requests the system must handle per second
  • What data needs to be stored per link and how it should be structured
  • How the redirect and creation APIs should be shaped
Show Answer

1. Requirements Gathering

Functional Requirements
  • User submits a long URL and receives a short URL
  • User can optionally choose a custom alias
  • Anyone who visits the short URL is redirected to the original long URL
  • Optional: links can expire after a set time
  • Optional: basic click count per link
Non-Functional Requirements
  • High availability for redirects (a broken short link looks bad publicly)
  • Low latency on redirect (should feel instant)
  • Redirects should heavily outnumber creations (read-heavy system)
  • Short codes must not collide with each other
Scale Requirements
  • How many new links are created per day?
  • How many redirects (clicks) happen per day?
  • Do we need analytics beyond a raw click count?
  • Do links expire, and if so what's the default TTL?

Questions to ask the interviewer:

  • Should short codes be guessable/sequential or random?
  • Is a custom alias feature required for v1?
  • Do we need to support link editing/deletion?

2. Scale Estimation

Assumptions
  • 10 million new links created per day
  • Read:Write ratio of 100:1 (redirects vastly outnumber creations)
  • Each link record is small, ~500 bytes including metadata
  • Links are retained for 5 years by default
Calculations
Write QPS = 10M / 86,400 sec ≈ 116 writes/sec
Read QPS = 116 * 100 ≈ 11,600 reads/sec ≈ 12K QPS
Peak factor ~3x average for both → Peak Write ≈ 350 QPS, Peak Read ≈ 35K QPS
Storage per day = 10M links * 500 bytes ≈ 5 GB/day
Storage per year ≈ 5GB * 365 ≈ 1.8 TB/year
Storage for 5 years ≈ 9 TB total
Write bandwidth = 116 * 500 bytes ≈ 58 KB/sec (negligible)
Read bandwidth = 12,000 * ~1KB (redirect response) ≈ 12 MB/sec
Final Numbers
  • ~116 writes/sec avg, ~350 writes/sec peak
  • ~12K reads/sec avg, ~35K reads/sec peak
  • ~1.8 TB/year storage growth

Uncertain / worth double-checking:

  • Actual read:write ratio (could be 10:1 or 1000:1 depending on product)
  • Whether analytics events multiply the write load significantly

What matters most for the design discussion: Read QPS and redirect latency dominate the design conversation since this is an overwhelmingly read-heavy, latency-sensitive system.

  • Not asking whether custom aliases are in scope before designing the API

Problem 2 — Pastebin

Basic Content

Problem statement: Design a service where users can paste text (e.g., code snippets) and get a shareable link others can use to view the content.

Context / scenario: Developers want to quickly share a chunk of code or logs with a teammate via a link, sometimes with an expiration.

What you are expected to determine:

  • What functional variations matter (syntax highlighting, expiration, privacy)
  • How large pastes can be and how that affects storage per day
  • The read/write ratio for a link-sharing product
  • The core entity and the create/read APIs
Show Answer

1. Requirements Gathering

Functional Requirements
  • User submits text content and receives a shareable URL
  • Anyone with the link can view the paste (unless private)
  • Optional: paste expires after a chosen duration
  • Optional: paste can be marked private/password protected
Non-Functional Requirements
  • Durability of stored pastes until they expire
  • Low latency for viewing (read path)
  • Reasonable max paste size to bound storage per item
  • Availability for both create and view paths
Scale Requirements
  • Max paste size allowed?
  • Expected read:write ratio?
  • Default and max retention period?

Questions to ask the interviewer:

  • Is there a maximum content size we should enforce?
  • Do pastes need version history or edits after creation?
  • Should we support syntax highlighting metadata (language tag)?

2. Scale Estimation

Assumptions
  • 1 million new pastes/day
  • Average paste size 10 KB, max 1 MB
  • Read:Write ratio of 10:1
  • Default retention: 30 days unless marked permanent
Calculations
Write QPS = 1,000,000 / 86,400 ≈ 12 writes/sec
Read QPS = 12 * 10 ≈ 120 reads/sec
Peak (3x) → ~36 writes/sec, ~360 reads/sec
Storage per day = 1M * 10KB ≈ 10 GB/day
Storage per 30-day window ≈ 300 GB (steady state, since old pastes expire)
Write bandwidth ≈ 12 * 10KB ≈ 120 KB/sec
Read bandwidth ≈ 120 * 10KB ≈ 1.2 MB/sec
Final Numbers
  • ~12 writes/sec avg, ~36 peak
  • ~120 reads/sec avg, ~360 peak
  • ~300 GB steady-state storage with 30-day retention

Uncertain / worth double-checking:

  • Actual average paste size (logs can be much larger than code snippets)
  • What fraction of users choose 'permanent' retention, which changes long-term storage growth

What matters most for the design discussion: Storage growth is bounded by retention policy here, unlike a system where all data lives forever — this is worth calling out explicitly.

3. Core Entities / API Design

Entities

Represents one submitted block of text and its metadata.

APIs

Create a new paste

Response

{ "paste_id": "p_9xk2", "url": "https://paste.sh/p_9xk2" }

Important parameters

  • content (required, size-limited)
  • language (optional)
  • ttl_seconds (optional)
  • is_private (optional)

Edge cases

  • Content exceeds max size
  • Empty content
  • Invalid TTL
GET/v1/pastes/{paste_id}

Retrieve paste content for viewing

Request

(none)

Response

{ "paste_id": "p_9xk2", "content": "print('hi')", "language": "python", "created_at": "..." }

Important parameters

  • paste_id (path param)
  • password (if private)

Edge cases

  • Expired paste → 410
  • Private paste without correct password → 403

What a Strong Candidate Should Notice

  • Recognize paste size limits directly affect storage-per-day estimates
  • Notice that expiration makes this different from 'store forever' systems — steady-state storage matters more than cumulative
  • Think about private/password-protected pastes as a non-functional (security) requirement
  • Keep the entity model minimal — one core entity is enough at this stage

Common Mistakes

  • Calculating cumulative storage for years without accounting for expiration
  • Ignoring max content size, leading to unbounded storage-per-item assumptions
  • Adding unnecessary entities like 'User' when the problem doesn't require accounts
  • Not clarifying whether pastes are public by default

Problem 3 — API Rate Limiter (as a Service)

Basic Infrastructure

Problem statement: Design a rate-limiting service that other backend services can call to check whether a given client has exceeded its allowed request quota.

Context / scenario: Multiple internal microservices want a shared way to enforce 'X requests per minute per API key' without each reimplementing the logic.

What you are expected to determine:

  • What limits need to be configurable (per-user, per-API-key, per-IP)
  • The QPS the rate limiter itself must handle, since every protected request calls it
  • What data must be tracked per client to make an allow/deny decision
  • The shape of the check API and how fast it must respond
Show Answer

1. Requirements Gathering

Functional Requirements
  • Given a client identifier, determine if the current request is allowed under its configured limit
  • Support configurable limits per client (e.g., 100 requests/minute)
  • Return remaining quota and reset time to the caller
  • Support different limit tiers for different clients/API keys
Non-Functional Requirements
  • Extremely low latency (it sits in the hot path of every request)
  • High availability — if the limiter is down, dependent services are affected
  • Consistency can be relaxed slightly (approximate counting is acceptable) in favor of speed
  • Must scale linearly with total traffic across all protected services
Scale Requirements
  • How many protected requests per second across all services?
  • How many distinct clients/API keys need independent counters?
  • What time windows are supported (per-second, per-minute, per-day)?

Questions to ask the interviewer:

  • Is slight inaccuracy in limiting acceptable for the speed/simplicity tradeoff?
  • Do limits vary per endpoint or just per client?
  • Should exceeding the limit be logged for later analysis?

2. Scale Estimation

Assumptions
  • The limiter is called on 500 million protected requests/day
  • 5 million distinct clients (API keys) being tracked
  • Each check requires reading/incrementing a small counter (~100 bytes)
Calculations
Check QPS = 500,000,000 / 86,400 ≈ 5,787/sec ≈ 6K QPS average
Peak (business hours can be 5x average for bursty API traffic) → ~30K QPS peak
Counter storage = 5M clients * 100 bytes ≈ 500 MB total resident data
Read+write bandwidth ≈ 6,000 * 200 bytes (read+write combined) ≈ 1.2 MB/sec avg
At peak: 30,000 * 200 bytes ≈ 6 MB/sec
Final Numbers
  • ~6K QPS average, ~30K QPS peak
  • ~500 MB of active counter state
  • Sub-10ms latency budget per check

Uncertain / worth double-checking:

  • True peak multiplier — bursty client behavior (e.g., a retry storm) could spike far higher than 5x
  • Whether counters need to persist across restarts or can be treated as ephemeral

What matters most for the design discussion: Latency budget and QPS matter far more than storage size here — this system lives or dies on how fast a single check can complete.

3. Core Entities / API Design

Entities
RateLimitPolicy

client_id, limit_count, window_seconds, tier

Defines how many requests a given client may make in a given time window.

UsageCounter

client_id, window_start, current_count

Tracks how many requests a client has made in the current active window.

APIs
POST/v1/ratelimit/check

Check and record whether a request is allowed

Request

{ "client_id": "key_abc123", "cost": 1 }

Response

{ "allowed": true, "remaining": 42, "reset_at": "2026-09-22T10:05:00Z" }

Important parameters

  • client_id (required)
  • cost (optional, default 1 — for weighted requests)

Edge cases

  • Unknown client_id (no policy configured)
  • Clock skew affecting window boundaries
  • Cost larger than the entire limit
PUT/v1/ratelimit/policies/{client_id}

Set or update a client's rate limit policy

Request

{ "limit_count": 1000, "window_seconds": 60 }

Response

{ "client_id": "key_abc123", "limit_count": 1000, "window_seconds": 60 }

Important parameters

  • client_id (path param)
  • limit_count
  • window_seconds

Edge cases

  • Lowering a limit while a window is already in progress

What a Strong Candidate Should Notice

  • Recognize this is a latency-critical, high-QPS infrastructure component, not a typical CRUD app
  • Discuss that slight inaccuracy might be an acceptable tradeoff — a non-functional judgment call
  • Separate the 'policy' entity (configuration) from the 'counter' entity (live state)
  • Think about what happens for a client with no configured policy

Common Mistakes

  • Treating this like a normal read-heavy CRUD service and ignoring latency constraints
  • Not distinguishing between rate-limit configuration data and fast-changing counter data
  • Designing an API that requires a full round trip to a slow database per check
  • Forgetting to return remaining quota / reset time, which callers need to behave well

Problem 4 — Personal To-Do List (Multi-Device Sync)

Basic Productivity

Problem statement: Design a to-do list app where a user can create, complete, and delete tasks, with changes syncing across their phone, tablet, and browser.

Context / scenario: A single user manages their own private list of tasks and expects it to look the same everywhere they log in.

What you are expected to determine:

  • What functionality is required for a personal (not shared) task list
  • How syncing across devices affects the API shape (not necessarily QPS)
  • What fields a Task needs to support ordering and completion
  • How to estimate scale even though this is a lower-traffic, personal-data system
Show Answer

1. Requirements Gathering

Functional Requirements
  • User can create a task with a title and optional due date
  • User can mark a task complete/incomplete
  • User can delete a task
  • User can list their tasks, sorted by due date or manual order
  • Changes made on one device appear on other logged-in devices
Non-Functional Requirements
  • Strong consistency is nice-to-have but eventual consistency across devices is acceptable within a few seconds
  • High durability — losing someone's tasks is a bad experience
  • Low latency for common operations (create/complete/list)
  • Data is private per-user, so access control matters even at small scale
Scale Requirements
  • How many active users and tasks per user on average?
  • How often does a user check/update their list per day?
  • Do we need real-time push sync or is polling-on-open acceptable?

Questions to ask the interviewer:

  • Is this single-user only, or could tasks be shared with others later?
  • Do we need offline support with conflict resolution?
  • Is there a limit on number of tasks per user?

2. Scale Estimation

Assumptions
  • 10 million active users, averaging 30 tasks each
  • Each user opens the app ~5 times/day, each session does ~3 reads and ~2 writes
  • Each task record is small, ~200 bytes
Calculations
Total daily writes = 10M users * 5 sessions * 2 writes ≈ 100M writes/day
Write QPS = 100,000,000 / 86,400 ≈ 1,157/sec ≈ 1.2K QPS
Total daily reads = 10M * 5 * 3 ≈ 150M reads/day → Read QPS ≈ 1,736/sec ≈ 1.7K QPS
Peak (mornings/evenings spike, ~3x) → ~3.6K write QPS, ~5.2K read QPS
Total stored tasks = 10M users * 30 tasks * 200 bytes ≈ 60 GB total
This grows slowly since task count per user is roughly steady-state (completed tasks may be cleaned up)
Final Numbers
  • ~1.2K write QPS avg, ~1.7K read QPS avg
  • ~60 GB total storage at steady state
  • Low absolute scale — this is not a bottleneck-heavy system

Uncertain / worth double-checking:

  • Whether completed/deleted tasks are retained for history or purged, which changes storage growth over time
  • Real usage pattern of sync frequency across multiple devices per user

What matters most for the design discussion: Even though QPS is modest, sync correctness and data ownership (per-user isolation) matter more than raw throughput here.

Entities
User

user_id, email, created_at

Owns a private set of tasks.

Task

task_id, user_id, title, due_date (nullable), is_complete, sort_order, updated_at

A single to-do item belonging to exactly one user.

APIs

Create a new task

Request

Response

{ "task_id": "t_881", "title": "Buy groceries", "is_complete": false }

Important parameters

  • title (required)
  • due_date (optional)

Edge cases

  • Empty title
  • Due date in the past
PATCH/v1/tasks/{task_id}

Update a task (e.g., mark complete)

Request

{ "is_complete": true }

Response

{ "task_id": "t_881", "is_complete": true, "updated_at": "..." }

Important parameters

  • task_id (path param)
  • fields to update

Edge cases

  • Task belongs to a different user
  • Concurrent edits from two devices
GET/v1/tasks?updated_since={timestamp}

Sync tasks changed since last check

Request

(none)

Response

{ "tasks": [ { "task_id": "t_881", "title": "...", "is_complete": true, "updated_at": "..." } ] }

Important parameters

  • updated_since (optional, enables incremental sync)

Edge cases

  • Clock differences between client and server
  • Very large updated_since gaps requiring a full resync

What a Strong Candidate Should Notice

  • Recognize that per-user scale can still be estimated even without huge global QPS
  • Think about 'updated_since' style APIs as the natural fit for multi-device sync
  • Call out eventual consistency across devices as an acceptable non-functional tradeoff
  • Keep entities simple — this doesn't need sharing/collaboration concepts unless asked

Common Mistakes

  • Assuming this needs the same architecture-scale thinking as a global consumer app
  • Forgetting to design for incremental sync (only supporting 'get everything every time')
  • Not considering per-user data isolation as a requirement
  • Overcomplicating the entity model with sharing/permissions that weren't asked for

Problem 5 — Simple Online Poll / Voting App

Basic Social

Problem statement: Design a service that lets a user create a poll with multiple options, share it via a link, and let others vote on one option, with live-ish result counts.

Context / scenario: A community organizer wants to quickly create a poll (e.g., 'best meeting time') and share it with 50–500 participants.

What you are expected to determine:

  • Functional scope: one vote per person, changeable votes, anonymous vs identified voters
  • How to estimate traffic for a bursty, event-driven product (spikes around poll creation)
  • Core entities for polls, options, and votes
  • APIs for creating a poll, casting a vote, and reading results
Show Answer

1. Requirements Gathering

Functional Requirements
  • User creates a poll with a question and 2+ options
  • Other users vote for exactly one option using a shared link
  • Poll creator/viewers can see live vote counts
  • Optional: poll can close after a deadline or manually
Non-Functional Requirements
  • Vote counts must be accurate — no double counting or lost votes
  • Reasonably low latency when reading results, especially near poll close
  • Availability during traffic bursts right after a poll is shared
  • Some mechanism to prevent trivial ballot-stuffing (e.g., one vote per session/device)
Scale Requirements
  • How many polls are created per day, and how many voters per poll?
  • Are votes anonymous or tied to accounts?
  • How 'live' do results need to be — real-time or a few seconds' delay?

Questions to ask the interviewer:

  • Should we prevent duplicate votes via login, cookie, or IP, and how strict does that need to be?
  • Can voters change their vote after submitting?
  • Is there a maximum number of options or voters per poll?

2. Scale Estimation

Assumptions
  • 500,000 polls created per day
  • Average of 40 votes per poll, but popular polls can get 10,000+ votes
  • Vote and poll-read traffic clusters heavily right after creation (bursty, not evenly spread)
Calculations
Total votes/day = 500,000 * 40 ≈ 20,000,000 votes/day
Average Write QPS = 20,000,000 / 86,400 ≈ 231/sec
Average Read QPS (result views, ~5x votes) ≈ 1,157/sec
Because traffic is bursty (a popular poll can get thousands of votes in minutes), Peak QPS could be 10–20x average rather than the usual 2–3x
Peak Write QPS ≈ 231 * 15 ≈ 3,465 ≈ 3.5K QPS
Peak Read QPS ≈ 1,157 * 15 ≈ 17K QPS
Storage: each vote record ~50 bytes → 20M * 50 bytes ≈ 1 GB/day ≈ 365 GB/year
Final Numbers
  • ~231 write QPS avg but up to ~3.5K at peak
  • ~1.2K read QPS avg but up to ~17K at peak
  • ~365 GB/year vote storage

Uncertain / worth double-checking:

  • Actual burst multiplier — a poll shared in a large group chat could spike far more than 15x locally
  • Whether vote-change (re-voting) meaningfully increases write volume

What matters most for the design discussion: The gap between average and peak load is the most important number here — this system must be designed around bursty, spiky traffic rather than a smooth average.

3. Core Entities / API Design

Entities
Poll

poll_id, creator_id (nullable), question, created_at, closes_at (nullable), is_closed

Represents a single poll and its lifecycle.

Option

option_id, poll_id, text, vote_count

One selectable choice within a poll.

Vote

vote_id, poll_id, option_id, voter_fingerprint, created_at

A single cast vote; voter_fingerprint (session/cookie/account id) used to prevent duplicates.

APIs

Response

Important parameters

  • question (required)
  • options (2+ required)
  • closes_at (optional)

Edge cases

  • Fewer than 2 options
  • Duplicate option text
POST/v1/polls/{poll_id}/vote

Cast a vote for one option

Request

{ "option_id": "opt_2" }

Response

{ "poll_id": "poll_44", "option_id": "opt_2", "accepted": true }

Important parameters

  • poll_id (path param)
  • option_id (required)

Edge cases

  • Duplicate vote from same voter
  • Voting after poll is closed
  • Invalid option_id
GET/v1/polls/{poll_id}/results

Get current vote tallies

Request

(none)

Response

{ "poll_id": "poll_44", "results": [ {"option_id":"opt_1","votes":12}, {"option_id":"opt_2","votes":30} ] }

Important parameters

  • poll_id (path param)

Edge cases

  • Very popular poll causing hot-read pressure on one poll_id

What a Strong Candidate Should Notice

  • Identify that this workload is fundamentally bursty rather than smooth, and reason about peak-vs-average differently than earlier problems
  • Think about duplicate-vote prevention as a real functional/non-functional requirement
  • Notice a single popular poll can become a 'hot key' read pattern
  • Separate Poll, Option, and Vote as distinct entities instead of cramming into one

Common Mistakes

  • Using a flat 2-3x peak multiplier without recognizing this workload can spike far higher
  • Not addressing duplicate voting at all in requirements
  • Merging vote counts directly into the Option entity without considering audit/history needs
  • Forgetting to handle the 'poll is closed' edge case in the vote API

Problem 6 — Simple Blog Publishing Platform

Basic Content

Problem statement: Design a platform where authors can write and publish blog posts, and readers can browse and read them.

Context / scenario: Think of a lightweight Medium-style platform: authors write posts, readers browse a list and read individual articles.

What you are expected to determine:

  • What functionality separates authors from readers
  • Read vs write ratio for a content-publishing platform
  • Core entities: Author, Post, and how they relate
  • APIs for publishing and reading posts
Show Answer

1. Requirements Gathering

Functional Requirements
  • Author can create, edit, and publish a post (title + body)
  • Reader can list published posts and read an individual post
  • Author can save a post as a draft before publishing
  • Optional: posts can have tags for browsing by topic
Non-Functional Requirements
  • Read-heavy: far more people read posts than write them
  • High availability for reads (a down blog looks bad)
  • Reasonable durability for drafts (authors shouldn't lose work)
  • Moderate consistency — a newly published post can take a few seconds to appear in listings
Scale Requirements
  • How many authors and posts published per day?
  • How many reads per post on average (some posts go viral)?
  • Average post size (affects storage)?

Questions to ask the interviewer:

  • Do we need comments/likes in this scope, or just publishing and reading?
  • Should unpublished drafts be excluded from all read APIs?
  • Is there a need for versioning/edit history of posts?

2. Scale Estimation

Assumptions
  • 50,000 new posts published per day
  • Average post body size 5 KB (mostly text, images referenced by URL not stored inline)
  • Average of 200 reads per post over its lifetime, spread over time
  • Read:Write ratio roughly 50:1 in steady state
Calculations
Write QPS (new/edited posts) = 50,000 / 86,400 ≈ 0.6/sec (very low)
Total reads/day ≈ 50,000 posts * 200 reads, spread across their lifetime — but focusing on *today's* reads across all historical posts: assume 50M read events/day platform-wide
Read QPS = 50,000,000 / 86,400 ≈ 579/sec ≈ 600 QPS avg
Peak (3x, plus occasional viral spikes) ≈ 1.8K QPS typical peak
Storage per day = 50,000 * 5KB ≈ 250 MB/day ≈ 91 GB/year
Read bandwidth ≈ 600 * 5KB ≈ 3 MB/sec avg
Final Numbers
  • Write QPS negligible (<5/sec even at peak)
  • ~600 read QPS avg, ~1.8K peak
  • ~91 GB/year content storage

Uncertain / worth double-checking:

  • How 'viral' a single post can get — one highly shared post could dominate read traffic briefly

Edge cases

What a Strong Candidate Should Notice

  • Explicitly separate ingestion load (trivial) from broadcast/fan-out load (enormous) as two completely different problems within the same system
  • Identify that frequent low-value updates (clock ticks) may dominate total load more than rare high-value events (scoring), and question that assumption with the interviewer
  • Model GameEvent broadly enough to include both meaningful official events and lightweight periodic ticks
  • Recognize a single game_id can become an extreme 'hot key' both for state reads and for live-stream subscriptions

Common Mistakes

  • Estimating this system as if read/write load were remotely balanced, when it's almost entirely a one-to-millions broadcast problem
  • Failing to ask whether periodic 'keep-alive' updates are even in scope before finalizing an estimate that could be off by an order of magnitude
  • Not recognizing a single popular game as a hot-key case distinct from the platform-wide average
  • Treating the ingestion path with the same design concern as the broadcast path, when they have almost nothing in common in terms of scale
